## A-0. 用語集

本文書では略語を初出時に説明し、以後もなるべく日本語表記を併用する。

- **ISA(命令セットアーキテクチャ)**: CPUが直接理解できる機械語命令の規格。CPUの
  「言葉」。Raspberry PiのArmとESP32のXtensa/RISC-Vは言葉が違うため、片方向けに
  コンパイルした実行ファイルはもう片方では動かない(実行ファイルの互換性がない)。
- **AOT(事前コンパイル)**: プログラムを実行する前に、あらかじめ対象チップの機械語まで
  翻訳しておく方式。実行しながら1命令ずつ翻訳する「通訳方式(インタプリタ)」の対義。
  WASMの実行環境では通訳方式に対しAOTは10〜50倍速いという報告がある。
- **ネイティブ実行**: そのチップ向けに直接コンパイルされた機械語を走らせること。
  翻訳層が一切なく、そのチップで出せる最高速度の基準。WASMをAOTしたコードは
  機械語として走るためネイティブに近い速度が出るが、(1)WASMという中間形式を経由する
  ことでコンパイラの最適化が甘くなる分、(2)サンドボックス(安全な実行環境)のための
  メモリ範囲チェック等が埋め込まれる分、ネイティブよりわずかに遅い。
  この上乗せコストと引き換えに「1本の.wasmを異なるISAのノードに配れる移植性」と
  「無線経由でのモデル差し替えやすさ」を得るのが、本設計でWASMを採るトレードオフ。
- **RTOS(リアルタイムオペレーティングシステム)**: 「決められた時間内に必ず処理を
  終える」ことを保証する軽量OS。FreeRTOS、Zephyrなど。マイコンでのセンサー周期読取や
  制御に使う。本文書で「マイコン」と言うときは、OSなし(ベアメタル)またはこの種の
  軽量OSで動く、RAM数百KB〜数MB級のチップ(ESP32、Arm Cortex-M等)を指す。
- **組込みLinux**: Linuxが動く小型ボード(Raspberry Pi Zero 2 / Pi 4、Jetson等。
  RAM 512MB〜数GB)。本文書では「マイコン」と明確に区別する。
- **OTA(無線経由更新)**: ネットワーク越しにファームウェアやモデルを書き換えること。
- **MQTT**: 出版購読(Pub/Sub)型の軽量メッセージングプロトコル。仲介役をブローカーと呼ぶ。
- **mDNS**: 同一ネットワーク内で機器同士が名前で発見し合う仕組み。IPネットワーク前提。
- **WASM(WebAssembly)**: 特定のチップに属さない共通の中間形式(バイトコード)。
  配布形式として使い、各ノードが自分の機械語にAOTする。

---

- **定義域分割 / テンソル分割(2026-08-22追加)**: どちらも「空間方向の分割」と
  呼ばれるが別物。定義域分割は座標入力の関数の担当範囲を切る(本プロジェクトの
  標準。MLPでも可能。領域分解PINNがこの系)。テンソル分割は入力配列そのものを
  切る(CNN向き。全域自己注意型は原理的に困難)。本仕様で単に「空間分割」と
  書く場合は定義域分割を指す。

## A. 仕様の具体化案

### A-1.0 プロジェクトの思想(2026-08-10追加、出典は2026-08-08付メモ)

以降の全仕様の上位にある3つの思想。個別の技術判断はこれらに照らして行う。

1. **群としてのAI**: 独立した多数のAIモデルが通信しながら協調して推論・学習し、
   互いに影響しながら動作する。この見方では中央のブローカーは本質ではなく、
   P2Pで通信できれば群は成立する(A-5改訂の根拠)。
2. **空間をAI化する**: 既存のワールドモデル学習は視覚依存度が高い。人間の感覚に
   基づかない多様な物理量のセンシングからワールドモデルを構成することを狙う。
   空間に分散配置されたマイコン群はそのための「感覚器の群」である。
3. **NNを動的に構成する**: 現存するマルチエージェントは固定構造のNNを並べて
   協調させる。協調推論中・分散学習中にエージェントのNN自体を動的に構成できる
   システムは新規性が高い(A-6に研究課題として追記)。
   補足(2026-08-22決定): 群は**最初から分割されて生まれる**ことを前提とし、
   動的性の主役は参加・離脱(ADD/REMOVE)とモデルサイズ変更(GROW/SHRINK)。
   実行中の領域の切り直し(SPLIT/MERGE/MOVE)は必須要件ではない。
   詳細: docs\2026-08-18-b16-design.md。

**界面の一般化(2026-08-22追加)**: 界面(独立に推論・学習する主体どうしが、
定められたフォーマットで境界量を交換する面)は、物理場の空間的な境目に
限らない。ロボット本体とエンドエフェクタの結合部(力・位置・トルク)、
ロボット同士の連携面も同じ骨格で扱える。界面フォーマットの標準化と界面残差の
監視・適応は、機器間のインタフェースのずれを吸収する道具になりうる。
Physical AI潮流への本プロジェクトの立ち位置は「補完」——単体ロボットの
巨大モデルを分割するのではなく、空間そのもの・機体の部位ごとの知能を
界面で繋ぐ側を担う(全域自己注意型モデルの空間分割が原理的に困難である
以上、群が得意なのは空間側の知能である)。

**開発方針(予算制約)**: ハードウェア購入予算が少ないため、ソフトウェア/
シミュレータの開発とシミュレータ上での検証に時間を割く。実機は手持ちの
ESP32×4台を上限とし、規模拡大の検証はシミュレータで行う(C章 M-S系列)。

### A-1. ターゲットハードウェアの枠組み：2つの限界探索(2026-08-05改訂)

全仕様がここに依存するため最初に決めるべき。資料では「マイコン」と一括りだが、
要求されている機能(MQTTブローカー/Webサーバー/WASMランタイム/ローカルキュー/
無線経由更新)はハードウェア階層によって実現可能性が大きく変わる。

**改訂の経緯**: 初版では「Class 1(マイコン)とClass 2(組込みLinux)を同一クラスタに
混在させるヘテロジニアス構成」を正式仕様として提案したが、混在運用はプロジェクトの
意図ではないことが確認されたため撤回する。本プロジェクトの目標は次の2つであり、
これは同一プラットフォームの**上下の限界探索**として、混ぜずに独立に検証する。

- **目標1**: マイコンだけで(=クラスタ全ノードがマイコンで)どこまでできるか、の限界を知る。
- **目標2**: 組込みLinuxを許容すれば何ができるか、の到達点を知る。

#### 各階層の能力の境界(判断基準はほぼRAM容量)

| 階層 | 例 | RAM | 成立する機能 | 成立しない/非常に厳しい機能 |
|---|---|---|---|---|
| マイコン(ベアメタル/リアルタイムOS) | ESP32系, Arm Cortex-M | 数百KB〜数MB | センサー収集、通信クライアント、軽量HTTPサーバー、小型モデル推論、境界同期つき協調推論 | Mosquitto級ブローカー、通常のWebサーバー、分散学習、大型モデル(FNO等) |
| 組込みLinux | Raspberry Pi Zero 2 / Pi 4, Jetson | 512MB〜8GB | 上記すべて+MQTTブローカー、Webサーバー、wasmtime、分散学習、キュー永続化 | 特になし(制約は電力とコストに移る) |

マイコン階層の内部にも境界がある。WASM実行環境の経験則として、RAM 256KB未満は
通訳方式のみの軽量ランタイム(Wasm3、フラッシュ64KB・RAM 10KB程度から動作)、
256KB以上でAOTが使えるならWAMR、という使い分けが知られている。AOTは通訳方式の
10〜50倍速いため、推論を伴う目標1の検証は実質的に「AOTが使えるマイコン
(ESP32-S3級以上)」が下限になる見込み。

#### 目標1(マイコン単独)の限界に関する現時点の見立て

- 到達できる見込み: データ収集、Pub/Sub、ローカルキュー(RAMリングバッファ)、
  小型サブモデルのAOT推論、隣接ノードとの境界同期(協調推論)、無線経由のモデル差替え。
- 限界となる見込み: ブローカー兼任ノードの役割(MQTTブローカー+Webサーバー)と分散学習。
  ブローカーは超軽量実装(組込み向けブローカーの移植 or 自前の最小実装)でどこまで
  縮められるかが目標1の研究課題そのものになる。学習はメモリと計算量から原理的に厳しく、
  「学習だけは目標1の範囲外」と結論づけることも成果として許容する。
- したがって目標1の検証項目は「4ワークフロー(収集/推論/学習/分割配置)のうち、
  どれが・どの規模まで・全マイコン構成で成立するか」の境界線を引くこと。

#### 目標2(組込みLinux)の到達点に関する現時点の見立て

計画資料に書かれた全機能(4ワークフロー+可視化レイヤーStep 1〜6)が技術的に成立する。
目標2の検証項目は機能の可否ではなく、性能・規模(ノード数、モデルサイズ、
同期周期)と運用性(電力、コスト、耐障害性)の定量化になる。

#### WASMを配布形式に採る理由(両目標をまたぐ設計判断)

目標1のチップ(Xtensa/RISC-V)と目標2のボード(Arm)は命令セットが異なるため、
ネイティブ配布ではチップ種別ごとにビルドと配布を分ける必要がある。WASMを共通の
配布形式にすれば、同じ.wasmを配って各ノードのランタイム(マイコンはWAMR、
組込みLinuxはwasmtime)がそれぞれの機械語にAOTでき、配布物とソースコードを
1本に保ったまま両目標を検証できる。速度のわずかな上乗せコスト(A-0「ネイティブ実行」
参照)と引き換えに、移植性と無線でのモデル差替えやすさを取る。

→ **決定済み(B-13, 2026-08-05)**: 実装の主軸は
  **(b) マイコン主軸(足し算)** とする。最初から限界に挑み、成立しない機能が
  実機で判明した時点でその機能を組込みLinux構成(目標2)へ移して比較する。
  この決定により、目標1の「限界を知りたい」は机上検討ではなく
  **実機での成立/不成立の判定**として遂行する。各マイルストーンの完了時に
  「限界レポート」(RAM・フラッシュ使用量、実行速度、成立/不成立の判定と理由)を
  記録し、これの蓄積がそのまま目標1の成果物になる。
  初期ターゲットボードの固定(例: 目標1=ESP32-S3のPSRAM搭載品、目標2=Pi Zero 2 W)は
  引き続き要決定(B-9)。

### A-3. コンパイラレイヤーの具体化

#### 入力の定式化(現仕様の最大の穴)
「重いランタイムを除去して計算グラフと重みデータを切り出す」とあるが、**入力形式が
未定義**。入力は性質の異なる2系統あり、統一パイプラインに乗せるには共通IRが要る。

- 系統1: 学習済みNN(PINNs / FNO / DeepONet等) → PyTorch等から **ONNXにエクスポート**
  したものを正式入力とする。ランタイム除去=「ONNXグラフ+重みだけを受け取り、
  tract/burnで裸の計算カーネルにAOTコンパイルする」と定義できる。
- 系統2: Rust製数値ソルバ → そもそも「計算グラフ」が存在しない。ソースコードである。
  ここは発想を変え、**ソルバ側にDyne SDK(トレイト)を実装してもらう**方式を提案する:

```rust
trait DyneSolver {
    type State;      // 担当領域の物理状態
    type Boundary;   // 境界面で交換する物理量+勾配
    fn step(&mut self, dt: f64, neighbors: &BoundaryInputs<Self::Boundary>);
    fn boundary_out(&self, face: FaceId) -> Self::Boundary;
    fn subdomain(&self) -> DomainSpec; // 空間範囲の宣言
}
```

  これを実装したクレートはコンパイラが `wasm32-wasip2` にビルドし、通信ロジックを
  ホスト側(ランタイムレイヤー)が注入する。つまり系統2の「分割」はコンパイラが
  自動で行うのではなく、**領域分割可能なソルバとして書いてもらい、分割数・境界
  トポロジーの決定と配置だけをコンパイラが担う**。系統1(NN)のみ自動分割の対象とする。

→ この整理により「同じパイプラインか別か」という課題(B-1)に答えが出る:
  フロントエンド2系統(ONNX取込み / SDKソルバ取込み) → 共通の中間表現
  (サブドメイン+境界トポロジー+実行体) → 共通のバックエンド(WASM化・パッケージ化・
  デプロイ)という **フロントエンド分岐・バックエンド共有** の1本パイプラインになる。

#### モデルアーキテクチャ別の分割可能性(リサーチタスクの下敷き)
空間方向分割の先行研究は存在し、方式がアーキテクチャごとに異なる:

- PINN系: XPINN / cPINN / FBPINN(領域分割PINN)。界面で物理量と勾配(またはフラックス)
  の連続性を損失に入れる。→ Boundary Sync Protocolと自然に整合。**最初に実装すべき系統**。
- 数値ソルバ(FDM/FVM/FEM): 古典的なドメイン分割(ハロー交換)。最も枯れている。
  → M0の題材に最適(1D/2D熱伝導方程式)。
- FNO: スペクトル畳み込みが**大域演算**のため素朴な空間分割は不可。
  局所化変種(Local FNO, domain-decomposed FNO)の追試が必要。→ 研究タスクとして分離。
- DeepONet / Transformer系PhysicalAI: attentionが大域のため同様に不可。
  「分割せず同一モデルを各ノードに複製し、担当領域の入力だけ変えて協調推論」という
  資料中の代替案(モデル並列でなくデータ空間並列)をこの系統の正式ルートにする。

#### 出力コンテナ形式の定義(POST /deploy のペイロード仕様を兼ねる)
`.dynepkg` (tar) を定義する:

```
model.wasm          … AOTコンパイル済みアクター
manifest.toml       … 下記
weights.bin         … 量子化済み重み(wasmに埋めない。差し替え可能にする)
```

manifest.toml の必須項目:
subdomain(担当空間範囲) / faces(境界面IDと隣接ノードの論理名) /
exchange_schema(境界で交換する物理量・勾配の型とバイトレイアウト) /
dt_policy(タイムステップ規約) / version / model_hash / 必要リソース(RAM/flash)

---

追記(2026-08-10, M-S0知見3): .dynepkgのマニフェスト検証には**数値スキームの
安定条件チェック**(陽解法ならα·Δt/h²≤1/2等、スキームごとの条件をmanifestに宣言)
を含める。M-S0で安定条件違反の構成が発散(NaN)する事故を実際に踏んだ。
実機デプロイ後に発散へ気づくのでは遅く、コンパイル/デプロイ時に拒否すべき。

### A-4. Boundary Sync Protocol の具体化

現仕様の矛盾を先に指摘する(→B-2):協調推論が「隣のマイコンとしか通信しない」のに、
通信をMQTT(ブローカー経由)に載せると、ブローカーが推論のクリティカルパスに入り
「ブローカー非依存の原則」に反する。したがって:

**具体化案:境界同期はブローカーを経由しないP2P直接通信(UDP、必要ならQUIC)とする。**
MQTTは「収集データ・推論結果の外部公開/監視」専用、境界同期は別プレーンに分離する。

- コントロールプレーン: MQTT(データ公開・コマンド・ハートビート)
- シミュレーションプレーン: 隣接ノード間P2P(境界同期)

メッセージスキーマ案(1メッセージ=1境界面×1ステップ):

```
BoundaryMsg {
  face_id: u16,        // manifestで規定した境界面
  step: u64,           // 論理タイムステップ(壁時計は使わない)
  seq: u32,            // 再送検出用
  payload: bytes,      // exchange_schema通りの物理量+勾配(固定長)
  crc: u32,
}
```

同期モデル案(要検討・B-3):
- 基本は **ステップ同期(BSP型)**: 全ノードが step n の境界値を交換してから n+1 へ進む。
  正しさの検証が容易なのでM0はこれ。
- 不安定ネットワーク対策として **有界非同期(bounded staleness)** をオプション化:
  隣接の境界値が最大 k ステップ古くても外挿(前回値 or 線形外挿)して進行を許す。
  k を超えたら停止してMQTTに劣化通知。XPINN系は界面損失で吸収できるため相性が良い。
- 時刻はすべて論理ステップで扱い、壁時計同期(NTP/PTP)には依存しない。
  実データ同期(データ同化)のときのみセンサータイムスタンプを使う。

M0実測からの追記(2026-08-05、詳細は docs\2026-08-05-m0-report.md):
- **過去ステップ再送応答**: BSP同期ではノード間のずれは最大1ステップ。各ノードは
  直近2ステップ分の送信済みメッセージを控えとして保持し、過去ステップの重複を
  受信したら控えを再送して応答する。起動レース(相手のbind前の送信消失)と
  走行中のパケット消失を同一機構で治癒できることを実測で確認。
- **終了時ドレイン**: 最終ステップ後も一定時間受信を続けて再要求に応答してから
  終了する。先に終えたノードが即終了すると相手が置き去りになる。
- **再送の最小間隔(バックオフ)**: 受信エラーを一律タイムアウト扱いにして
  即再送すると、OSによっては再送が高速に空回りする(Windowsでは未bindポート宛
  送信後のICMP到達不能で受信が即エラー戻りする。実測resend=201)。再送には
  最小間隔を設ける。
- **界面IDの一意化(仕様変更)**: face_idは「送信者から見た面」ではなく、
  manifestで規定するクラスタ全体で一意な界面IDとする。ノード視点の変換を
  不要にする(M0で変換漏れバグが実際に混入したため)。M1で実装に反映する。

### A-5. ランタイムレイヤー(通信基盤)の具体化(2026-08-10全面改訂)

#### 決定: ブローカーレス構成へ転換

「群としてのAI」(A-1.0)の観点から再検討し、**MQTTブローカーは当面不要**と判断。
これに伴い、旧仕様の一連の機構——mDNSによるブローカー選出、epoch式リーダー選出、
リース、スプリットブレイン対策——を**まるごと撤回**する(ROS2のDDSが中央
ブローカーを持たないP2P pub/subで成立していることを参考にした。ただしDDS自体は
RAM要件からマイコンでは困難)。

新しい3層構成:

1. **マイコン群の自律動作** → P2P pub/subで完結。中央ノードなし。
2. **群全体の観測** → 開発者PCが群の一員(peer)として参加し、ワイルドカード
   購読で全ノードのテレメトリを受ける。PCは「特別な管理者」ではなく
   「よく聞く参加者」であり、PCが不在でも群の動作は変わらない。
3. **同期的なコマンド** → 各マイコンの軽量APIサーバー(既存設計のまま存続)。

#### プレーン分離(M0設計を継承)

- **シミュレーションプレーン(境界同期)**: 現行のまま。自前のUDP・40バイト
  固定長バイナリ・論理ステップ同期(A-4)。pub/sub基盤には載せない。
- **コントロールプレーン(テレメトリ・コマンド・ハートビート・観測)**: ここを
  旧MQTT+選出機構の代わりに**zenohで置き換える候補**とする。マイコン側は
  軽量実装のzenoh-pico(実測フットプリント50KB未満、構成次第で15KB程度、
  ESP32動作実績あり)。

#### zenoh採用の検証項目と既知の課題(B-15)

- **ピアモードの成立性が核心**: zenoh-picoは歴史的にクライアントモード
  (ルーターへの接続)が先行し、ピアツーピアは後発。クライアントモード+PC上の
  ルーターという構成にすると、撤去したはずの中央ノードが名前を変えて復活する
  ことになり思想に反する。**マイコン同士がルーター不在でpub/subできること
  (ピアモード/UDPマルチキャスト)をESP32実機で成立判定する**ことが採用条件。
- **観測者不在時のデータ保持**(B-14): MQTTのretainやローカルキューイング相当を
  zenohでどう実現するか。ローカルキュー仕様(下記)との組み合わせで設計する。
- 不成立の場合の代替: 自前の超軽量pub/sub(UDPマルチキャスト+トピック前方一致)
  をコントロールプレーン専用に書く。要件はテレメトリ配送と購読だけなので
  MQTTブローカーよりはるかに小さい。

#### ローカルキューイングの仕様(存続・再定義)

- マイコン構成ではRAMリングバッファ+閾値超過時に古い低優先データから破棄。
  優先度: 障害通知 > 推論結果 > センサー生データ。上限・破棄ポリシー
  (oldest-drop)・再送レート制限をconfigで規定。
- 新しい役割: 観測者(PC peer)不在時のデータ保持装置を兼ねる(B-14)。
  観測者の再参加時に未送信分を吐き出す「追いつき配送」の要否も同時に決める。

#### トピック(キー)設計案(旧MQTTトピック案を継承)

zenohのキー表現でも同じ階層が使える。名前空間は維持:
```
dyne/{cluster}/tele/{node}/sensor/{ch}     … センサーデータ
dyne/{cluster}/tele/{node}/inference       … 推論結果
dyne/{cluster}/sys/{node}/heartbeat        … ハートビート(1〜5s周期)
dyne/{cluster}/sys/{node}/event            … 障害・劣化通知
dyne/{cluster}/cmd/{node}/**               … コマンド(REST APIの非常用ミラー)
```
観測者はdyne/{cluster}/**を購読する。{cluster}識別の運用はB-12のまま未決。

#### API仕様の追記(存続)

既存4エンドポイントに加え:
```
GET  /metrics       … リソース使用率(再分割計画エンジンの入力になる)
POST /deploy        … .dynepkg受領。A/Bスロット書込み→検証→切替。失敗時自動ロールバック
POST /rollback      … 前スロットへ戻す
GET  /boundary      … 境界同期の統計(遅延・欠損率)。Orchestratorの障害検知材料
```

#### 撤回した旧仕様の記録(再訪用)

2026-08-05版のA-5には、mDNS広告(`_dyne._udp.local`+TXTでcapability/priority/
epoch)、発見ウィンドウ内の(priority, node_id)最小ノードによるブローカー自己選出、
MQTTリース(retained)による死活監視、epoch比較によるスプリットブレイン解消、
seq付与+購読側重複排除、という一連の設計があった。ブローカーが将来必要になった
場合(例: 目標2のクラウド連携)はGitの履歴から復元する。

### A-6. 分散学習ワークフローの具体化(仕様の穴が多い。B-4参照)

前提の整理: 空間分割されたサブモデルは**ノードごとに重みが異なる**(担当領域が違う)ため、
FedAvg型の「同一モデルの重み平均」は適用できない。適用可能な形は:

- 形態1(領域別ファインチューニング): 各ノードが自領域のセンサーデータで自サブモデルを
  局所学習。界面整合性はXPINN型の界面損失(境界値・勾配の不一致ペナルティ)で保つ。
  境界同期は推論時と同じBoundary Sync Protocolを流用でき、追加で必要なのは
  「界面損失の勾配」の交換のみ。→ **最初にサポートすべき形態**。
- 形態2(複製モデルのフェデレーション): 分割不能モデル(FNO/Transformer系)を全ノードに
  複製した場合のみFedAvg等が成立する。集約役はブローカー兼任ノードが担う。
- 「再統合」の定義: 形態1では全サブモデル+領域マップをまとめて1つの区分的モデル
  (piecewise model)としてPCへ吸い上げ、`.dynepkg`の逆変換でアーカイブする、と定義する。
  重みを1つのネットワークに融合することは(蒸留を除き)仕様外とする。
- ロボット強化学習(将来): デジタルツイン校正学習とはデータフローも同期要件も別物
  (経験収集→方策更新のループ)。パイプラインは共有できるのは配布・OTA部分のみ。
  「分散学習ワークフローが2本走る」は正しく、ランタイムに**学習ジョブの多重実行と
  リソース隔離(実行スロット)**の概念を入れておく必要がある。設計だけ先行し実装は後回し。

#### NNの動的構成(2026-08-10追加、思想3に対応する研究課題)

固定構造のNN群を協調させるだけでなく、**協調推論中・分散学習中にNNの構造
そのもの(幅・深さ・分割粒度・担当領域)を動的に変えられる**ことを本プロジェクト
の研究上の柱とする。既存設計との接続: Physical Cluster Orchestratorの再分割
(A-8)は「担当領域の動的変更」としてこの一部を既に含む。残る未定義は
(a)何を動的にするかの定式化(B-16)、(b)構造変更時の重み引き継ぎ
(補間・蒸留・再学習のいずれか)、(c)変更のトリガー(精度劣化・負荷・ノード増減)。
実験はまずシミュレータ(M-S系列)で行い、実機は成立したものだけ持ち込む。

### A-7. データ同化(「現実データとシミュレーションの同期」)の具体化

資料では一文だが、実体は**データ同化(data assimilation)**であり手法の選定が要る(B-5)。
段階案: v1はナッジング(観測値へ緩和項で引き寄せる。実装が軽くマイコン構成でも動く) →
v2でアンサンブルカルマンフィルタ(組込みLinux構成限定。ノードあたり複数アンサンブルは
メモリ的に厳しいため簡約版を検討)。同化周期・観測誤差共分散はmanifestで宣言する。

### A-8. Physical Cluster Orchestrator(再分割)の入出力定義

再分割計画エンジンは以下を入出力とする関数として仕様化しておくと、後から実装しやすい:
```
入力: 物理トポロジー(領域マップ+センサー到達範囲) / モデル依存グラフ /
      残存ノードの /metrics / 現在のmanifest群
出力: 新しい領域マップ / ノード→サブモデル割当 / 再学習が必要な領域のリスト /
      推定精度劣化(界面増加数・解像度低下から推定)
```
精度劣化の推定方法自体が研究課題(B-7)。v1は「界面数の増分と担当領域の拡大率」を
プロキシ指標として提示するだけに留める。

## B. 仕様の不明点・矛盾点(優先度順)

- **B-1. パイプライン共有問題(資料中の課題)**: A-3で提案した通り
  「フロントエンド2系統・バックエンド共有の1本」+「ランタイムは収集/推論/学習を
  同一アクターの動作モードとして扱う」で解消できる見込み。ただし系統2(Rustソルバ)を
  SDK方式にすること自体が仕様変更(ユーザーにトレイト実装を要求する)なので要承認。
- **B-2. 境界同期の通信経路が未規定**: MQTT経由だとブローカー非依存原則と矛盾する。
  P2P直接通信プレーンの新設(A-4)を承認するか要決定。
- **B-3. 時間同期モデルが未規定**: ステップ同期か有界非同期か、外挿の許容範囲、
  停止条件。物理的な正しさ(数値安定性・CFL条件との関係)に直結する。
- **B-4. 分散学習の集約セマンティクスが未定義**: 「再度統合」が何を意味するのか
  (A-6の定義案を叩き台に要決定)。学習中の境界交換頻度、学習と推論の同時実行可否も未定。
- **B-5. 「現実データとの同期」の手法が未定義**: データ同化手法・周期・観測誤差の扱い。
- **B-6. 一貫性モデルが未宣言**: 分断・ブローカー交代時にデータの欠落/重複をどこまで
  許容するか。A-5案は「at-least-once + 購読側重複排除、欠測は記録」だが明文化が要る。
- **B-7. 精度劣化推定の方法が未定義**: 再分割時の推定精度提示(dyne rebalance --dry-run)は
  現状根拠となるモデルがない。プロキシ指標で始めることの承認が要る。
- **B-8. ネットワーク媒体と規模の想定が未記載**: Wi-Fi/Ethernet前提か(mDNSはIPネットワーク
  前提)。想定ノード数(4台か100台か)で選出・トピック・再分割の設計が変わる。
- **B-9. ターゲットハードウェア → 一部決定(2026-08-05)**: 目標1の初期ボードは
  手持ちの **ESPr Developer 32 Type-C ×4台**(ESP32-WROOM-32: Xtensa LX6 2コア240MHz、
  SRAM 520KB、フラッシュ4MB、PSRAMなし)とする。当初想定のESP32-S3+PSRAMより
  一段厳しい条件だが、WAMRの経験則(RAM 256KB以上でAOT可)は満たしており、
  目標1の限界探索としてはむしろ好適。留意点: (1)PSRAMなしのためWi-Fiスタックと
  同居した実効ヒープは200〜300KB程度の見込みでモデルサイズ境界が早く来る、
  (2)フラッシュ4MBでA/Bスロットは窮屈、(3)先行事例でAOTモジュールロード時の
  メモリ配置(mmap不可)の問題が報告されておりM1のリスク項目。
  目標2の代表ボード(Raspberry Pi等)は引き続き要決定。
  追記(2026-08-10): ニューラルネットの実機推論(M4)に進む際は、Xtensa AOT問題
  (M1b)の回避としてRISC-Vコアのボード(ESP32-C6等)を調査・入手する方針

- **B-11. 可視化レイヤーStep 4の負荷**: ブローカー兼任ノードにWebサーバー+UI配信+API中継
  まで載せると単一ノードへの集中が進む。組込みLinux構成なら成立するが、役割をさらに分離
  (Webサーバー担当を別ノードに選出)する選択肢も設計時に残しておくべき。
- **B-12. クラスタ識別**: 複数のマイコン群(複数拠点)をCLIが統合する際の

  **(b)マイコン主軸(足し算)を採用**。理由: 目標1(マイコン単独の限界)がこの
  プロジェクトの研究的な核であり、5〜10年後の需要から逆算する方針(2026-08-04メモ)
  とも整合する。制約下で鍛えた軽量設計はそのまま組込みLinux構成の品質にもなる。
  トレードオフとして受け入れるもの: 開発サイクルの遅さ(書き込み・実機デバッグ)、
  WAMR環境構築とno_std対応の先行コスト、プラットフォーム全体像の完成が遅れること。
  付随決定: 目標1の検証は机上ではなく実機判定で行い、マイルストーンごとに
  限界レポートを記録する(A-1参照)。C章はマイコン主軸で組み替え済み。

---

- **B-14. 観測者不在時のデータ保持(2026-08-10追加)**: ブローカーレス化により、
  MQTTのretain相当が失われた。観測者(PC peer)不在の間のテレメトリを
  ローカルキュー(A-5)でどこまで保持し、再参加時に追いつき配送するか。
  RAMリングバッファの容量制約との兼ね合いで「何秒ぶんを保証するか」を決める。

- **B-15. zenoh/zenoh-picoの成立判定(2026-08-10追加)**: 採用条件は
  「マイコン同士がルーター不在でpub/subできること(ピアモード)」。ESP32実機での
  RAM/フラッシュ実測とピアモード動作確認が必要。クライアントモード+PCルーター
  構成は中央ノードの復活であり思想に反するため不採用。不成立なら自前の
  超軽量pub/sub(UDPマルチキャスト)に切り替える。→ C章 M3で判定。

- **B-16. NNの動的構成の定式化 → 方針決定(2026-08-22)**:
  docs\2026-08-18-b16-design.md(全面改訂版)にて確定。前提=最初から分割されて
  生まれる群。主役オペレータ=ADD/REMOVE/GROW/SHRINK(機能保存の原則、
  評価軸=乱れ・回復時間・コスト)。界面の情報共有フォーマット=重複なし+
  値・勾配を標準。最初のNN実装=領域分解PINN型。SPLIT/MERGE/MOVEと
  「場の標本の持ち運び」は任意の付録(恒久死回復等)へ。M-S1はa(ADD/REMOVE機構、
  差分法でビット一致基準)→b(DD-PINN)→c(界面残差トリガー)の順。
  新規性検証済(2026-08-22): 適応的な領域分解PINNは既出(AB-PINNs等、学習時・
  単一計算機)。主張は「分散自律・実行時・資源適応の再構成」というシステム層に
  再配置(設計書8章)。

- **B-17. シミュレータの忠実度(2026-08-10追加)**: シミュレータ検証を実機の
  代替として成立させるには、実機実測値の注入が要る。現時点で注入できる値:
  ステップ実行時間79.5ms(Classic通訳・240MHz)、RAM上限(実効約250KB)、
  Wi-Fi遅延・欠損率(M2で実測予定)。ネットワークモデルの粒度(遅延分布・
  パケロス・分断)をどこまで作り込むかも要決定。
  追記(2026-08-10): 中間層としてEspressif公式QEMUフォークを使う場合も、
  サイクル精度がない(速度計測不可)・Wi-Fi非対応という限界があるため、
  時間と無線の忠実度は常に実機実測が正となる(C章「検証の3層構造」参照)。

## C. 実装ロードマップ案(マイコン主軸・2026-08-05改訂)

B-13の決定に従い、マイコン主軸(足し算)で組み替えた。原則は次の3つ。

- 各マイルストーンは「動くもの」と「限界レポート」(RAM・フラッシュ使用量、実行速度、
  成立/不成立の判定と理由)の2つを成果物とする。
- 実機で不成立と判明した機能は、その場で組込みLinux構成(目標2)の実装候補リストへ
  移し、マイコン側では追わない。目標2の実装はM6以降にまとめて行う。
- 実機サイクルの遅さを緩和するため、ロジックはまずPC上のWASM環境
  (wasmtime、あるいはWAMRのx86ビルド)で動かしてから実機に載せる。
  「PCで動く→実機で計測」を全マイルストーン共通の手順とする。

- **M0: PC上の2プロセス縦切りPoC(実機なし・選出なし) → 完了(2026-08-05)** —
  1D熱伝導方程式をRustソルバ(SDK方式)で2分割し、PC上の2つのWASMプロセスで
  境界同期(P2P/UDP・ステップ同期)を検証。**単一ノード解と全格子点でビット完全一致、
  解析解との誤差は理論次数どおり**。アクターWASMは2,184バイト(no_std・ヒープなし)。
  詳細と知見は docs\2026-08-05-m0-report.md。

#### 検証の3層構造(2026-08-10追記)

本プロジェクトの検証手段を3層で定義する。層ごとに捕まえられる問題の種類が
異なり、上の層ほど反復が速い。課題に応じて適切な層を選ぶ。

| 層 | 手段 | 実行するもの | 捕まえる問題 | 限界 |
|---|---|---|---|---|
| 上 | **M-S0シミュレータ** | 実機と同一のWASM + PCホスト | プロトコル論理、規模(Nノード)、故障回復、研究テーマ(動的NN・分散学習) | ESP-IDF層・実機ハードの問題は見えない |
| 中 | **QEMU(Espressif公式フォーク)** | 実機用ファームウェア一式(main.c+WAMR+ESP-IDF) | ESP-IDF層の統合問題(例: M1で踏んだpthread制約・fast-interpロード失敗の類)。書き込み往復なしで反復可 | サイクル精度なし(速度計測不可)。Wi-Fiなし(仮想イーサネット代替)。メモリ保護の忠実度は不確か |
| 下 | **実機(ESPr Developer 32 Type-C)** | 同上 | 時間(ステップ実行・同期遅延)、無線(Wi-Fi遅延・欠損)、電力、メモリ保護の真実。**校正値の源泉** | 反復が遅い(書き込み・手動操作)。台数上限4 |

運用原則: (1) 計算の正しさはWASMの同一性により全層で共有される(M1でPC/実機の
全桁一致を実証済み)。(2) 時間の忠実度は下層が正であり、上層は下層の実測値で
校正する(B-17)。(3) QEMU層は必須ではなく、実機書き込みの往復が開発の律速に
なった時点で導入する(導入自体をマイルストーンにはしない)。

#### シミュレータ系列(M-S、2026-08-10新設。実機系列と並行)

予算制約(A-1.0)により、規模拡大・動的NN構成・分散学習の研究はシミュレータで
先行させる。M0の構成(PC上のホスト+WASMアクター)がそのまま種になる。

- **M-S0: Nノードシミュレータ基盤 → 完了(2026-08-10)** — 単一プロセス・
  離散イベント・仮想時刻のシミュレータ(crates/dyne-sim)。合格基準を達成:
  N=16ビット一致、ロス10%+遅延+停止+分断の複合注入下でもビット一致を維持し
  自己回復。同一シードで完全再現。実機校正(79.5ms/ステップ、RAM上限拒否)動作。
  界面ID一意化・再送バックオフをここで初実装(M2の実機実装も同仕様とする)。
  詳細: docs\2026-08-10-ms0-report.md。
- **M-S1: 動的NN構成の実験場(2026-08-24にa/b/cへ細分化)** — B-16の
  定式化(docs\2026-08-18-b16-design.md)に基づき、協調推論中の参加・離脱・
  サイズ変更をシミュレータ上で実験する。
  - **M-S1a: ADD/REMOVEの機構 → 完了(2026-08-24)** — 差分法アクター
    (無改変のheat1d_actor.wasm、状態書き込みAPI dyne_set のみ追加)で、
    (前半)状態移送つき離脱・復帰=`--handover`、(後半)解釈βの領域拡張ADD=
    `--add` を実装。合格基準3点を達成: 参照解とのビット一致(後半は複合参照解、
    2〜8ノード・カオス注入・handover併用込み)、参加直後の乱れ・回復時間の計測、
    既存検証(M-S0系)の回帰維持。設計原則「状態移送で運ぶのは物理状態のみ、
    通信状態はプロトコルの再送に治させる」と「境界条件の切り替え=再init+状態復元
    (handover機構の再利用)」を確立。残課題: 参加ステップの整列は大域情報に
    依存(実システムでの合わせ方はM3以降)、隣接ノード同士の同時ADDは未対応。
    詳細: docs\2026-08-24-ms1a-report.md。
  - **M-S1b: DD-PINN型アクターでのADD/GROW/SHRINK → 完了(2026-08-26)** —
    時刻離散化PINN(座標xを入力する小型MLP、幅16×1層、LM法)を共有Rustクレート
    crates/heat1d-pinn-actor として実装しWASM化。ノード間で運ぶ状態は格子点の
    温度のみ(重みは運ばない)。GROWは零重み拡張で機能保存(全格子点ビット一致)、
    SHRINKは末尾ニューロン削除+温め。合格基準3点: (i) 決定論(同一入力で全出力
    ビット一致、カオス注入込み)、(ii) 解析解との最大誤差がN=1〜8で1e-4台
    (差分法と同水準)、(iii) 動的構成の乱れ・回復時間の計測(誤差CSV)。
    必須計測の「N増加時の劣化」はN=16で2e-2を確認(1ノード5点では残差評価点が
    不足、粗い補正なしの領域分解の理論と整合)。残課題: N=16劣化の対策(中点を
    残差評価点に追加)、解釈βのADD試験の段差問題(解釈α型ADDの実装で比較)、
    LM法の行列(約1MB)はESP32のRAM上限を超えるため実機化には別の最適化器が要る。
    詳細: docs6-08-25-ms1b-report.md。
  - **M-S1c: 自動トリガー** — 界面残差に基づくT2トリガーの自動化、
    「発火しないことが正解」のシナリオ、中央集権型適応との比較。
- **M-S2: 分散学習(界面損失)の先行実験** — 実機M6の前哨。XPINN型の領域別学習を
  シミュレータで成立させ、通信量・収束性を測ってから実機に持ち込む。

実機系列(M2〜)は「シミュレータで動いたものの実機判定」に役割を寄せる。
限界レポートの思想は不変: シミュレータの結果は実機実測値で校正されて初めて
目標1の証拠になる。

各マイルストーンの終わりに、確定した仕様と限界レポートをdocsに追記していく。
目標1の最終成果物は「全マイコン構成で成立する機能の境界線」を示す限界レポートの
総集編であり、目標2の成果物は全機能が動くプラットフォームそのものである。
