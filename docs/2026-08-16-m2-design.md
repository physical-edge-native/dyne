# 2026-08-14-M2設計書(docs\2026-08-16-m2-design.md)

## 目的

実機のESP32を2台、無線LAN(Wi-Fi)で接続し、M0で確立した境界同期プロトコルを
本物の無線ネットワーク上で成立させる。あわせて、シミュレータ(M-S0)の校正に
必要な無線の実測値を採取する(B-17)。

成果物は「動くもの」(2台での協調推論の完走)と「限界レポート第4号」
(無線の遅延分布・喪失率・同期オーバーヘッド・Wi-Fi込みのメモリ残量)。

## M2で実装する仕様(これまでの決定・知見の実機反映)

1. **境界同期プロトコル一式のC移植**: M0のホスト(Rust)で実装した
   BSP同期・40バイト固定長メッセージ・CRC32・送信控えの保持・
   過去ステップ再要求への応答再送・終了時ドレインを、ESP-IDF上のCで実装。
2. **界面IDの一意化**(M0知見3): メッセージはクラスタ一意の界面番号を運ぶ。
   M-S0で初実装済みの方式を実機に持ち込む。2台構成なので界面は0番のみ。
3. **再送バックオフ**(M1知見4): 再送に最小間隔を設ける。
4. **pthread規約**(M1知見3): WAMR処理は必ずpthread上で実行。
5. **CPU 240MHz**(M1知見5): sdkconfig.defaultsに含める。
6. 実行方式はClassic通訳(M1bの結論による確定値79.5ms/ステップ)。

## 問題設定と合格基準

M0と同一: 全域[0,1]を65点、ノードA=[0,0.5]の33点、ノードB=[0.5+h,1.0]の
32点、α=1、dt=1e-4、2000ステップ。

**合格基準: 分割解が単一ノード解とビット完全一致すること。**
実機2台の値を全点PCへ持ち帰るのは煩雑なので、判定は次で行う:
各ノードが終了時に自分の温度配列のバイト列のCRC32(誤り検出用の要約値、
32ビット)を表示し、PC上で単一ノード解の対応区間から計算した期待値と
照合する。CRC32一致は実用上ビット一致と同義(不一致の見逃し確率は約42億分の1)。
補助として代表点の値(17桁表示)と解析解との誤差も表示する。

## 計測項目(限界レポート第4号 → シミュレータ校正への注入値)

| 項目 | 用途 |
|---|---|
| 境界メッセージの往復遅延(RTT)の分布(最小/中央値/95%点/最大) | M-S0の--lat-ms/--lat-jitter-msの根拠値 |
| メッセージ喪失率(再送統計から推定) | M-S0の--lossの根拠値 |
| 1ステップの全体時間と、計算時間(79.5ms)との差=実測同期オーバーヘッド | M-S0の予測(理想NWで+0%)との突き合わせ |
| Wi-Fi起動後の空きメモリ・実行後最小空きメモリ | 「Wi-Fi込みで載る」ことの実証(M1では119KB残、Wi-Fiスタックは目安70KB前後) |
| resend/replay回数 | プロトコル自己回復の実働記録 |

## 要決定: 接続形態(B-8の一部)

無線の繋ぎ方に3案ある。**どれにするか選んでほしい。**

**案a: 既存のWi-Fiルーター経由** — 2台とも家庭のルーターに接続し、
互いのIPアドレスでUDP通信する。
- 利点: ファームウェアが最も単純。PCも同じネットワークにいるため、
  将来の観測(M3)への接続が自然。
- 欠点: ルーターの性能・混雑が計測に混入し、再現性が落ちる。
  ルーターのSSID/パスワードをビルド設定に入れる手間。
  ルーターによっては端末間通信を遮断する設定(AP隔離)があり、事前確認が要る。

**案b: 1台をアクセスポイント化して直結(推奨)** — ノードAが自分で
Wi-Fiネットワーク(例: SSID "dyne-m2")を立て、ノードBがそこへ接続する。
外部機器に依存しない。
- 利点: 環境非依存で再現性が高い(計測値が「ESP32同士の素の無線特性」になり、
  シミュレータ校正値として最も筋が良い)。SSID/パスワードを固定値で
  焼き込めるため設定作業ゼロ。ルーターの都合と無関係。
- 欠点: A側にアクセスポイント役のメモリ負荷が上乗せされ、2台のメモリ条件が
  非対称になる(ただしそれ自体が良い計測データになる)。

**案c: ESP-NOW(Espressif独自の直接通信)** — Wi-Fi接続の手続きなしに
MACアドレス宛てで直接フレームを送る方式。
- 利点: 遅延が最小クラス。接続確立が不要。
- 欠点: **Espressif独自方式**であり、汎用プロトコル(UDP前提のA-4)から
  逸脱する。目標2(組込みLinux)へ持ち込めず、設計の一般性を損なう。
  M2の目的には過剰適合。

**推奨は案b。** 理由は計測の再現性(校正値の質)と設定レスの2点。案aは
M3(観測者PCの参加)の際に追加で検証すれば足りる。案cは高速化が必要になった
将来の飛び道具として温存する。

## アーキテクチャ(案b前提の概要。a採用なら接続部のみ差替え)

```
ノードA (アクセスポイント役, 192.168.4.1)     ノードB (子機役, 192.168.4.2)
┌────────────────────────┐      ┌────────────────────────┐
│ pthread: 計算+同期ループ        │      │ pthread: 計算+同期ループ        │
│  WAMR(Classic) + actor.wasm   │ UDP  │  WAMR(Classic) + actor.wasm   │
│  担当 [0, 0.5] 33点            │←───→│  担当 [0.5+h, 1] 32点          │
│  界面0の右側                    │ 40B  │  界面0の左側                    │
└────────────────────────┘      └────────────────────────┘
```

- 同一ファームウェアで、役割(A/B)はビルド設定(menuconfigの専用項目)で切替。
- Wi-Fiの省電力機能は無効化する(有効だと受信が間欠になり遅延が数十〜
  数百ミリ秒暴れる。計測の大敵)。
- ステップループはM0と同一の3拍子: 送信→相手のステップn受信まで待つ
  (タイムアウトで控え再送)→計算。

## リスクと対策

- **Wi-Fi省電力による遅延暴れ** → 起動時に省電力オフを明示。
- **初回パケットの遅延**(アドレス解決の初回コスト) → 計測はウォームアップ
  100ステップ後から集計。
- **メモリ**: Wi-Fi込みで線形メモリ128KBが確保できるか。M1実績(残119KB)と
  Wi-Fi目安70KBからギリギリの見込み。不足時はアクター側の格子上限を縮めた
  軽量版wasm(線形メモリ64KB)へ切替える予備手順を用意する。
- **書き込みの2台運用**: COMポートが2つになる。手順書でポート確認方法を明記。
