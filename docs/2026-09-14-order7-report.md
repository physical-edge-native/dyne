## 1. 7a: 制御面MQTT第1段

- **規約を文書化**(docs\2026-09-14-mqtt-control-plane.md): トピックをノードID・
  界面IDに対応させ(`dyne/node/<id>/...`、`dyne/iface/<id>/residual`)、各ノードが
  必ず応答すべきトピックとメッセージ形式を規定。独立の「軽量API」は設けず、
  **規約そのものが差込口**。
  - 設定注入: `dyne/cfg/<id>`(retained)で境界条件キー・担当区間・シード・
    モード・界面の結線(データ面UDPの相手)・観測周期を一括注入。応答義務
    `ack`(受理/拒否+ペイロードCRC32)。
  - 参加・離脱: `status`(retained)+**LWT**(遺言メッセージ)で不意の離脱も
    通知。`online` にMACとIPを載せ、RSSIのMAC→ノードID解決と結線情報の
    材料にする。
  - 観測: 温度場(field)・界面残差(residual、界面の左側ノードのみ=
    シミュレータの記録規則と同一)・リアルタイム率(rt)・センサ(sensor)・
    RSSI(rssi)。**ワイルドカード購読**(`dyne/node/+/field` 等)で全域観測。
  - 層の規律: データ面(40バイト意味論+UDP直送)はMQTTを通らない。制御面の
    MQTT依存はノード側1ファイル(dyne_mqtt.c)に閉じ、第2段(B-15判定次第の
    zenoh-pico移行)ではその層だけ差し替える。
- **PC側ツール**(ワイルドカード購読の実現):
  - scripts/mqtt_observe.py … `dyne/#` 購読+種類別CSV記録(field/sensor/rssi/
    rt/residual/status)。
  - scripts/mqtt_config.py … 1次元チェーン設定の生成・注入・start。格子分割は
    シミュレータと同一規則。`--absent`(部分観測)と `--bc` 4キー対応。
    transparent の指数和係数はPC側で計算して注入(規約§2.1)。
  - どちらも paho-mqtt 使用(pip導入済み)。ブローカーは mosquitto 等を想定
    (ユーザーのPCへ別途インストール)。

## 2. 7b: 実機ファーム更新(node-esp32/、m2-esp32ベース)

m2-esp32(2台固定・コンパイル時役割)を土台に、**設定注入駆動の汎用ノード
ファーム node-esp32/** を新設(m2はマイルストーン成果物として凍結)。
全ノード同一ファームウェアで、ブートストラップは menuconfig の3項目
(Wi-Fi・ブローカーURI・ノードID)のみ。

| 発注項目 | 実装 |
|---|---|
| (i) 規約への応答 | cfg受理(cJSONで検証、ack、状態遷移)、ctl(start/stop/report/reboot)、status+LWT、観測の周期発行。BSP協調はm2の単一界面ループを**最大2界面へ一般化**(送信控え・応答再送・再送バックオフ・終了時ドレインはM0/M1知見のまま) |
| (ii) センサ読取 | DHT20(0x38、CRC8検証)と BME280(0x76/0x77、データシート整数補償式)のI2Cドライバ(sensors.c、IDF 5.5の新i2c_masterドライバ)。切替は設定注入 `mode.sensor`。読取値は sensor トピックへログ発行のみ(同化接続=発注8) |
| (iii) F1境界条件キー | **4キーすべて対応**。dirichlet(値つき)/zero_grad/linear_extrap はbcコードの注入のみ(実機wasmをF1対応版heat1d_actorに更新)。transparent は指数和係数をPCが計算し設定注入→ファームは dyne_transparent_coef へ流し込むだけ(要否報告は§3) |
| (iv) RSSI収集 | AP受信強度+プロミスキャス受信による近傍MACごとの受信強度(EWMA+フレーム数)。データ面のUDPフレーム自体が測定源になるため計算参加ノード間は追加通信なし。rssi トピックへ周期発行(rssi.c、Kconfigで無効化可) |
| (v) リアルタイム率 | ステップ実時間・計算時間・同期待ちの統計(窓ごとの mean/min/max)と rt_rate = Δt/実ステップ時間、Δt余裕を rt トピックへ周期発行。有界非同期転換(12月)の布石データ |

## 3. transparent の実機実装の要否報告(発注7b(iii))

**実装済み・推奨「要」**。コストは次のとおり極小:

- **メモリ**: 新wasm(F1対応版)の線形メモリ宣言は**2ページ=128KBで旧版から
  不変**(補助変数・係数の静的領域 約2.6KB は既存ページ内に収まる)。wasmファイル
  +1,310B(2,181→3,491B)。設定注入の係数JSON約2KBは受信バッファ(8KB)内の
  一時消費のみ。
- **演算**: 1ステップ・1面あたり、半陰的更新の積和 約4×M=128回(M=32)。
  M1実測の1ステップ79.5msに対し完全に無視できる(µs級)。
- ファーム側に exp/log の実装は不要(係数はPCで計算して注入する規約)。
- **未実測(ユーザー実機確認待ち)**: 実機での実ステップ時間への影響と
  ヒープ実測。rt トピックの compute_ms を dirichlet 設定時と transparent 設定時で
  比較すれば1コマンドで検証できる。

## 5. ユーザー実機確認の手順(最小2台)

1. PCで mosquitto を起動(未導入なら https://mosquitto.org/ から。
   `mosquitto -v` で1883待受、リスナーに `allow_anonymous true`)。
   PCのモバイルホットスポット(またはルーター)に全ノードとPCを接続。
2. 各ボード: node-esp32/ で `idf.py menuconfig` → Dyne Node(SSID・パスワード・
   `mqtt://<PCのIP>:1883`・ノードID 0/1)→ `idf.py -p COMx flash monitor`。
3. `python scripts\mqtt_observe.py --broker localhost` → 各ノードの
   `status: online`(MAC・IP)を確認。
4. `python scripts\mqtt_config.py --broker localhost --nodes 2 --points 65
   --steps 2000 --peers <IP0>,<IP1> --sensor dht20 --start`
5. 期待: ack(ok)→ configured → running(rt・field・residual が流れる)→
   約3分で done×2(CRC32)。mqtt_log/ にCSVが残る。
6. 比較用シミュレータ値(2026-09-18: `--crc` オプションを追加実装):
   `dyne-sim.exe --wasm ...heat1d_actor.wasm --nodes 2 --points 65 --steps 2000 --crc`
   → `CRC32(u bytes) = [node 0: 0x3CC6AD26, node 1: 0x8AC47DE7]` のように
   ノード別CRCを印字する。定義は実機の status: done の crc32 と同一
   (u[] の f64 リトルエンディアン連結の IEEE CRC32)。任意の構成
   (--absent・--unobserved-bc 込み)で使え、縮小版wasmを指定しても同値になる
   (バイト一致検証済み)。--crc なしの出力は従来と不変(回帰に影響しない)。
7. 復旧(ストール・離脱時、規約§3.5): `python scripts\mqtt_config.py
   --broker localhost --stop`(設定注入なしに ctl: stop のみ発行。2026-09-18追加)
   → 再設定(手順4)→ start。

## 6.5 検収回答(ローカル分、2026-09-18)への追記3点

ローカル検証項目はすべて合格、transparent実機実装「要」承認済み。以下は
検収回答で求められた明文化(規約 §3.5 にも同内容を追記済み):

1. **LWT発火時の残存ノードのBSPループ**: **ストール**(再送バックオフを続けて
   その界面で待つ)。pause扱い(相手復帰での自動再開)ではない——再起動した
   相手はステップ0から始まり整合しないため。回収は `ctl: stop`(走行中の受信待ち
   ループが毎スライスで stop を確認する実装)→ 再設定 → 再start。離脱の自動治癒
   (handover/ADDの実機化)は第1段のスコープ外(発注9以降)。
2. **ackの再送・タイムアウト・部分成功**: cfgはretained+QoS1で、ノードは受信の
   たびにackを返す(冪等=再注入がそのまま再送)。規約: **startは全計算ノードの
   ack(ok)確認後に発行**、ack欠落はタイムアウト(目安10秒)でcfg再注入。部分成功
   のままstartした場合も挙動は定義済み(未受理ノードは status err で無視、受理側は
   ストール→stopで回収)。mqtt_config.py の --start は簡易(1秒猶予)であり、
   確実な運用は mqtt_observe.py でack確認後にstartのみ発行。
3. **プロミスキャスRSSIの縮退**: 2段階を用意。(a) 実行時: `rssi_period_ms: 0` の
   設定注入で**プロミスキャス受信そのものを停止**(受信コールバックのCPUコスト
   ゼロ。再注入で再開)——検収回答を受けて追加実装し、再ビルド成功を確認。
   (b) ビルド時: Kconfig DYNE_RSSI_SNIFF でスニファをコンパイルから外す。

## 6.6 実機不具合対応(2026-09-18、実機確認①の途中報告への回答)

**症状**: ESPr Developer 32(PSRAMなし)で Wi-Fi 接続・IP取得後、
`WASM module instantiate failed: allocate linear memory failed` で停止。

**(1) 原因の切り分け**:

- **起動順の退行ではない**: M2 も「Wi-Fi → WASM初期化」の順だった
  (m2-esp32/main/main.c の m2_task: wifi_up() → WAMR init → instantiate)。
- **原因は新ファームのメモリ消費増**: WASMの線形メモリ128KBは**連続**した
  内部RAMを要する。node-esp32 は m2 に対して esp-mqtt・cJSON のリンク
  (静的RAM増)+MQTT送受信バッファ(計12KB)+組み立てバッファ(8KB静的)等が
  増えており、Wi-Fi起動後の**最大連続ブロック**が128KB+αを下回った
  (M2は同じ順序で成立していた=元々余裕が小さく、消費増で閾値を割った)。
- **診断ログを追加**: 起動直後・WASM後・Wi-Fi後・サービス後の4点で
  空きヒープ総量と**最大連続ブロック**(heap_caps_get_largest_free_block)を
  出力する(`[dyne] heap(boot): free=... largest=...`)。再現時の切り分けと、
  今後の余裕の定点観測に使う。

**(2) 修正案の選択肢とトレードオフ**(PSRAM/S3前提は不採用の条件どおり):

| 案 | 内容 | トレードオフ |
|---|---|---|
| (a) **採用・実装済み** | **WASM初期化をWi-Fi起動前へ移動**(起動直後の未断片ヒープで128KBを最初に確保)+MQTTバッファ縮小(受信8→4KB、送信4→2KB。transparent係数込みcfg約2.4KBは収まり、超過分は分割組み立てが受ける) | Wi-Fi・MQTTが残りヒープで動く必要がある(見込み〜100KB、Wi-Fiは〜70KB)。失敗が「Wi-Fi起動失敗」に転化する可能性は残る→診断ログで実測確認。機能影響なし(instantiateは設定に依存しないため順序は自由) |
| (b) 予備 | 小型アクターwasm(N_MAX を 4096→1024 等に縮小 → 線形メモリ**1ページ=64KB**)。M2の heat1d_actor_small.wasm の前例あり | ノードあたり格子点上限が下がる(実験1の13〜33点には十分)。wasmが2系統になり管理コスト増。数値は格子点数が同じなら不変だが要ビット一致確認 |
| (c) 予備 | WAMRインスタンスヒープ16→4KB・実行スタック16→8KB(アクターはno_std静的確保でwasm内mallocなし) | 〜20KBの節約。学習型アクター投入時(S3)にスタック要求の再調整が要るかもしれない |

(a)で不足なら (a)+(c)、それでも不足なら (b) を追加する段取りを推奨。

**(3) 「線形メモリ2ページ=128KBで不変」との整合**: あの報告は**wasm側の要求量**
の話で正しい(F1の追加静的領域約2.6KBは既存2ページ内に収まり、要求は128KBの
まま)。今回の失敗は wasm の要求が増えたのではなく、**ファーム側**の消費増で
128KBの連続ブロックが「Wi-Fi起動後には」残らなくなったことによる。すなわち
transparent実機コスト報告(§3)は不変で、問題は割当のタイミングにあった。

**経過**: (a)+診断ログを実装しフルビルド成功 → **実機再測定(2026-09-18)で
(a)の前提が不成立と判明**: heap(boot) largest=110,592(約108KB)。ESP32の
DRAMはハード的に区画割れしており(heap_init: 6KB/129KB/14KB/111KB)、最大区画
129KBから静的消費を引いた連続ブロックは約108KB——**起動直後でも128KBの
線形メモリは構造的に確保できない**(M2はBSSが小さく大区画がより広かったため
成立していた)。診断ログは意図どおり動作し、この切り分け自体が(a)の成果。

**(b) 縮小版wasmの実施(2026-09-18、ユーザー指示)**:

- **格子点上限と根拠**: N_MAX=4096→**2048**、wasmスタック32KB→**8KB** で
  線形メモリ**1ページ=64KB**(検証済み: wasmのメモリ宣言 min=1ページ)。
  根拠: 1ページ65,536B − スタック8,192B − 透過境界の係数・補助変数2,560B −
  リンカ予約1,024B ≈ 53KB、u/u_next の16B/点で理論上限≈3,360点 → 2の冪へ
  丸めて余裕をとり2,048点(実験1の必要13〜33点/ノードの60倍)。
- **管理方法**: **同一クレート+cargo feature「small」**(数値経路は配列サイズ
  以外完全同一)。ビルドは scripts/build-actor-wasm.ps1 がフル版(シミュレータ用、
  従来どおり)と縮小版(node-esp32/main/heat1d_actor_small.wasm へ複製)の
  2系統を一括生成。別クレート化・別ソース化はしない(二重実装の禁止と同じ理由)。
- **正しさの検証**: シミュレータで縮小版wasmを指定した3シナリオ(基本16ノード /
  transparent+warm ADD / 部分観測+ナッジング σあり)の**全出力がフル版と
  バイト一致**(PASS (bit-exact) も維持)。
- **(c) の併用 = 要と判断し実施**: WAMRインスタンスヒープ16→4KB・実行スタック
  16→8KB。根拠: アクターは no_std 静的確保で wasm 内 malloc を使わず、呼び出しは
  浅い(dyne_step は葉関数)。Wi-Fi・MQTT用の残りヒープを最大化する。
  見積り: wasm一式 ≈ 64+4+8+管理 ≈ 80KB → 108KB区画に収まり、全体では
  201KB−80KB ≈ 120KB が後続(Wi-Fi ~70KB+MQTT ~15KB)に残る。
- **実機での最終確認はユーザー確認待ち**(期待: after-wasm まで進み、
  Wi-Fi接続 → status online。heap 4点ログの値の記録もお願いしたい)。

**実機確認①の結果(2026-09-18、ユーザー実測)— 合格**:

- 2台協調(2ノード・65点・α1.0・dt1e-4・2000ステップ・seed42・境界既定)が完走。
  **実機CRC32 = node 0: 0x3CC6AD26 / node 1: 0x8AC47DE7 が、シミュレータの
  `--crc` 出力(および M2 当時の期待値定数)と完全一致 = 実機とシミュレータの
  ビット一致を確認**。l2 ≈ 5.6e-5・linf ≈ 8.0e-5(解析解比、シミュレータと桁一致)、
  再送2・応答再送2・CRCエラー0(2000ステップ)。
- **ヒープ定点(縮小版wasm+(c)適用後、2台ほぼ同値)**:
  boot free=201,780 / largest=110,592 → after-wasm 112,060 / 53,248 →
  after-wifi 62,280 / 43,008 → after-services 36,304 / 34,816。
  見積り(§上記)どおり: wasm一式約90KB、Wi-Fi後も最大連続43KB・総空き62KBで
  成立。以後この4点を実機の余裕の定点とする。
- **リアルタイム率の初期実測**: step_ms mean 52〜54(max 102〜174)、
  compute_ms mean 約41 → rt_rate ≈ 0.1ms/53ms ≈ 0.0019。M1実測(65点単一、
  79.5ms/step)に対し33点/ノードで約41msと整合。有界非同期転換(12月)の
  基準値として記録。
- センサ未配線のため sensor トピックは "i2c read" エラーの周期発行
  (設計どおりの縮退動作)。実機確認②(センサ実測)は配線後に実施。

**実機確認⑥の結果(2026-09-18、ユーザー実測)— 合格**: 走行中(step 510付近)の
USB抜去で、(a) 残存ノードのストール(計算系の発行停止、sensor/RSSIは継続)と
(b) LWT発火({"state":"offline","reason":"lwt"}、抜去から1〜2分後=ブローカーの
キープアライブ検知)をともに確認。規約§3.5の記載どおり。offline行が端末で
目視できなかった件は、mqtt_observe.py が全メッセージを画面+CSVに出す実装の
ため見落とし(CSVには記録済み)——ただし「重要イベントが観測系の流量に埋もれる」
指摘は実験1(5ノード)で悪化するため表示を改善: **status/ack行の色+行頭マーカー
強調**(offline/err=赤、online/configured=緑、done=シアン)と **--quiet-obs**
(観測系はCSVのみ、画面は制御系だけ)を mqtt_observe.py に追加(2026-09-18)。
復旧の第1手として mqtt_config.py --stop も追加済み(§5 手順7)。

**実機確認⑥の完了(2026-09-18、ユーザー実測)**: (c) stop→再設定→再start の
復旧まで確認され、done×2・CRC一致(0x3CC6AD26 / 0x8AC47DE7、l2・linf同値、
resend 1〜2、crc_err 0)で**⑥完了**。付随して発見された不具合と対処:

- **「start直後に即停止」事故の原因究明(2026-09-18 完了。当初の「応急処置前の
  残存retained」説は時系列不整合のため撤回・訂正)**:
  - **確定した原因 = ファームのstopフラグのラッチ**(仮説(c))。g_stop_req は
    いつでもセットされる一方、消費はBSPループ内のみ・クリアは中断時のみ
    だったため、**idle(configured)中に受けたstopは見かけ上無害のまま残留し、
    次のstartを最初の受信スライス(≤20ms)で即中断**させていた。証拠:
    status.csv の署名——事故1: running(1534.619)→stopped(1534.637)=**18ms**、
    事故2: 両ノードとも running→stopped=**1ms/0.5ms**。retained配達なら
    購読時(接続時)に届くためstartとのミリ秒同期は起こらない。1618.68秒の
    node 0 単独の stopped は走行中ノードへの正規のstop消費で、そのとき idle
    だった node 1 に(および再発行分が node 0 に)ラッチが残った。「応急処置後に
    再発しない」のは、事故2で両ノードのラッチが中断処理で消費・クリアされた
    ためで、応急処置(空retained送信)との相関は因果ではない。
  - **仮説(a) 棄却(再現実験)**: 実験当時の版と同一の発行
    (paho publish qos=1・retain引数なし)を行い、①先行購読者への配達は
    **retained=0**、②発行後の新規購読者(mosquitto_sub -F "%r %t %p")には
    **何も届かない**=貼り置きを作らないことを実測確認。現在のretained格納の
    全列挙(--retained-only)も status×2(LWT)+cfg×2 のみで **ctl の貼り置きは
    存在しない**。
  - **仮説(b) 棄却**: esp-mqtt は既定でクリーンセッションのためオフライン中の
    QoS1蓄積・再配達は発生せず、生存セッション内の重複は秒オーダーに限られる。
    分オーダー離れた2回の「start直後」を説明できない。
  - **不明として残る点**: ブローカー側の当時の記録は存在しない
    (mosquitto.conf は listener/allow_anonymous のみで、ログ出力・永続化とも
    未設定=retained格納はメモリのみ)。ラッチに至った個々のstop発行の正確な
    回数・時刻は status.csv からの再構成(上記)による推定を含む。
  - **修正**: (i) **start受理時に古いstopラッチを打ち消す**(startは常に新しい
    意思の表明。start後に届く新しいstopは従来どおり有効)、(ii) stop受信を
    警告ログで可視化。ビルド済み。
  - **維持する防御**: スクリプトの retain=False 明示と、ファームの
    **retained ctl 無視**(原因とは独立に有効な事故クラス遮断)。規約 §3.6。
  - **号令への世代番号・有効期限の要否(提案)**: **現時点では不要**。
    ラッチ排除により「古い号令が後から効く」経路は消え、stop/startは冪等で
    重複配達は無害。ノード間の時刻同期がないため有効期限方式はかえって脆い。
    将来、複数操作者や自動化で号令の取り違えが問題になったら、start に
    期待世代(cfgのgen)を載せてノード側で照合する方式を推奨(cfg側のgenと
    同じ仕組みの延長で実装可能)。
  - **cfg側で同種の事故が起きた場合の評価**: cfg は意図的に retained(宣言型)
    なので「古い貼り置きcfgが再起動ノードを旧設定でconfiguredにする」ことは
    起こりうるが、cfgは宣言であって即時の動作を起こさず、動き出す契機は start
    のみ。**gen照合(ackとstatusのエコーをPC側でstart前に斉一性確認)で検出は
    足りる**。強化するなら上記の「startに期待genを載せる」方式が同時にこちらの
    最終防壁にもなる(現時点では運用ルールで十分と判断)。
- **設定の鮮度管理(確認【2】への回答)**: 再起動ノードが retained cfg で自動
  configured になるのは**意図した仕様**(cfg=宣言型。再注入の手間とLWT復帰の
  自動化)。古い貼り置き設定の検出のため **世代番号 `gen`** を導入——注入ツールが
  UNIX秒で付与し、ノードは ack と status(configured)にエコー。PC側で全ノードの
  gen一致を照合できる。不要になったIDのcfgは空retainedで掃除(規約§3.6)。
- 状態変化の目視性(確認【1】)は前項の mqtt_observe.py 改善(色+マーカー・
  --quiet-obs)で対応済み。

## 6.7 ビルド障害対応: managed_components のハッシュ不一致(2026-09-18)

**症状**: `idf.py fullclean` が espressif__wasm-micro-runtime の core/version.h の
ハッシュ不一致(「managed_componentsが前回CMake実行以降に変更された」)で停止。

**(1) 直接編集したか**: **していない**(発注7以降の編集は node-esp32/main/ と
docs・scripts のみ。managed_components には一切触れていない)。

**(2) 変更の主体と性質**: WAMRコンポーネント自身の build-scripts/version.cmake が
**CMake configure のたびに core/version.h をソースツリー内へ configure_file で
再生成**する。Windows では configure_file が CRLF で書くため、パッケージ版
(LF、593バイト、CHECKSUMS.json のハッシュ e261247b…)と改行分の24バイトだけ
食い違う(CRLF→LF 正規化のみでパッケージ版ハッシュに**完全一致**することを
検証済み=内容の変更はゼロ)。Linux では再生成結果がパッケージ版と同一バイトに
なるため顕在化しない、**Windows固有のパッケージングの衝突**。意図した変更でも
事故でもなく、ビルドの副作用が毎回再発する構造のため「復元してやり直す」だけ
では解決しない。

**採った対処(設計判断)**: (i) version.h をパッケージ版(LF)へ復元。
(ii) **node-esp32/CMakeLists.txt に configure 完了後の LF 正規化を追加**——
コンポーネント本体には一切触れず、再生成された CRLF をパッケージ版とバイト一致
の LF へ戻すことで、以後のハッシュ検証が常に通る。エラーメッセージ推奨の
components/ への移動(=11MB・775ファイルのベンダーツリー化と依存の凍結)は、
差分が改行のみで内容改変が存在しない本件には過大と判断し不採用
(WAMR更新でこの副作用が解消されたら正規化スニペットは削除できる)。
実装細部: CMake の file(READ)/file(WRITE) はWindowsで**テキストモード変換**を
行い CRLF を扱えないことが判明したため、検出は file(SIZE)(バイト長)と
file(READ) の文字列長の差、正規化は python(ESP-IDF環境に常備)の
バイナリ置換で行う。

**(3) 検証**: 本環境で `fullclean → build → fullclean → build` の2サイクルを
連続実行し、**両サイクルとも合格**(各ビルドで「dyne: normalized wamr
core/version.h to LF」が発火し、fullclean のハッシュ検証を毎回通過)。
version.h は正規化済み(593バイト=パッケージ版とバイト一致)の状態で引き渡す
ため、**手元ではそのまま fullclean → build が通る**(要再確認)。

## 7. 実装上の判断(事後報告の小さな判断)

1. **新ディレクトリ node-esp32/**(m2-esp32 は凍結保存)。マイルストーン成果物を
   壊さず、以後の実験1〜5の共通ファームとして育てる。
2. **Wi-FiはSTA専用**(APはPCのホットスポット/ルーター)。M2のノードA=AP方式は
   ブローカー(PC)との同一セグメント化が煩雑なため第1段では不採用。
   17ノード規模の通信構成はB-18(ロードマップ8章)で判定。
3. **transparent係数はPC計算・設定注入**。ノード側のexp/log再実装を避け、
   数値の出所を一元化(規約§2.1に明記)。
4. **近傍RSSIはプロミスキャス受信**でデータ面フレームを測定源にする(追加通信
   なし)。CPU負荷が問題になった場合に備え Kconfig で無効化可。
5. status の `done` に CRC32・L2/Linf を載せ、M2の検証流儀(CRC照合)を
   規約に引き継いだ。
