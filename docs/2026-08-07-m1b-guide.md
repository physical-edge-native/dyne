# 2026-08-07-M1b手順書(docs\2026-08-07-m1b-guide.md)— AOT(事前コンパイル)への挑戦

## 目的と背景

M1aで通訳方式の速度限界(79.5ms/ステップ)が確定した。M1bでは、wasmを
事前にXtensaネイティブコードへ変換(AOT)してから実機に載せ、速度がどこまで
改善するかを実測する。

前提知識: AOT変換器`wamrc`の公式配布物にはXtensaバックエンドが入っておらず、
Espressif版LLVM(実験的Xtensaターゲット)を自前ビルドする必要がある(M1b調査で確定)。
このビルドはLinux前提のスクリプトが公式提供されているため、**ツールチェーン構築に
限りWSL2を使う**(案B)。書き込み・実行は従来どおりWindowsネイティブ。

**バージョン整合の重要事項**: AOTファイルには形式バージョンがあり、実機の
ランタイム(コンポーネント2.4.0~1 = WAMR 2.4.0)と一致するwamrcで変換しないと
ロードを拒否される。**必ずWAMR-2.4.0タグからビルドすること**(手順に組込済)。

所要時間の目安: WSL2導入10分 + 依存導入5分 + LLVMビルド30〜60分(CPU数依存、
放置可) + wamrc数分 + 変換数秒 + 実機側5分。

## 1. WSL2の導入(初回のみ)

管理者権限のPowerShell(スタートボタン右クリック →「ターミナル(管理者)」)で:

```powershell
wsl --install -d Ubuntu
```

再起動を求められたら再起動。初回起動時にUbuntuのユーザー名とパスワードを
決める(何でもよい。パスワードは後でsudoに使う)。

以後の「WSL内」の作業は、スタートメニューの「Ubuntu」を開いて行う。
ディスクはWSL側に15GB程度の空きがあること。

## 2. ビルド依存の導入(WSL内)

```bash
sudo apt update
sudo apt install -y build-essential cmake ninja-build git python3 python3-pip ccache
```

## 3. WAMR(2.4.0タグ)の取得とLLVMビルド(WSL内)

```bash
cd ~
git clone --branch WAMR-2.4.0 --depth 1 https://github.com/bytecodealliance/wasm-micro-runtime.git
cd wasm-micro-runtime/wamr-compiler
```

公式の`build_llvm_xtensa.sh`はpipの導入方法が新しいUbuntuと相性が悪いので、
中身を2段に分けて実行する:

```bash
python3 -m pip install --user --break-system-packages -r ../build-scripts/requirements.txt
python3 ../build-scripts/build_llvm.py --platform xtensa
```

これがEspressif版LLVM(branch xtensa_release_18.1.2)を取得してビルドする。
**ここが30〜60分**。ターミナルは閉じずに放置(PCのスリープは切っておく)。
途中で失敗した場合はエラーの最後の20行を報告。

## 4. wamrcのビルドと変換(WSL内)

```bash
cd ~/wasm-micro-runtime/wamr-compiler
mkdir -p build && cd build
cmake ..
make -j$(nproc)
./wamrc --version
```

`wamrc`のバージョンが表示されたらビルド成功。続いてM1のwasmを変換する。
WindowsのファイルはWSLから`/mnt/c/...`で見える:

```bash
./wamrc --target=xtensa --size-level=3 \
  -o /mnt/c/Users/koyab/Documents/dyne/m1-esp32/main/heat1d_actor.aot \
  /mnt/c/Users/koyab/Documents/dyne/m1-esp32/main/heat1d_actor.wasm
ls -la /mnt/c/Users/koyab/Documents/dyne/m1-esp32/main/heat1d_actor.aot
```

変換が成功したら**AOTファイルのサイズを控える**(限界レポート用。wasm 2,181バイト
との比較値になる)。

エラーが出る場合の代替フラグ: `--target=xtensa`で「target not found」系が
出たら`--target=xtensa --cpu=esp32`を試し、それでも駄目ならエラー全文を報告。

## 5. M1プロジェクトのAOT対応(Windows側)

2ファイルに小さな編集を行う。

**`m1-esp32\main\CMakeLists.txt`**: EMBED_FILESを差し替え:

```cmake
    EMBED_FILES "heat1d_actor.aot"
```

**`m1-esp32\main\main.c`**: 埋め込みシンボル名の2行(ファイル前半)を変更:

変更前:
```c
extern const uint8_t wasm_start[] asm("_binary_heat1d_actor_wasm_start");
extern const uint8_t wasm_end[]   asm("_binary_heat1d_actor_wasm_end");
```

変更後:
```c
extern const uint8_t wasm_start[] asm("_binary_heat1d_actor_aot_start");
extern const uint8_t wasm_end[]   asm("_binary_heat1d_actor_aot_end");
```

これだけでよい。WAMRはロード時にwasm/aotをファイル先頭のマジックで自動判別
するため、ロード以降のコードは無変更で動く。menuconfigの変更も不要
(AOTサポートは既定で有効、Classic通訳と共存できる)。

## 6. ビルド・書き込み・計測(Windows側、ESP-IDF PowerShell)

```powershell
cd C:\Users\koyab\Documents\dyne\m1-esp32
idf.py -p COM3 build flash monitor
```

(いつもどおり、Connecting...で止まったらFLASH+RESETの手動操作。)

## 7. 見るべき結果

成功パターン: M1 REPORTが出て、
- `per-step time`が数ms以下に落ちている(通訳79.5msの10〜50倍速=1.6〜8msが期待帯)
- L2/Linf/u値がこれまでと同一(AOTでも数値が変わらないことの確認。
  もし変わればそれ自体が重大な発見)

失敗パターンとその価値:
- `load failed`: AOT形式バージョン不整合(wamrcの版違い)またはXtensa AOTの
  ローダ問題。エラーメッセージを記録。
- `instantiate failed`または実行時クラッシュ(Guru Meditation): AOTコードの
  実行可能メモリ(IRAM、空き78KB)への配置問題の可能性。パニックメッセージの
  先頭行とバックトレースを記録。
- いずれの失敗も「ESP32(PSRAMなし)におけるAOTの壁」として限界レポート第2号に
  追記する。成功でも失敗でもM1bは完了する。

## 補記: この作業がDyne本体に持つ意味

「Xtensa向けAOTコンパイラは配布されておらず、LLVMごと自前ビルドが必要」という
事実は、Dyneのコンパイラレイヤー(仕様書A-3)が将来、wamrc相当のAOT変換器を
自前でビルド・配布する必要があることを意味する。今回WSL2内に作る環境は
その最初の雛形であり、M4(コンパイラ系統1)で再利用する。
