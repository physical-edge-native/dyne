# 2026-08-14-M-S0シミュレータ解説(docs\2026-08-14-ms0-explainer.md)

本書は、本プロジェクトで作成したシミュレータ「M-S0」の設計と動作を、
前提知識のない読者にも分かるように解説する。

用語の前提を最初にまとめる。

- **M-S0**: 本プロジェクトの作業段階(マイルストーン)の名前。Mはマイルストーン、
  Sはシミュレータを意味し、シミュレータ系列の0番目=基盤づくりを指す。
- **ノード**: 計算に参加する1台ぶんの参加者。実世界ではマイコン1台に相当する。
- **マイコン**(マイクロコントローラ): 手のひらサイズの小型コンピュータ。
  本プロジェクトではESP32という機種を使っている。
- **WebAssembly**(略してWASM): プログラムの共通配布形式。一度この形式に
  変換したプログラムは、パソコンでもマイコンでも同じものがそのまま動く。
- **アクター**: WebAssembly形式にした計算プログラムのこと。本書の例では
  「1次元の熱伝導方程式(棒の中を熱が伝わる現象の数式)を、担当区間だけ解く
  プログラム」がアクターである。

## 1. 何をシミュレートするのか

対象は「**N台のノードが、細長い領域を分担して物理計算を協調して解く**」様子である。

領域(たとえば長さ1の棒)をN個の区間に切り、各ノードが自分の区間の温度分布を
計算する。ただし区間の境目の温度は隣のノードの計算結果に依存するため、
**各計算ステップのたびに、隣どうしが境目の値をメッセージで交換する**必要がある。
この「計算と通信の繰り返し」がシミュレーションの本体である。

シミュレータが模擬するのは**通信網と時間**だけで、計算そのものは模擬しない
(2.5節)。通信網には、遅延・メッセージの喪失・ネットワークの分断・ノードの
一時停止といった「意地悪」を意図的に注入でき、それでも計算全体が正しく
完了するか(自力で立ち直るか)を調べられる。

## 2. 設計

### 2.1 「単一プロセス」とは

プロセスとは、OS上で動くプログラムの実行単位のことである。素朴に考えると、
16台のクラスタを模擬するには16個のプログラム(プロセス)を起動し、本物の
ネットワーク通信で繋げばよい。実際、本プロジェクトの初期実験(M0と呼ぶ段階)は
2プロセス+本物の通信で行った。

しかしこの方式には研究道具として致命的な欠点がある。**実行するたびに結果の
細部が変わる**のだ。OSが各プログラムをいつ動かすか、メッセージがいつ届くかは
毎回微妙に異なるため、「さっき観察した興味深い現象をもう一度再現したい」が
できない。

M-S0では方式を変え、**プログラムを1つ(単一プロセス)にして、その内部に
N台ぶんのアクターを並べる**。ノード間の通信は本物のネットワークを使わず、
プログラム内部のデータ受け渡しで表現する。これにより実行順序を完全に
掌握でき、次節の仕組みと合わせて「何度実行しても寸分違わず同じ結果」を
実現している。

### 2.2 「離散イベント」とは

シミュレーション時間の進め方には大きく2流派ある。時計を一定刻みで進めながら
毎回全員の状態を更新する方式(時間駆動)と、「次に何かが起きる瞬間」まで
一気に時間を飛ばす方式(**イベント駆動=離散イベント方式**)である。
M-S0は後者を採る。

仕組みは「**予定表**」に例えられる。シミュレータは起きるべき出来事(イベント)を
予定表に書き込み、時刻順に1件ずつ処理する。イベントは3種類しかない。

1. **配達**: 「ノード3が送ったメッセージが、時刻Tにノード4へ届く」
2. **目覚まし**: 「ノード5は時刻Tになったら、返事が来ていないか確認する
   (来ていなければ再送する)」
3. **計算完了**: 「ノード7の今ステップの計算が時刻Tに終わる」

たとえば「遅延5ミリ秒のネットワーク」は、送信時に「5ミリ秒後の配達」を
予定表に書くことで表現する。「メッセージ喪失」は、配達を予定表に
書き込まない(=永遠に届かない)ことで表現する。何かが起きる合間の時間は
処理する必要がないので飛ばす——これが「離散」の意味である。

### 2.3 「仮想時刻」とは

予定表の時刻は、**現実の時計とは無関係のただの数字**である。シミュレータは
「いま仮想時刻50000マイクロ秒」といった数値を持ち、イベントを処理するたびに
その数値を進める。

これの利点は劇的である。実機のマイコンでは1計算ステップに79.5ミリ秒かかる
ことが実測で分かっている(本プロジェクトの実機実験M1の測定値)。この遅さを
シミュレータで再現するとき、本当に79.5ミリ秒待つ必要はなく、**予定表上で
「計算完了は79.5ミリ秒後」と書くだけ**でよい。結果として、仮想的には5分以上
かかるクラスタの動作が、現実には数秒で終わる。逆説的だが、「実機の遅さを
正確に模擬しながら、実行は実機よりはるかに速い」が両立する。

### 2.4 決定論性(乱数シード)

メッセージ喪失(確率10%など)や遅延のゆらぎは乱数で決める。M-S0の乱数は
**シード(種)と呼ばれる初期値から数列を機械的に生成する方式**(xorshiftという
古典的な計算法)で、シードが同じなら乱数列も完全に同じになる。

単一プロセス(2.1)+予定表方式(2.2)+シード固定乱数の3点セットにより、
**同じ指定で実行すれば、メッセージがいつ失われるかまで含めて、出力の全行が
バイト単位で一致する**。これは検証で実際に確認しており、Linuxと
Windowsという異なるOS間でも全出力が一致した(6章の検証7・7b)。

### 2.5 「計算は本物」とは

シミュレータと聞くと「計算も含めて全部が模擬(偽物)」と思われがちだが、
M-S0は違う。**物理計算の部分は、実機のマイコンで動かしているのと
バイト単位で同一のWebAssemblyファイルを、そのまま実行している。**
模擬しているのは通信網と時間だけである。

これが成立する根拠がWebAssemblyの性質である。同じWebAssemblyファイルは
実行環境が違っても同じ計算結果を出す。本プロジェクトでは実機実験(M1)で
「パソコンでの実行結果と、マイコンでの実行結果が、小数の全桁まで一致する」
ことを確認済みであり、この事実によって「シミュレータの計算結果=実機の
計算結果」が保証される。CPUの命令を1つずつ真似る重いエミュレーションを
しなくても、計算の正しさに関しては実機と等価なのである。

言い換えると、M-S0が答えられる問いは「この協調の**手順**は正しいか、
どんな悪条件まで耐えるか」であり、答えられない問いは「実機の**時間・無線・
電力**の真の値はいくつか」である。後者は実機での測定が唯一の情報源であり、
測定値をシミュレータに注入して使う(次節)。

### 2.6 実機の測定値の注入

シミュレータを実機に近づけるため、実機実験の測定値を2つ注入している。

- **計算時間**: 1ステップ=79.5ミリ秒(実測値)を仮想時刻で消費する。
  値はオプションで変更できる。
- **メモリ上限**: 実機の使用可能メモリはおよそ250キロバイトしかない。
  起動時に「1ノードが必要とするメモリ量」を見積もり、上限を超える構成は
  **実行前に拒否**する(実機なら起動に失敗する構成を、シミュレータでも
  同じように弾く)。実際に、古い設定の計算プログラム(必要量1,162KB)を
  与えたところ正しく拒否された実績がある。

### 2.7 境目の番号付け(過去の不具合からの改良)

隣接ノードが境目の値を交換するとき、メッセージに「どの境目の話か」を
書く必要がある。初期実験(M0)では各ノードが自分から見た向き(自分の右端/
左端)で書いていたが、Aの「右端」とBの「左端」は同じ場所を指すため、
受信側で読み替えが必要になり、読み替え忘れによる発見困難な計算誤りが
実際に発生した。

M-S0ではこの方式を廃止し、**境目そのものにクラスタ全体で通用する通し番号を
振る**(ノード0と1の間=0番、ノード1と2の間=1番、…)。全員が同じ場所を
同じ番号で呼ぶので、読み替えという操作自体が存在せず、この種の誤りは
原理的に起きない。住所に例えるなら、「うちの右隣」「おたくの左隣」と
言い合うのをやめて境界線に番地を振った、ということである。

### 2.8 扱う故障の範囲

注入できる故障は3種類: **一時停止**(ノードを指定時間フリーズさせ、後で
復帰させる)、**メッセージ喪失**(指定確率で握りつぶす)、**一時分断**
(指定時間、クラスタを2グループに割り、間の通信を全て落とす)。
再送の仕組み(6章の検証3で詳述)により、3種類とも自力で立ち直れる。

一方、**ノードが完全に死んで戻ってこない**故障は対象外とした。死んだノードの
担当区間の計算結果は失われるため、立ち直るには「他の誰かが担当を引き取り、
状態を作り直す」再編成が必要で、それは通信の再送では解決できない。将来の
段階で作る上位の管理機構の仕事であり、現在の通信手順の守備範囲を正直に
線引きした結果である。

## 3. 実装の場所と各ファイルの役割

実装はリポジトリ内の以下に置かれている。

| 場所 | 役割 |
|---|---|
| `crates/dyne-sim/Cargo.toml` | 部品表。プログラム名と、依存する外部部品(wasmi = WebAssemblyをパソコン上で実行するためのライブラリ、ほか)を宣言する |
| `crates/dyne-sim/src/main.rs` | **シミュレータの全実装**(1ファイル完結、約600行) |
| `crates/heat1d-actor/` | 計算プログラム(アクター)の源泉。ここからWebAssemblyファイルが作られる。**シミュレータはこれを一切改変せずに使う** |
| `crates/heat1d-actor/target/wasm32-unknown-unknown/release/heat1d_actor.wasm` | 上をビルドしてできる実行対象。実機に書き込むものと同一 |
| `crates/dyne-host/` | (参考)初期実験M0で作った2ノード版。こちらは本物の通信(UDP=コンピュータ間の基本的な通信方式の一つ)を使う。M-S0はこれのNノード・仮想通信版にあたる |

`main.rs`の内部は次の部品で構成される。

- **設定解析**: コマンドラインの指定(4章)を読み取る。
- **乱数**: シード固定の乱数生成(2.4)。
- **アクター読み込み**: WebAssemblyファイルをノード数ぶん読み込み、
  それぞれに担当区間を割り当てて初期化する。
- **メッセージとイベント**: 境目の値を運ぶメッセージの定義と、
  予定表(2.2)に載る3種類のイベントの定義。
- **ノードの状態機械**: 各ノードは常に「境目の値待ち」「計算中」「完了」の
  いずれかの状態にあり、イベントを受けて状態を移る。再送や、遅れてきた
  相手への応答(6章)もここで行う。
- **イベントループ**: 予定表から時刻順にイベントを取り出して処理する心臓部。
- **分割と検証**: 領域のN分割の割り付け、メモリ上限チェック(2.6)、
  実行後の答え合わせ(6章)。

## 4. 実行コマンドとオプション一覧

実行例:

```
dyne-sim --wasm heat1d_actor.wasm --nodes 16 --points 65 --steps 2000 \
  --loss 0.10 --lat-ms 5 --lat-jitter-ms 3 --step-ms 79.5 --seed 42 \
  --pause 7@20000:40000 --partition 8@60000:90000
```

| オプション | 意味 | 既定値 |
|---|---|---|
| `--wasm パス` | 実行するWebAssemblyファイル(必須) | — |
| `--nodes N` | ノード数 | 16 |
| `--points P` | 領域全体の格子点数(計算の細かさ)。各ノードに最低3点必要 | 65 |
| `--steps S` | 計算ステップ数 | 2000 |
| `--alpha A` | 熱の伝わりやすさ(物理定数) | 1.0 |
| `--dt T` | 1ステップぶんの物理時間の刻み幅。安定条件(5.4)に注意 | 1e-4 |
| `--loss X` | メッセージ喪失率(0〜1。0.10なら10%) | 0 |
| `--lat-ms L` | 通信遅延の平均(ミリ秒) | 0 |
| `--lat-jitter-ms J` | 遅延のゆらぎ幅(0〜2Jの一様乱数を加算) | 0 |
| `--step-ms C` | 1ステップの計算時間(実機校正値。仮想時刻で消費) | 79.5 |
| `--timeout-ms T` | 返事を待つ時間。超えたら再送を検討する | 100 |
| `--seed N` | 乱数シード。同じ値なら実行結果が完全に再現される | 42 |
| `--ram-cap-kb K` | 1ノードのメモリ上限(キロバイト)。超える構成は起動拒否 | 250 |
| `--pause n@a:b` | ノードnを仮想時刻aミリ秒からbミリ秒まで一時停止 | なし |
| `--partition k@a:b` | 仮想時刻a〜bミリ秒の間、ノードk-1とkの間で分断 | なし |

終了コード: 0=検証合格、1=検証不合格、2=メモリ上限による起動拒否。

## 5. 知見の解説

### 5.1 前提: BSPとは

BSP(Bulk Synchronous Parallel、一括同期並列)は並列計算の古典的な進め方で、
「全員で足並みをそろえて1歩ずつ進む」方式である。本シミュレータでは
各ステップが次の3拍子で進む。

1. 各ノードが自分の境目の値を隣へ送る
2. 隣からの値が**全部そろうまで待つ**
3. そろったら1ステップ計算し、次のステップへ

肝は2の「待つ」で、これにより全ノードが常に同じステップ番号の値を使って
計算することが保証される。時計合わせは不要で、ステップ番号(論理的な歩数)
だけで同期する。以下の知見はすべてこの性質から派生する。

### 5.2 同期オーバーヘッドとは

**定義**: クラスタ全体の完了時間が、「待ちが一切なかった場合の理想時間
(=ステップ数×1ステップの計算時間)」をどれだけ超過したかの割合。

超過の原因はBSPの「待つ」である。メッセージが遅れたり失われたりすると、
計算自体は終わっているのに隣の値待ちで手が止まる。この待ち時間の積み重ねが
オーバーヘッドになる。

実測では、理想的な通信網なら超過ほぼ0%、喪失率10%+遅延5±3ミリ秒の
悪条件では**+118%**(完了時間が2.2倍に伸びる)だった。悪条件時の主因は
「失われたことに気づくまでの待ち」で、返事待ちの上限(100ミリ秒)と
再送間隔の設定値がそのまま効く。この数値を安く測れるようになったことが
シミュレータの成果であり、通信パラメータの最適化(実機の無線測定値を
注入した上での調整)に使っていく。

### 5.3 大域結合とは

**定義**: 1台の遅れが、直接の隣だけでなくクラスタ全体の進行に波及する性質。

BSPでは、ノードAが止まると隣のBはAの値を待って止まり、するとその隣のCも
Bの値を待って止まり……と、停止が鎖のように伝播する。実測では、16台中の
1台を仮想20秒停止させたところ、**全体の完了が約24秒遅れた**(停止時間+
伝播の余波)。

これは欠陥ではなくBSPの本質的な代償で、「全員の足並みの保証」と引き換えに
「最も遅い1台に全体が律速される」。将来の改良候補として、隣の値が少々
遅れても予測値で先へ進む方式(有界非同期)が仕様に挙がっており、その
価値(どれだけ速くなるか、精度をどれだけ損なうか)を定量評価する土台が
このシミュレータである。

### 5.4 安定条件とは

**定義**: 数値計算の答えが発散(無限大や非数に爆発)しないための、刻み幅に
関する数学的な制約。

本例の熱伝導計算は「時間刻み dt を、空間の細かさ h の2乗に比べて十分小さく
取る」必要がある(具体的には α·dt/h² ≤ 1/2。αは熱の伝わりやすさ)。これを
破ると、通信や手順がすべて正しくても、計算値がステップごとに増幅されて
数ステップで無限大に発散する。

開発中、格子点数を65から257に増やした際(hが1/4になり、h²は1/16になる)、
dtを据え置いたままこの条件を4倍以上超過し、**答えが全点で非数(NaN)になる
事故を実際に起こした**。シミュレータには起動時の安定条件チェックを追加して
解決したが、教訓はより大きい: 将来、計算プログラムを実機群に配布する際は、
配布物の検査段階でこの種の条件を自動検証すべきである。実機に配ってから
発散に気づくのでは遅い。

## 6. 検証マトリクス詳解

以下、実施した検証それぞれについて「条件の意味」「内部で何が起きるか」
「結果」を解説する。全検証で共通の答え合わせ方法は次の2つ。

- **ビット一致検証**: 同じ問題を「分割せず1ノードで」解いた参照解と、
  N分割の協調解を全格子点で比較し、**小数の全ビットまで一致**することを
  要求する。1ビットでもずれたら不合格。通信や手順の誤りは必ず数値のずれと
  して現れるため、これが最も厳しい合否判定になる。
- **理論解との誤差**: 熱伝導方程式には紙と鉛筆で導ける厳密解があり、
  数値解との誤差が理論どおりの大きさ(格子を細かくすると2乗で縮む誤差)に
  収まることを確認する。

### 検証1: N=2、理想的な通信網

過去の初期実験(2プロセス+本物の通信で実施)と同じ構成の再現である。
方式を単一プロセス+仮想時刻に全面的に変えても同じ答えが出ることを確認する
「回帰試験」にあたる。内部では境目が1箇所だけあり、毎ステップ2通の
メッセージが遅延ゼロで即配達される。結果: 65点全点ビット一致。

### 検証2: N=16、理想的な通信網(合格基準その1)

ノードを16台に増やし、境目は15箇所、毎ステップ30通のメッセージが飛ぶ。
各ノードの担当は4〜5点まで細るが、BSPの3拍子(5.1)が守られる限り、
分割数によらず「1ノードで解いた場合と同一の計算」になるはずである。
結果: 65点全点ビット一致。分割の一般化(2→N)が正しいことの確認。

### 検証3: N=16+メッセージ喪失10%+遅延5±3ミリ秒(合格基準その2)

通信の信頼性を意図的に落とす。内部の動きは次のとおり。

- 送信のたびに乱数を引き、10%の確率で配達イベントを予定表に書かない
  (=喪失)。届く場合は5±3ミリ秒後の配達として書く。
- 受け手は値がそろわないので待つ。100ミリ秒待っても来なければ、
  **送信済みメッセージの控えを再送**する(再送どうしの間隔には下限を設け、
  無駄な連射を防ぐ)。
- 相手のほうが先に進んでいる場合もある。そのとき相手には「過去のステップの
  メッセージ」が届くことになるが、これは「あなたのそのステップの値を私は
  まだ受け取れていない」という遭難信号として解釈し、**控えから該当ステップの
  値を送り返す**(応答再送)。この仕組みが、喪失・追い越し・出遅れのすべてを
  同じ原理で治す。

重要なのは、**どれだけ通信が荒れても計算結果は変わらない**ことである。
BSPでは「ステップnの計算にはステップnの隣の値を使う」と論理的に決まって
おり、通信の乱れは「値がいつ届くか」だけを変え、「どの値を使うか」を
変えない。したがって乱れの影響は完了時間(同期オーバーヘッド+118%)に
現れ、数値には現れない。結果: 喪失9,572通・再送29,728通・応答再送5,106通
という荒れ模様の末に、65点全点ビット一致。

### 検証4: N=16+ノード7を仮想20秒間停止

ノードの一時的なフリーズ(実世界なら瞬断や過負荷)を模す。内部では、
停止中のノード宛のイベントをすべて停止解除時刻まで繰り延べる。停止中、
隣のノードは値が来ないので待ち、定期的に再送する(それも本人が起きるまで
処理されない)。解除されたノードは溜まったメッセージを一気に処理して
追いつく。5.3で述べたとおり停止は全体に波及し、完了が約24秒遅れたが、
結果は65点全点ビット一致。「遅れても間違えない」の実証である。

### 検証5: 複合カオス(喪失10%+遅延+停止+30秒分断)

検証3・4に加え、仮想60〜90秒の間クラスタを2つに割り、またぐ通信を全て
落とす(分断)。実世界なら中継機の一時故障に相当する。分断中、境界を
またぐ再送はすべて失われ続けるが、分断解除後の再送・応答再送で回復する。
すべての故障が同時に起きても、結果は65点全点ビット一致。

### 検証6: メモリ上限による起動拒否

上限を意図的に100KBに絞って起動し、必要量138KB(実機実測に基づく見積り)の
構成が**計算開始前に拒否される**(終了コード2)ことを確認した。実機なら
起動に失敗して原因調査に時間を食う構成を、シミュレータが事前に弾けることの
確認である。

### 検証7・7b: 決定論性

同じシード・同じ指定で2回実行し、出力の全行が一致することを確認(検証7)。
さらに同じ指定をLinuxとWindowsで実行し、喪失数・再送数・完了時刻まで
**OSが違っても全出力が一致**することを確認した(検証7b)。「あの現象が出た
実行」をシード1つで誰の環境でも呼び出せることを意味し、再現性が求められる
研究道具としての要件を満たす。

### 検証8: 大きな問題(257点)と実行速度

格子を4倍に細かくした問題で規模耐性と実行速度を測った。なおこの検証の
初回、時間刻みを据え置いたため安定条件(5.4)を破って発散する事故を起こし、
起動時チェックの追加につながった。正しい刻み幅での再実行では、16台・
2000ステップ・喪失5%の条件で257点全点ビット一致、**仮想266秒ぶんの
クラスタ動作を現実の約4.5秒で完走**した。仮想時刻方式(2.3)の効率の
実証であり、この速さが今後のパラメータ探索実験の回転数を支える。

## 7. まとめ

M-S0は「通信と時間は模擬、計算は本物」という割り切りにより、(1) 実機と
同一の計算プログラムを、(2) 意地悪な通信条件下で、(3) 完全な再現性つきで、
(4) 実機より桁違いに速く動かす道具である。厳しい合否判定(全ビット一致)を
全条件で通過しており、以後の研究(通信方式の改良、ネットワーク構成の実験、
学習の分散実行)はこの土台の上で行う。実機の役割は消えるのではなく、
「時間・無線・電力の真の値を測ってシミュレータに教える」校正役として
続いていく。
