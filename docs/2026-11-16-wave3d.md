# 3次元の波動方程式を多数の区画に分けて解く — ビット一致と並列化の効率の予備測定(2026-11-16)

> barye リポジトリ(physical-edge-native/barye@760cd20)から移した(2026-11-16、Issue #41)。コマンド名・パスは Dyne での名前に置き換え、Issue 番号は barye のもの(physical-edge-native/barye#N)と明記した。本文の「Barye」は移す前のプロジェクト名。
> 用語: この文書の「区画」は各ノードの担当区間(合意済みの用語の「区画」と同じ)、「境目」は界面(ノードとノードの区画の境目)を指す。

作成: Claude Code(下書き。メンテナーの編集前)。関連: Issue physical-edge-native/barye#8(3D wave equation split into patches,
bit-exact against the single-patch solve)。内部向けの作業記録。第三者向けの説明は README.md(英語)と
`crates/dyne-native/src/wave3d.rs` のドキュメントコメント(英語)にある。

## 0. 要約

- 3次元の波動方程式 `u_tt = c²(u_xx + u_yy + u_zz)` の区画(パッチ)の計算部品を、Rust のネイティブ実装で
  作った(`wave3d.rs`)。時間は3段の中心差分(リープフロッグ法、蛙跳び法)、空間は7点のラプラシアン
  (各点と、x・y・z の両隣の計6点)。安定条件はクーラン数 ν = cΔt/h ≤ 1/√3(約 0.577)。
- 区画の分け方・面の番号・1区画1スレッドの実行器は、2次元のときに次元によらない形で書いたものを
  そのまま使った(`decomp.rs`、`patch.rs` は変更なし)。区画どうしは毎ステップ、**面(6面)の値だけ**を
  2次元の板(スラブ)として、Dyne のメッセージ形式(ワイヤ形式 v2 の IFACE_BAND、f64 の列)で交換する。
  7点のラプラシアンは辺・角の隣を使わないので、辺・角の交換はない。
- **ビット一致**: 25×23×21 の格子、80ステップで、単一区画の解と 1×1×1・2×2×2・3×2×1・4×4×2・1×3×5・
  5×1×2・1×1×7 の分割解が、値固定・ゼロ勾配・吸収境界・混在(6面に3種を混ぜる)・安定条件を超えて発散する
  場合(ν = 0.6)の 5種すべてでビット一致した(35通り)。
- **2次元との一致**: z 方向に変化しない3次元の問題(初期値 cos(πx)·cos(2πy)·cos(0·πz)、z の2面はゼロ勾配)は、
  どの z の断面も2次元の計算部品の解とビット一致した(値固定・ゼロ勾配・混在の3種、2×2×2 分割)。
  2次元の計算部品は Dyne の WebAssembly の計算部品とビット一致が確かめてあるので、3次元の x・y の項の
  演算順が2次元と同じであることの確認になる。
- **OS をまたいだ一致のための固定値**: 25×23×21・ガウス型の山・値固定0・ν = 0.5・100ステップの単一区画の
  場の CRC32(誤り検出用のハッシュ値)を **2ca26bb5** に固定し、テストと `scripts/ci-check.sh` の [4] で確かめる。
  手元(Windows)ではデバッグ版・リリース版とも同じ値。Linux・macOS は CI で確かめる。
- **並列化の効率(予備値)**: 192³ の強スケーリングで 12 コアまでに約 3.4 倍(効率 29%)、22 コアで逆に遅くなる。
  1区画 64³ の弱スケーリングの効率は 16 コアで 18%。2次元と同じく、メモリの帯域と待ち合わせで頭打ちになる。
  **測定の途中で電池駆動に変わっていた**(§4.1)ので、数値は予備値として扱う。

## 1. 選んだ方式と小さな実装判断

Issue physical-edge-native/barye#8 の指示(リープフロッグ法、7点のラプラシアン、2次元と同じ境界、面の IFACE_BAND による交換、
次元によらない分割と実行器の再利用)の範囲で実装した。以下はエージェントが決めた小さな実装判断:

1. **確認の道具は新しいプログラム `dyne-native-wave3d`** にした(`dyne-native-wave2d` に3次元の動作を足す案ではなく)。
   理由: `dyne-native-wave2d` は Dyne の2次元の wasm(WebAssembly)の計算部品を動かす経路(`--wasm`)を持ち、
   格子の指定も `NXxNY` の形なので、3次元を混ぜると引数の意味が分かれる。引数の読み取りの小さな関数
   (約 20 行)は2つのプログラムで重複している。
2. **演算の順序**は2次元の自然な延長にした:
   `lap = ((W − 2u + E) + (S − 2u + N)) + (D − 2u + U)`(x、y、z の順に左から足す)。更新式・最初のステップ・
   係数(ν²、ν²/2、吸収境界の係数 (ν−1)/(ν+1) を初期化で1回だけ計算)は2次元と同じ。
   この順序を `wave3d.rs` の冒頭のドキュメントコメントに「ビット一致の比較のための約束」として書いた
   (将来 Dyne 側に3次元の wasm の計算部品を作るとき、同じ順にすれば比べられる)。
3. **外周の境界の適用順**も2次元の延長: 外周の面の枠(ゴースト点)を面0〜5の順に埋める → 全点を更新 →
   吸収境界を面0〜5の順に適用 → 新しい値を現在の値にする → 値固定の面を面0〜5の順に再設定。
   辺・角では後の面が勝つ。
4. **面の板の並べ方**: 面の上の2軸のうち、番号の小さい軸を速く回す(x の面: y が速く z が遅い。y の面: x、z。
   z の面: x、y)。区画の点の並び(x が最も速い)と同じ向き。
5. 境界の種類の型 `Outer` は2次元のものをそのまま使う(`wave3d::Outer` として再公開)。初期値は3次元用の
   `wave3d::Initial`(正弦の定在波・ガウス型の山・余弦の定在波。2次元と同じ3種)。
6. Dyne に3次元の wasm の計算部品が無いので、2次元の `actor_cfg` / `actor_faces` に当たるもの(wasm の設定の
   呼び出しを作る関数)は作っていない。

## 4. 並列化の効率(予備測定)

### 4.1 測定の条件

- CPU: Intel Core Ultra 7 155H(22 論理 CPU、速さの違うコアの混在。2次元の記録 docs/2026-11-16-wave2d-milestone.md §4.1)。
  Windows 11、電源プラン「バランス」。
- **電源の状態**: 作業の開始時は AC 電源(`Get-CimInstance Win32_Battery` の BatteryStatus = 2)だったが、
  測定の直前と直後の確認では **BatteryStatus = 1(電池で放電中、残り 62%)** だった。つまり**この測定は電池駆動**。
  また、同じ PC でほかのエージェントがビルドを行っている可能性がある(測定の直前の CPU の負荷は 2% だった)。
  **以下の数値は予備値**として扱い、AC 電源・ほかの負荷のない状態での再測定が必要。
- 問題: 定在波 sin(πx)·sin(πy)·sin(πz)、値固定0、ν = 0.5(非正規化数が出ないように)。
- 時間: 全区画の準備が終わってから最後のステップが終わるまでの実時間 ÷ ステップ数。各条件3回の中央値。
  「計算」は各区画が1ステップの計算そのものに使った時間(平均 / 最も遅い区画)。
- `p` コアの分け方: `pz` は p の約数で pz³ ≤ p の最大のもの、残りを2次元と同じ規則で px × py(px ≥ py ≥ pz)。
  22 = 2·11 は 11×1×2 になり、区画が細長くなる(面の値が多い)。

### 4.2 強スケーリング: 192×192×192(約 708 万点、2段で状態 113 MB)、20ステップ

再現: `cargo run --release --bin dyne-native-wave3d -- scaling --mode strong --grid 192x192x192 --cores 1,2,4,8,12,16,22 --steps 20 --repeat 3`

| コア | 分割 | ms/ステップ | 計算 ms(平均 / 最遅) | 速度向上 | 効率 |
|---:|---:|---:|---:|---:|---:|
| 1 | 1×1×1 | 12.062 | 11.257 / 11.257 | 1.00 | 100% |
| 2 | 2×1×1 | 7.627 | 6.361 / 6.466 | 1.58 | 79% |
| 4 | 2×2×1 | 4.690 | 3.699 / 3.779 | 2.57 | 64% |
| 8 | 2×2×2 | 3.729 | 2.315 / 2.492 | 3.23 | 40% |
| 12 | 3×2×2 | 3.526 | 1.819 / 1.974 | 3.42 | 29% |
| 16 | 4×2×2 | 3.620 | 1.824 / 2.048 | 3.33 | 21% |
| 22 | 11×1×2 | 5.161 | 1.724 / 2.182 | 2.34 | 11% |

メッセージなしの1区画のループ: 11.987 ms/ステップ(1点1ステップ約 1.7 ns)。12 コアで全体の処理量は約 20 億点/秒。
1点あたりの読み書きを約 24 バイトとすると約 48 GB/s で、2次元の記録(4〜6 コアで約 55〜60 GB/s で頭打ち)と同程度。
8 コアを超えると計算時間がほとんど縮まず(**メモリの帯域の頭打ち**)、実時間と計算時間の差(面の値の組み立て・写しと
待ち合わせ)が実時間の約半分を占める。2次元と違い、面の値が多い(192×192 の面で1通 約 295 KB)ので、
メッセージの組み立てと写しの費用も無視できない可能性がある(内訳は未測定)。

再現: `cargo run --release --bin dyne-native-wave3d -- scaling --mode weak --patch 64x64x64 --cores 1,2,4,8,12,16 --steps 50 --repeat 3`

| コア | 分割 | 格子 | ms/ステップ | 計算 ms(平均 / 最遅) | 効率 |
|---:|---:|---:|---:|---:|---:|
| 1 | 1×1×1 | 64×64×64 | 0.321 | 0.321 / 0.321 | 100% |
| 2 | 2×1×1 | 128×64×64 | 0.387 | 0.303 / 0.308 | 83% |
| 4 | 2×2×1 | 128×128×64 | 0.618 | 0.352 / 0.397 | 52% |
| 8 | 2×2×2 | 128×128×128 | 1.255 | 0.550 / 0.576 | 26% |

| 16 | 4×2×2 | 256×128×128 | 1.784 | 0.969 / 1.039 | 18% |

メッセージなしの1区画のループ(64³): 0.348 ms/ステップ。1区画の計算時間が 8 コアから伸び始める(0.30 → 0.97 ms)のは、
2次元と同じく、全体の帯域の上限と、速さの違うコアの混在のためと考えられる。

### 4.4 読み取り(予備)

1. 3次元でも、この方式(1点の計算が軽い陽解法、毎ステップの交換)の効率は、この PC では2次元と同じく
   メモリの帯域と待ち合わせで決まる。12 コアの約 3.4 倍が上限で、22 コアでは遅くなった。
2. 3次元では面の値が多く、メッセージの費用が2次元より大きい可能性がある。内訳(組み立て・写し・待ち)を分けて
   測ることは今回していない。
3. 電池駆動・ほかの負荷の可能性があるので、結論は再測定のあとに出す。

## 5. 失敗・限界として残すこと

- 22 コアの分割 11×1×2 は形が悪く、強スケーリングでは 16 コアより遅い。コアの数の選び方(素因数の大きい数を避ける)
  か、分割の規則の改良が必要。
- 測定は電池駆動で行った(開始時は AC 電源だったが、測定時には電池に変わっていた)。

## 6. 未解決・メンテナーに決めてほしいこと

1. 3次元の wasm の差込口(`dyne_init3d` に当たるもの)を Dyne 側で決めるか。決めれば、この文書の演算順の約束どおりに
   作って、2次元と同じくバイト単位で比べられる(Issue physical-edge-native/barye#3 の範囲)。
2. 面の値のメッセージの費用を減らすか(例: 面の値を f64 の列に詰め直さず、受け手の枠へ直接写す共有メモリの経路)。
   ただし、メッセージの形式(Dyne との共有)を通らない経路になるので、方針の判断が要る。
3. AC 電源での再測定(`dyne-native-wave3d scaling` を §4.2・§4.3 の再現の行で実行するだけでよい)。
