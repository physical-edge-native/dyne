docs/2026-11-07-plan.md §1-10〜1-12(Physical-Edge Native Architecture の特徴と仮定 A1〜A7)、

ユーザーの目標(要約): 「Physical-Edge Native Architecture を使えば、GPU なしでも Isaac Lab にここまで近づける」ことを示す。
題材は、Dyne のツールチェーンが測距から作った部屋(USD)の中で、移動台車(車輪で走るロボット)が目標地点へ進む強化学習。
発表は 2026-11-22。その時点で途上でもよい。

本書の用語(初出の説明):
- **強化学習(RL)**: 試行と報酬から方策(観測→行動の対応。ここでは小さな NN)を学ぶ方法。
- **環境ステップ(env-step)**: 方策が1回行動を選び、環境が1回進むこと。物理の1刻み(物理ステップ)とは別。
  方策を 10 Hz で動かし物理を 2 ms 刻みで進めるなら、1 環境ステップ = 50 物理ステップ。
- **並列環境**: 同じ課題の世界を多数同時に動かし、学習のデータを速く集めること。Isaac Lab の速さの源。
- **剛体**: 変形しない物体。位置・向き・速度・角速度で状態が決まる。
- **ゴースト(写し)**: 隣の区画の物体のうち、自分の区画の物体と接触しうるものの状態の写し。
  計算はしない(持ち主が計算する)。数値計算の領域分割での「ゴーストセル」と同じ考え方の物体版。
- **のりしろ(halo)**: ゴーストを受け取る範囲の幅。界面からこの距離以内の物体を隣へ写す。
- **持ち主(owner)**: その物体の運動を計算するノード。本書の推奨では「物体の中心がある区画のノード」。
- **移管(migration)**: 物体の中心が区画を出たとき、持ち主を隣のノードへ移すこと。
- **一斉同期の段階進行(BSP、bulk synchronous parallel)**: 全ノードが「計算 → 界面の受け渡し → 次のステップ」を
  そろって繰り返す方式。dyne-sim / dyne-sim2d / 実機ファームのステップ同期がこれ。
- **SDF(符号つき距離の場)**: 各点から最も近い表面までの距離(物の中は負)。sdf2d-grid-actor が測距から作る φ。
- 合意済みの用語(界面・境界・格子型アクター・メールボックス方式)は docs/draft/2026-09-26-project.md のとおり。

## 1. Isaac Lab が実際に提供するもの、そのうち何を狙うか

### 1.1 Isaac Lab の構成(確かめた範囲)

Isaac Lab は NVIDIA の、GPU で並列に動かすロボット学習の枠組み。Isaac Gym の後継で、Isaac Sim(USD を土台にした
シミュレータ)の上に作られている(Mittal ほか 2025、arXiv:2511.04831)。

| 機能 | 内容 | 出所・確度 |
|---|---|---|
| 物理エンジン | **PhysX 5**。剛体、関節つきの機構(articulation。ロボットの腕や車輪)、変形体(布・柔らかい物)、流体のための位置ベースの計算、接触の報告、SDF による衝突判定 | 論文 §2.2 |
| GPU と CPU | PhysX は CPU でも GPU でも動く。状態と操作は GPU から直接読み書きでき、摩擦・質量などの値は CPU 側の API で設定する | 論文 §2.2。**Isaac Lab 全体を CPU だけで実用的に回せるかは要確認** |
| 並列環境 | 同じ場面を数千〜数万複製して同時に進める。8 GPU・16,384 環境で、Franka の引き出しの課題が毎秒 160 万フレーム超、DextrAH の課題が毎秒 90 万フレーム超 | 論文 §4.1.1 |
| 1 GPU あたりの目安 | Isaac Gym(前身)で、Ant(4本脚)を A100 1枚・4,096 環境で平均 **毎秒 54 万環境ステップ**、20 秒で報酬 3000 超 | Makoviychuk ほか 2021、arXiv:2108.10470。**車輪ロボットの行き先の課題での値は要確認(GPU を借りたとき実測)** |
| センサ | 接触センサ・IMU・座標の変換、カメラ(RGB・深度・領域分け)、光線を飛ばす距離センサ(RayCaster。LiDAR 風・高さの走査) | 論文 §3.3 |
| 場面の取り込み | **USD が中心のデータ層**。URDF・MJCF・メッシュからの変換器あり | 論文 §2.1 |
| 学習の枠組みとの接続 | 複数の RL ライブラリへの包み(rsl_rl・rl_games・skrl・Stable-Baselines3 と理解しているが、本書では**要確認**) | 論文 §1 は「多様な RL ライブラリ」とのみ |
| 車輪ロボットの例 | 公式の手引きに Jetbot(差動二輪の小型ロボット)の環境を作る手順がある(direct workflow) | Isaac Lab 公式の walkthrough |
| 計算機の要件 | Isaac Sim 5.0 の最低は **RTX 4080(VRAM 16GB)**、RT コアの無い GPU(A100・H100)は非対応、RAM 32GB 以上 | Isaac Sim 5.0 の要件のページ |
| 版の動き | Isaac Lab 3.0 は物理の既定を Newton(NVIDIA Warp の上の新しいエンジン)に移し、Isaac Sim 5.1 以前を非対応にした | Isaac Lab 3.0 の導入手順のページ。**借りる計算機の版を要確認**(docs/2026-11-11-usd-physics.md の台本は Isaac Lab 2.x 前提) |

## 2. 「Isaac Lab に近づく」をどう測るか

### 2.1 指標の候補

| 記号 | 指標 | 測り方 | 何と比べるか | 備考 |
|---|---|---|---|---|
| F1 | **分担の正しさ** | 区画で分担した結果と単一ノードの結果のビット一致 | 自分自身 | CLAUDE.md の合格基準。Isaac にはない性質を示せる |
| F2 | **物理の近さ(決まった場面)** | 同じ部屋・同じ初期条件・同じ指令の列で、軌跡の差(位置の最大誤差 [mm]、止まる位置、反発後の速さ) | MuJoCo(CPU、.venv に 4.0.0 あり)と PhysX(Isaac、借りた GPU) | **合格の物差し: Dyne と MuJoCo の差 ≤ PhysX と MuJoCo の差**(物理エンジンどうしでも差があるので、その幅の中に入れば「同等」と言える) |
| F3 | 物理の近さ(統計) | 多くの物体がぶつかり合う場面は小さな差が増幅される(初期値に敏感)ので、最終位置の分布・運動エネルギーの減り方で比べる | 同上 | 軌跡そのものの一致は求めない |
| R1 | **学習の結果** | 行き先の課題の成功率、学習曲線(環境ステップ数に対する成功率) | Isaac Lab(Jetbot)、MuJoCo | 同じ課題の定義・同じ報酬 |
| R2 | **方策の持ち運び** | Dyne の環境で学習した方策を Isaac Lab(または MuJoCo)で評価したときの成功率の落ち方。逆向きも | 同上 | 「環境として近い」ことの最も強い証拠。シミュレータ間の転移(sim-to-sim) |
| T1 | 速さ | 物理ステップ/秒、環境ステップ/秒(1環境あたり・全体)、目標の成功率までの実時間 | Isaac Lab の実測 | **桁で負ける見込み**(§5.5)。正直に示す |
| C1 | 費用 | 機材費、消費電力、100 万環境ステップあたりの電力量、GPU の時間あたりの料金 | GPU の計算機 | 電力あたりの環境ステップでも負ける見込み(§5.5) |
| L1 | 形の変化の反映 | 部屋の物が動いてから、環境の衝突判定が変わるまでの時間 | Isaac(USD を書き出し直して読み込み直す) | Physical-Edge Native が有利な軸。ノード群は φ を持ち続けているので数秒(実験6の結果しだい) |
| S1 | 台数による伸び | 4→8→16 台での物理ステップ/秒、1ステップの受け渡しのバイト数・相手の数 | 自分自身 | 実験3の通信の実測と合わせる |
| P1 | 生データの移動量 | PC へ送るバイト数/秒 | 中央に集める構成 | 測距の生データを中央へ送らないこと(仮定 A4) |

### 2.2 主張の段階(推奨)

- **2週間(2026-11-22)の最小の主張**(反証されにくく、守れる範囲):
  「平面の剛体の物理を、区画ごとのノードが隣との受け渡しだけで分担して計算し、**単一ノードの計算と1ビットも違わない**。
  同じ部屋の USD で、決まった場面の軌跡は MuJoCo と ○ mm 以内(PhysX と MuJoCo の差と同程度)。
  同じ物理の計算部品の上で、GPU を使わずに移動台車の学習曲線が上がる。速さは Isaac Lab より ○ 桁遅く、
  それを補う利点は形の変化の反映(L1)と生データを集めないこと(P1)」。
  - 実機のノード群で物理を動かすのは途上でよい(P10)。シミュレータ(dyne-sim2d)で通信の損失・遅延・一時停止を入れてもビット一致、までは示す。
- **2月(2027-02)のより強い主張**:
  「Dyne の環境で学習した方策を Isaac Lab に持って行っても成功率が ○% 保たれる(R2)。実機16台で同じ物理が
  シミュレータとビット一致で動き、部屋の物を動かすと数秒で環境が変わり、その中で方策がノードの上で動く」。

**使わない言い方**: 「Isaac Lab より速い・安い」「Isaac Lab の置き換え」(§5.5 の見積もりでは反証される)。
P5(一定の仮定が当てはまるユースケースには適切)の書き方に合わせる。

## 3. 設計の選択肢

### 3.1 (a) 2次元か3次元か

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| **a1. 2次元(推奨)** | 床の上の平面の剛体。状態は (x, y, θ, vx, vy, ω)。重力は床との摩擦にだけ効く | 計算が軽い(C5 でも余裕。§5)。dyne-sim2d・sdf2d-grid-actor の長方形の区画と φ をそのまま使える。接触は円板・箱の2次元の判定で済む | 転倒・段差・坂・机の下をくぐる、は扱えない。Isaac との比較は「平面の課題」に限る |
| a2. 2.5次元 | 平面の剛体+高さの属性(机の天板の下を通れるか、など) | 家具の高さを使える | φ は2次元なので、高さごとの形は作れない。USD 側にも家具の上面の衝突判定が無い(usd-physics §4.1) |
| a3. 3次元 | 3次元の剛体と関節 | Isaac と同じ土俵 | 区画・距離場・計算部品をすべて作り直し。2月までにも無理 |

推奨: **a1**。主張の範囲を「平面の移動の課題」と明記する。

### 3.2 (b) 運動と接触の計算方法

前提: 区画で分担しても単一ノードとビット一致させたい。そのためには、各物体の力の計算に使う値と、足し合わせる順序が
分割のしかたに依らず同じでなければならない。

| 案 | 内容 | 分担との相性 | 精度・安定 | 1物理ステップの受け渡し |
|---|---|---|---|---|
| **b1. ペナルティ法+半陰的オイラー法(推奨)** | めり込み量に比例するばね+速さに比例するダンパで押し返す力。摩擦は滑りの速さに比例させ、クーロンの上限(μ×押す力)で切る。速度を先に更新し、新しい速度で位置を進める(半陰的オイラー法、symplectic Euler) | **最良**。接触の力は2物体の今の状態だけで決まる。両側のノードが同じ関数で同じ値を計算すれば作用・反作用が厳密に一致 | 刻みを小さく(2 ms 程度)、ばねを適度に硬く。めり込みが数 mm 残る(MuJoCo も柔らかい接触で 3.6 mm。usd-physics §5.1) | **1回** |
| b2. 逐次インパルス法(PhysX・Box2D 系) | 接触ごとに速度の拘束を1つずつ順に解いて反復する(ガウス・ザイデル法) | **悪い**。解く順序が大域的に決まるので、分担すると順序が変わり結果が変わる。ビット一致させるには、接触でつながった物体の塊を1ノードがまとめて持つか、反復ごとに受け渡す(ヤコビ法に変える) | 大きな刻みでも安定、積み重ねに強い | 反復の回数ぶん(10回なら10回)。Wi-Fi では不可 |
| b3. XPBD(拡張位置ベース法、Macklin ほか 2016/2019) | 位置の拘束を直接満たすよう動かす。小さな刻みを多く取り、1刻みに反復1回(small steps) | 中。反復をヤコビ法にすれば分担できる | 硬さの調整が刻みに依らない。安定 | 小刻みごとに1回(b1 と同程度) |
| b4. Box2D v3 の soft step | 柔らかい拘束+小刻み+最後の緩和 | 中(b3 と同様)。Box2D v3.1 は**機種をまたいだ決定論**を達成(FMA を無効にし、三角関数を自前の近似に) | 良い | 小刻みごと |

推奨: **b1**(2週間〜1月)。理由: 受け渡し1回で済み、ビット一致の規約が単純(§3.3 の3つの規約だけ)。
2月以降に、刻みを大きくしたい場合は b3 のヤコビ版を比べる(§3.3 の「深いのりしろ」と組み合わせる)。
Box2D の決定論の知見(FMA を使わない、三角関数を共通の実装に)は、既存のアクターが純 Rust の libm を使い、
WASM には FMA の命令が無い(relaxed SIMD を使わない限り)ことで既に満たしている。

#### 数の表し方(C5 には浮動小数点の演算器が無い)

| 案 | ビット一致 | C5 での速さ | 開発の手間 |
|---|---|---|---|
| **f64(推奨の出発点)** | WASM では機種に依らず一致(既存の全アクターで実証済み) | 最も遅い。ソフトウェアでの模倣(soft-float) | 既存と同じ |
| f32 | 同上 | f64 よりおよそ数割〜2倍速い見込み(**要実測**) | 小(型を変えるだけ) |
| 固定小数点(Q16.16 など整数で小数を表す) | 整数演算なので一致 | 事前コンパイル(AOT)なら浮動小数点の模倣より1桁以上速い見込み。インタプリタでは命令の解釈が支配的で差が縮む(**要実測**) | 大(平方根・三角関数・掛け算の桁あふれの扱いを自作) |

推奨: **f64 で書き、Rust の型パラメータで f32・固定小数点に差し替えられる形にしておく**。C5 の実測(bench-c5 に
物理の計算の計測を足す)で計算が律速になったときだけ切り替える。§5 の見積もりでは、1環境なら通信が律速で、
計算は律速にならない。

### 3.3 (c) 区画での分け方と受け渡し

**試作で確かめた規約**(theory/edge-physics/partitioned_discs.py。§5.2):

1. **持ち主 = 物体の中心がある区画のノード**。区画は今の長方形のブロック(dyne-sim2d の px×py)。
2. **接触の力は (小さい番号, 大きい番号) の向きで1つの関数が計算する**。界面をまたぐ接触は両側のノードが
   同じ入力で同じ関数を呼ぶので、同じ値になる(片方は符号を反転して使う)。作用・反作用は厳密に一致し、運動量が保存する。
3. **物体ごとの力の和は決まった順序で足す**: 相手の物体の番号の昇順 → 壁 → 床 → 駆動。単一ノードも同じ順序。
   浮動小数点の足し算は順序で結果が変わるので、これがビット一致の要。
4. のりしろ = 2×(最大半径)+余裕。界面からこの距離以内に中心がある物体の状態を、その区画の持ち主へ毎ステップ写す。
5. ステップの最後に中心が区画を出た物体は、新しい区画の持ち主へ移管する。物体は既にゴーストとして隣にあるので、
   移管は「持ち主の印」と、静的な値(半径・質量・慣性モーメント・形の種類・摩擦の値)の受け渡しで済む。

| 決めること | 案 | 推奨 |
|---|---|---|
| 持ち主の決め方 | c1 中心のある区画(推奨) / c2 物体ごとに固定の持ち主(動いても変えない) | **c1**。c2 は移管が無いが、遠くへ行った物体の計算のために遠いノードとの通信が要り、隣との通信だけという特徴3に反する |
| 斜めの隣 | c3 斜めの隣とも直接受け渡す(推奨) / c4 上下左右の隣を経由して2段で中継 / c5 区画の角では物体を置かない制約 | **c3**。試作では 4×4 で受け渡しの約 28%(48.5 通中 13.8 通)が斜めの隣宛て。c4 は1ステップに受け渡しが2回になる。dyne-sim2d は今は上下左右の4面だけを配送するので、角の界面IDを足す変更が要る |
| 受け渡しの頻度 | c6 1物理ステップに1回(推奨) / c7 深いのりしろ: K ステップに1回、のりしろを K 倍に広げ、ゴーストの物体も自分で重ねて計算する | 2週間は **c6**。c7 は通信の回数を 1/K にできる(Wi-Fi が律速なので効く)が、のりしろの中のゴーストの運動もそのまた外の物体に依るので、必要な幅が K×(相互作用の距離+移動量)に広がり、区画の幅(4×4 で 0.9 m)を超えやすい。2月の候補 |
| 区画の大きさの制約 | のりしろ ≤ 区画の幅 | 2×0.15 m+余裕 ≈ 0.32 m。3.6 m の部屋なら 8×8 まで可 |

**ワイヤ形式v2 に足すメッセージ**(crates/dyne-wire。本書では実装しない):

| 種別(案) | 中身 | 大きさ |
|---|---|---|
| BODY_STATE(ゴースト) | 物体の番号 u32、印 u32(持ち主の移管・形の種類)、x, y, θ, vx, vy, ω | f64 なら 1物体 56 B、f32 なら 32 B。ヘッダ 24 B+件数など 8 B |
| BODY_STATIC(移管・初回) | 半径(または箱の半分の寸法)、質量、慣性モーメント、摩擦係数、反発、形の種類 | 1物体 40 B 程度 |

1通の上限 1472 B に入る物体の数: f64 で (1472−32)/56 ≈ **25 物体**、f32 で 45 物体。試作(60物体、2×2)の
1通の最大は 544 B で収まった。§3.5 の「世界を重ねる」案で数が増える場合は、G10(分割送信)と同じ仕組みが要る。
配送の単位は今と同じ (界面ID, ステップ)。ステップ同期・直近2ステップの控え・再送の規約は dyne-sim2d のものをそのまま使う。

### 3.4 (d) 壁・家具を SDF で判定する

| 観点 | 評価 |
|---|---|
| 区画との一致 | ○ sdf2d-grid-actor の φ は同じ長方形の区画で分担されている。物理の計算部品は自分の区画の φ を引くだけ |
| のりしろ | ○(円板) 円板は中心の φ と勾配だけで判定でき、中心は自分の区画にあるので、双一次補間に要るのは区画+1格子の帯。**既存の界面サンプル列で足りる**(試作で全ステップ確認)。△(箱) 箱は角の点で判定するので、角が隣の区画にはみ出す。φ の帯を半対角線ぶん(0.1 m なら 4 格子)広げるか、円板の集まりで箱を近似する |
| 計算の軽さ | ○ 1物体1回の問い合わせ(約30演算)。物体の数に比例し、壁の複雑さに依らない |
| 形の忠実さ | △ 格子の刻み 2.5 cm より細かい角は丸まる。φ は表面の近く(±μ)では観測そのもの、遠くはアイコナール方程式の反復で広げた値。接触に使うのは表面の近くだけなので問題は小さい |
| 未観測の所 | △ φ が「情報なし」の所は壁が無い扱いになり、すり抜ける。USD の衝突判定にも同じ穴が残る(usd-physics §8)。課題の設計で「未観測=壁」とするかを決める(ユーザー判断、usd-physics と共通) |
| 形の変化 | ○ 物が動くと φ が数秒で変わり、環境もそのまま変わる(L1)。△ φ の急な変化でめり込みが急に増えると大きな力が出る → 押し返しの力・めり込みの速さに上限を設ける |
| 比較の公平さ | 生きた φ は雑音を含み、Isaac が読む USD(φ から作ったメッシュ)とわずかに違う。**物理の近さの試験(F2・F3)では、USD の衝突判定の板を同じ格子に焼き直した φ を使い、Isaac・MuJoCo と同じ形にそろえる**。デモ(L1)では生きた φ |
| 物体どうし | 物体どうしは SDF ではなく、2物体ずつの接触(円板どうし: 中心の距離、箱: 分離軸の判定)。候補の絞り込みは区画の中の一様な格子で行う(試作は総当たり) |

推奨: **採用**。試験は「USD から焼いた φ」、デモは「格子型アクターの生きた φ」の両方を使えるようにする。
同じノードで格子型アクター(φ)と物理の計算部品が両方動くことになる。1つの WASM にまとめるか、2つの計算部品を
同じノードで動かして φ をメールボックスで渡すかは実装の段で決める(小さな判断。実機のメモリが決め手)。

  方策の学習を PC が担うのは、この役割分担に合う。
- 一方、学習中の物理まで PC で回すと「GPU が無くても CPU で回せる」という主張にはなるが、Physical-Edge Native の主張ではない。
  発表では、E1 の部分は「単一ノードの照合解を学習にも使った」と正直に書き、ノード群の役割(本番の環境、形の変化の反映、方策の推論)を分けて示す。
- CLAUDE.md の文言を変えるかどうかはユーザーが判断する(エージェントは CLAUDE.md を編集しない)。

### 3.6 (f) 物理シミュレーション環境の中の時刻同期と OTA(P6)

**シミュレータ(dyne-sim2d の拡張)での意味**:

| 機能 | 再現のしかた | 試験(合格の目安) |
|---|---|---|
| 時計のずれ | ノード i の時計 = 真の仮想時刻 + 初期のずれ o_i + 進み遅れ d_i(ppm)× 時刻。同期(SNTP=簡易ネットワーク時刻プロトコル、と往復の時刻印による推定)の事象で、ずれを残差 ε まで縮める | ①**物理の計算はステップ番号で進むので、時計のずれを変えても結果はビット一致**(性質の試験)。②時計の値が効くのは、ヘッダの時刻印、センサの値(測距・IMU)をどのステップに対応させるか、実時間に合わせて進める速さ。動く箱の位置の誤差 ≈ 箱の速さ × 時計のずれ、を同期あり/なしで示す |
| 実時間への追従 | 物理ステップ s を、同期した時刻 t0 + s×Δt に始めるよう待つ(間に合わないときは遅れを記録) | 遅れの分布。同期が無いと隣どうしの待ち時間が増える |
| OTA(計算部品の差し替え) | 「配る」(ノードごとに届く時間と失敗の確率を持つ事象)と「**決めたステップ S で一斉に切り替える**」の2段。全ノードが受け取ったことを確かめてから S を決める。届かなかったノードがあれば S を延ばす | ①同じ中身の計算部品に差し替えたら、差し替えない場合とビット一致(状態の移送は dyne-sim の handover と同じ「物理状態だけ運ぶ」原則)。②版を混ぜて動かすと、界面をまたぐ接触の力が両側で違い、作用反作用が崩れて運動量が保存しなくなることを示し、一斉切り替えが必要な理由にする |
| 方策の更新 | OTA と同じ仕組みで方策の重みを配る | 切り替えたステップ以降の行動が新しい方策と一致 |

界面のメッセージに計算部品の版を載せる欄は今のワイヤ形式v2 に無い(ヘッダの版はワイヤ形式の版)。
BODY_STATE の印の欄に計算部品の版の下位ビットを入れ、版が食い違う受け渡しを検出できるようにする(案)。

**実機での意味**: 時刻同期は G1(SNTP+往復の時刻印)、OTA は G2(2面のパーティションテーブル、計算部品の別区画、ハッシュ確認、失敗時の巻き戻し)。
物理の計算部品も G2 の仕組みで配る。実機では「切り替えのステップ S」をノードに配る制御のメッセージが要る(PC → 全ノード)。

注意: heat1d の 79.5 ms は、1ステップの演算量(65 点の格子の更新)から考えると桁違いに大きい。原因は切り分けていない
(配列の上限まで回している、呼び出しの固定費が大きい、などの可能性。**要確認**)。物理の計算部品でも同じ固定費が
乗るなら、ステップの速さは通信ではなくこの固定費で決まる。P5 の最初に bench-c5 で測る。

### 5.2 試作の結果(theory/edge-physics/partitioned_discs.py、2026-11-11 実行)

条件: 3.6 m × 2.7 m の部屋(壁際に箱2つ)、円板 60 個(半径 5〜12 cm)+移動台車1台(半径 15 cm)、Δt = 2 ms、
3000 ステップ(仮想 6 秒)、初速 最大 2 m/s、床の摩擦小(0.02)。壁は 2.5 cm 刻みの SDF を双一次補間。
実行: `.venv\Scripts\python.exe theory\edge-physics\partitioned_discs.py 3000 60 0.02 2.0`

| 分割 | 判定 | 1ステップの受け渡しの通数(全体) | うち斜め | 1通の最大 | 1ノードの持ち物体の最大 / 見える物体の最大 | 界面をまたぐ接触(延べ) | 移管(延べ) | φ の参照が区画+1格子に収まる |
|---|---|---|---|---|---|---|---|---|
| 2×2 | **PASS (bit-exact)** | 9.8 | 1.8 | 544 B | 20 / 31 | 224 | 36 | ✓ |
| 4×4 | **PASS (bit-exact)** | 48.5 | 13.8 | 388 B | 12 / 19 | 334 | 81 | ✓ |

既定の条件(24 物体、床の摩擦 0.3、初速 0.6 m/s)でも 2×2・4×4 ともビット一致。Python の float は IEEE 754 の倍精度なので、
WASM の f64 での一致と同じ意味を持つ(ただし本物の計算部品で改めて確かめる)。1ノードの隣の数は最大 8(斜めを含む)。

### 5.3 C5 での計算の見積もり(**すべて要実測**)

1物理ステップあたりの浮動小数点の演算の数(試作の式から数えた概数):

| 処理 | 演算の数 | 回数(4×4、1ノード、60物体) |
|---|---|---|
| 接触の候補の判定(2物体) | 約 8 | 総当たりで 持ち×見える ≈ 4×10(平均)〜12×19(最大) |
| 成立した接触(平方根1・割り算2を含む) | 約 55 | 平均 0.1 未満 |
| 壁の問い合わせ(双一次補間と勾配) | 約 30 | 持ち物体の数 |
| 床の摩擦・積分 | 約 30 | 持ち物体の数 |
| 移動台車の駆動(sin・cos を含む) | 約 20+三角関数2回 | 0〜1 |

→ 1ノード1ステップで **平均 約 600 演算、最大 約 2,500 演算**。
C5(240 MHz、浮動小数点の演算器なし)で、WAMR のインタプリタ+f64 の模倣を **1演算 300〜1,000 サイクル**と仮定すると
(根拠は無い。Espressif の資料は「模倣で非常に遅い、固定小数点を推奨」とだけ述べる)、
平均 0.8〜2.5 ms、最大 3〜10 ms。事前コンパイル(AOT)ならこの数分の1。
**1環境なら、計算は Wi-Fi の受け渡し(次項)より軽い見込み**。§5.1 の固定費の問題が無ければ。

メモリ: 1物体 約 100 B(状態+静的な値+ゴーストの控え)、区画の φ は sdf2d の縮小版と共有。世界を K=10 重ねても数十 KB。PSRAM 8 MB に対して問題にならない。

### 5.4 ステップの速さと環境ステップ/秒

### 5.5 速さ・費用の比較の見込み(勝負しない軸を明確にするため)

| 項目 | ノード群(C5 ×16) | GPU の計算機(Isaac Lab) |
|---|---|---|
| 機材費 | 約 2.1 万円(C5 16台。two-week-plan §3.5) | RTX 4080 以上の計算機(数十万円)。今回は借りる |
| 消費電力 | 16 × 0.5〜1 W ≈ 8〜16 W(1台 100〜200 mA の見込み、**未実測**。実験0で測る) | 数百 W(**要確認**) |
| 環境ステップ/秒 | 約 1〜15 | 10⁴〜10⁶(**要実測**) |
| 電力あたり(J/環境ステップ) | 約 1 J | 約 10⁻³ J の桁 |

→ **速さで 4〜5 桁、電力あたりでも約 3 桁、負ける見込み**。「Isaac Lab より安い・省電力」は主張できない。
ノード群の価値は別の軸にある: ①環境が空間の中にあり、形の変化が数秒で反映される(L1)、②測距の生データを中央に集めない(P1)、
③GPU の調達が要らない(借りる・クラウドの時間の確保が要らない)、④ノードが増えれば区画が細かくなり、1台あたりの負担が減る(S1)。

## 7. ユーザーが決めること

1. **次元**: 2次元(推奨)/ 2.5次元 / 3次元。
2. **接触の計算方法**: ペナルティ法+半陰的オイラー法(推奨)/ XPBD / 逐次インパルス法(分担に不向き)。
3. **数の表し方**: f64 で出発し実測後に判断(推奨)/ 最初から f32 / 最初から固定小数点。
4. **斜めの隣の受け渡し**: 角の界面を足して直接送る(推奨)/ 上下左右を経由して2段で中継。
   dyne-sim2d・dyne-wire の変更を、並行の作業とどの順で入れるか。
5. **壁・家具の判定**: SDF を使う(推奨)。比較の試験は USD から焼いた φ、デモは生きた φ、の両方とするか。未観測の所を壁とみなすか(usd-physics §8 と共通)。
6. **強化学習の回し方**: E3(PC の CPU で同じ計算部品を回して事前学習、ノード群で評価・推論・追加学習。推奨)/ E1 / E2。
   **学習中の物理を PC で回すことを CLAUDE.md の前提の例外として認めるか**、CLAUDE.md を直すか。
7. **「GPU なし」の意味**: 学習を含めて GPU を使わない(PC の CPU は可)、でよいか。
8. **何をもって「近い」とするか**: 2週間は F1+F2+R1(+T1・C1 の正直な表)、2月は R2 を加える(推奨)。
   F2 の物差し「PhysX と MuJoCo の差の幅に入る」でよいか。
9. **比較の相手のロボット**: Isaac の Jetbot に寸法を合わせる(推奨)/ 別の車輪ロボット。
10. **時刻同期・OTA の再現の範囲**: §3.6 の試験一式を 12月(P4)に入れる(推奨)/ 2週間に前倒し。
11. **世界を重ねる並列環境(K 個)を入れるか、入れる時期**(推奨: 1月)。
