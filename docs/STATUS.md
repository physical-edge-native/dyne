  LM法。既定構成は幅16×1層(STATUS旧記載の2〜3層はLM法の行列上限と両立せず)。

### 1(b) 16ノード劣化対策(2026-08-26、完了)

方策: 方程式残差の評価点を格子点だけでなく格子間隔の内部点にも置く(設定キー
`sub`=細分数、既定1=従来どおり。`--pinn sub=2`)。内部点の「前ステップの値」は
前ステップ終了時のNNをその点で評価した値(u_prevを「前ステップのNNが表す関数」と
みなす)。アクター内で完結し、通信・仕様は不変。

結果(2000ステップ、解析解との最大誤差):

| sub | N=1 | N=4 | N=8 | N=16 |
|---|---|---|---|---|
| 1(従来) | 2.5e-4 | 6.1e-5 | 8.4e-5 | 2.1e-2 |
| 2 | 1.2e-4 | 8.7e-5 | 8.3e-5 | **3.1e-5** |
| 4 | 2.0e-4 | 2.5e-5 | 8.3e-5 | 7.4e-2 |

- **sub=2 で16ノードの劣化が解消**(2.1e-2 → 3.1e-5、差分法16ノードの8.0e-5より良い)。
  誤差は時間とともに単調減少(sub=1は単調増加だった)。劣化の原因は「1ノード5点では
  残差評価点が不足」で確定。粗い補正(全域を見る粗いモデル)は不要だった。
- **sub=4 は16ノードで逆に悪化**(7.4e-2、単調増加)。N=1〜8では問題なし。原因は未解明
  (5格子点に17評価点、49パラメータの構成で系統的な偏りが増幅する)。既定はsub=1のまま
  (既報の数値の再現性のため)、**16ノード以上では sub=2 を推奨**。
- sub=1 の4本は既報の値と完全一致(変更が既定動作を変えていないことの確認)。
- 計算コスト: sub=2 で約2倍、sub=4 で約4倍のステップ時間。
- sub=2・16ノードでの確認(すべて合格): 決定論=カオス注入(損失5%、遅延揺らぎ20ms)+
  handover(node5)を2回実行して全出力一致、最終誤差1.0e-4。GROW(node7 16→24、step251)=
  機能保存 4/4点ビット一致、最終誤差3.1e-5(無操作と同値)。SHRINK(16→8、温め50)=
  最終誤差3.1e-5(無操作と同値)。

### 今ここ(2026-11-17): 16台の最初の書き込みと、2次元の波動方程式の実機 2×2(場所A)

場所A = 2026-11-27 までの仮の部屋(以後の場所Bと値を直接比べない)。まとめの下書き: docs/2026-11-17-wave2d-hw-day1.md。

- **書き込み**: ESP32-DevKitC-VE 16台。1台は MAC の最後の1バイトが重なりノード番号 200 が重複 → ctl の node_id(NVS)で 201 にした。
  全台 PSRAM 8 MB・自己検査 PASS
- **内部 RAM の不足**: サービス起動後の空きが約 3.9 KB で、アクターの OTA が `"err":"task"` で失敗 → WASM の線形メモリを PSRAM へ
  (issue #82、PR #87 は未マージ。速度の低下の基準が未測定なので Refs)。修正後の空きは約 47 KB(46,951〜47,303 バイト)、
  アクターの OTA は4台・ファームの OTA は3台で ok。同じ夜に16台すべてを修正版で USB から書き直した
- **3×1 は実機で動かない**(縮小版アクターの区画の一辺の上限 48 点、`dyne_init2d failed rc=-1`)→ issue #83
- **2×2**(node 56・172・201・232、ブロックの順。232 は電池): gauss_dirichlet PASS (bit-exact) 55.2 秒、損失 0.3 も PASS 100.0 秒、
  gauss_absorb PASS 55.8 秒(1回目は node 201 が panic で再起動 → issue #85)。232 の電源を切ると、隣が足りない界面を 10 秒ごとに
  報告(想定どおり)。その後の回は**全台が同じ誤った CRC**になり、全台の再起動で直った → issue #86(runbook の回避策 PR #88)。
  再起動後は3回とも PASS
- **時間**: 計算 107.7〜113.7 ms/ステップ(41×41 の区画、インタプリタ、PSRAM。100 ステップ平均)、交換の待ちの中央値 17.3〜19.9 ms
  (PASS の回)、--rt-every 1 で 1ステップごとの待ちの中央値 20.9〜27.5 ms
- **時刻同期**(PC のサーバは UDP 12300。123 は w32time が使用中): rtt_min 2.6〜3.6 ms、rtt の中央値 4.1〜4.3 ms、
  残差の絶対値の中央値 0.1〜0.2 ms。ノード → PC の片道の中央値 878 ms は MQTT・PC 側の待ちとみられ**使えない**(issue #42 のコメント)
