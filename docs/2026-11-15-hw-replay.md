# 実機の入力の再生によるビット一致の確かめ方(2026-11-15、GitHub issue #2)

出所: Claude Code が 2026-11-15 に作成(コミット前。ユーザーが編集する)。
関連: docs/2026-11-13-firmware-nodes.md §5.3・§5.4・§10 の 8、crates/dyne-sim2d/src/replay.rs、scripts/hw_replay.py。

## 1. 何を確かめるか

これまでのビット一致は「シミュレータの中での分割解と単一ノード解の一致」だった。実機では、アクターに
センサの値(測距のフレーム、IMU の標本)をその場で渡すので、シミュレータは同じ入力を作れない。そこで、
**ノードがアクターへ渡した入力をそのまま記録し、dyne-sim2d で同じアクターに同じステップで渡し直して、
ノードが報告した状態の CRC32 と、シミュレータの同じノードの CRC32 を比べる**(実機とシミュレータの比較)。

- 比べる値: ノードの状態 = dyne_get(k)(k = 0..dyne_len)の f64 のビット列の CRC32
  (ファームの state_crc と同じ。field2d の発行の crc32、done の crc32)。
- 合格の基準: 記録にある全ての CRC32 が一致すること(ビット一致)。
- 単一ノード解との比較は、再生のときは**既定でしない**(`--replay-single` / `hw_replay.py check --single` で行う)。
  判定は実機とシミュレータの比較だけで行う(issue #2 のメンテナーの決定 3、2026-11-15)。

## 2. 決定(issue #2 のコメント、2026-11-15)と実装

| 決定 | 実装 |
|---|---|
| 1. 記録するかどうかは、menuconfig ではなく MQTT で送る実行の設定で、実行ごとに決める | 実行の設定(dyne/cfg/<id>)の `"replay":{"log":true}`(既定 false)。前の下書きの Kconfig の DYNE_REPLAY_LOG は**削除**した(下の理由) |
| 2. 再生の記録だけを QoS 1 で発行する(取りこぼしで偽の FAIL にしないため) | actor_setup・range_fed・imu_fed を QoS 1 で発行。他(field2d・rt・shape・imu_fused など)は QoS 0 のまま |
| 3. 再生のとき、単一ノード解との比較は任意で既定はしない | dyne-sim2d は `--replay` だけなら単一ノード解を解かない。`--replay-single` で解いて比べる |

Kconfig を残さなかった理由: 記録のコードは小さく(関数6つ。DevKitC-VE 向けのファーム全体は 1,352,880 バイトで、アプリの領域の 57% が空いている)、記録しない実行では領域を確保しない
(actor_setup の 4KB と imu_fed の 1.5KB は replay.log のときだけ実行の間だけ確保する)。コンパイル時の切り替えを
残すと「記録できないファーム」と「記録できるファーム」の2種類ができ、決定1の「同じファームで記録する・しない」と
食い違うため。他の作業(issue #19 の Kconfig の追加)との衝突も避けられる。

変更した動作(要確認): **range_fed は replay.log のときだけ発行する**ようにした。以前は feed.range なら常に QoS 0 で
発行していた。range_fed は再生のための記録で、PC の他の道具は使っていない(scripts/ を検索して確認)。
従来どおり常に発行したい場合は、node_v2.c の feed_range の1行を戻せばよい。

## 3. 実機の記録の形(MQTT、dyne/node/<id>/…)

| トピック | いつ | 中身 |
|---|---|---|
| actor_setup | 実行の始めに1回 | `{"idx","id","cfg":[[キー,値],…],"faces":[[種類,値]×4(W,E,S,N)],"init":{"nx","ny","ix0","iy0","h","alpha","dt"},"trunc":false}`。cfg はアクターへの dyne_cfg の全呼び出し(PC の設定、IMU の開始時刻 t0、センサの一覧を含む)を順に。値は %.17g(f64 を正確に戻せる桁)。4KB に入らなければ `{"idx","id","trunc":true}` だけ(シミュレータ自身の設定で再生する) |
| range_fed | 測距のフレームを受信メールボックスへ渡したステップ | 既存の range と同じ形 + step。距離 [m] = d_mm / 1000.0(ファームが渡す値と同じ)。時刻印 t_us もヘッダと同じ値 |
| imu_fed | IMU の標本を dyne_imu_push へ渡したステップ | `{"step","i0","s":[[t_us,ax,ay,az,gx,gy,gz],…]}`。戻り値によらず渡した全ての標本。1.5KB を超えるステップは分けて送り、i0 = そのステップの中での最初の標本の番号(欠けの検出) |
| field2d | field_every ごと(既存) | crc32 = そのステップの計算の後の状態の CRC32。トピックの番号は node.idx |
| status(done) | 終了時(既存) | crc32、計数(range_fed・range_rej、imu_pushed・imu_late・imu_early)と、**replay_skip**(送らなかった記録の数) |

MQTT のアウトボックスが 32KB を超えていたら記録を送らずに replay_skip を数える(メモリを食い尽くさないため。
実行は止めない)。PC の記録側(`hw_replay.py record`)は QoS 1 で購読する。

## 4. 再生の入力の形(テキスト、dyne-sim2d --replay)

scripts/hw_replay.py が MQTT の記録(JSON Lines)から作る。1行1要素、空白区切り、`#` 以降は注釈、f64 は全て
16桁の16進数のビット列(値を正確に運ぶため)。正本は crates/dyne-sim2d/src/replay.rs の先頭の説明。

```
dyne-replay 1
setup N nx ny ix0 iy0 h alpha dt     ノード N の初期化の値(シミュレータの区画と照合)。あれば dyne_cfg は下の cfg 行だけ
cfg N key val                        dyne_cfg の呼び出し(記録の順)
face N f kind param                  面 f の設定(シミュレータの面と照合)
range N step sid t_us count cols d×count st×count   ステップ step の送信の後に渡す測距フレーム
imu N step t_us ax ay az gx gy gz    ステップ step の計算の直前に dyne_imu_push へ渡す標本
check N step crc32 出どころ          ステップ step の計算の後のノードの CRC32(field2d / done)
```

照合: 記録の setup・face とシミュレータの区画・面が食い違えば `replay-setup` の行を出して FAIL にする
(IMU の融合のアクターは格子を使わないので、dt と「界面かどうか」だけを比べる)。

## 5. dyne-sim2d の追加の引数(指定しなければ従来と同じ動作・同じ出力)

- `--replay 経路`: 再生の入力を読み、模擬のセンサの代わりに記録したフレーム・標本を渡す。出力:
  `replay-check node N step S 出どころ sim X node Y OK|DIFF`、`replay-node N: … crc32 X`、
  `REPLAY PASS|FAIL …`。終了コードは一致なら 0。
- `--replay-single`: 再生でも単一ノード解を解いて比べる(全ノードの記録したフレームをノードの順に渡す。
  シミュレータ自身の設定を使うので、実機のセンサの設定が場面ファイルと同じときだけ意味がある。IMU の融合のアクターでは使えない)。
- `--replay-record 経路` [`--replay-hash-every N`(既定 50)]: アクターへ渡した入力と N ステップごとの CRC32 を、
  実機と同じトピック・同じ形の JSON Lines に書く(合成の記録。range_fed には正確な値の d_m も入れる)。
- IMU の融合のアクター(dyne_imu_push を持つ)では、熱拡散の安定条件の検査と解析解を使わない。

## 6. 手順

### 6.1 実機なしの確認(合成の記録。scripts/ci-check.sh の [7] と同じ)

```
cargo build --release -p dyne-sim2d
cd crates\sdf2d-grid-actor && cargo build --release --target wasm32-unknown-unknown && cd ..\..
set WS=crates\sdf2d-grid-actor\target\wasm32-unknown-unknown\release\sdf2d_grid_actor.wasm
target\release\dyne-sim2d.exe --wasm %WS% --scene crates\dyne-sim2d\scenes\empty.txt --steps 120 --quiet --replay-record rec.jsonl --replay-hash-every 10
.venv\Scripts\python.exe scripts\hw_replay.py check rec.jsonl --wasm %WS% -- --scene crates\dyne-sim2d\scenes\empty.txt --steps 120 --quiet --seed 7 --loss 0.2
```

`--seed` と損失を変えても ALL PASS になる(入力は記録から来て、ネットワークの乱れは結果を変えないため)。
`hw_replay.py corrupt rec.jsonl bad.jsonl --node 1 --step 30` で入力の値の1ビット(既定は仮数のビット 40、
相対で約 2^-12)を反転すると FAIL になる。

知見(2026-11-15): 仮数の**最下位**のビット(1 ulp)を反転した場合は、形のアクター(距離 1 m の区画1つ)でも
IMU の融合(加速度の標本1つ)でも、状態の CRC32 は変わらなかった(計算の丸めに吸収された)。CRC32 の比較で
分かるのは「状態が変わった入力の違い」であり、入力そのものの一致ではない。入力の一致は記録をそのまま渡すことで
保証している(再生の入力は f64 のビット列で運ぶ)。
IMU は `hw_replay.py synth-imu` → `convert` → `dyne-sim2d --replay … --replay-record` で記録を作って同じように確かめる。

### 6.2 実機の記録(実機が必要。未確認)

1. PC で記録を始める: `.venv\Scripts\python.exe scripts\hw_replay.py record --broker <ブローカー> --out run.jsonl`
2. 各ノードの実行の設定に `"replay":{"log":true}` を足して注入し、start する。field_every を小さくすると
   食い違いの起きたステップを細かく絞れる(既定 50)。
3. 全ノードの done を見てから記録を止める(Ctrl+C)。
4. 再生: `.venv\Scripts\python.exe scripts\hw_replay.py check run.jsonl --wasm <ノードと同じ .wasm> -- <実機と同じ分割・格子・ステップ数・外周の引数>`
   - 形のアクター: `--scene <場面> --px … --py … --steps … --h …`(格子の大きさは場面と刻みから決まる)
   - IMU の融合: `--px … --py … --nx … --ny … --dt <実機の dt> --steps …`(区画が 3×3 点以上になる nx・ny)
   - 前の実行が同じ記録に混ざるときは `--since <PC の時刻>` で切る(各ノードの最後の actor_setup より後だけを使う)
5. 判定: ノードごとに PASS / FAIL / INCOMPLETE。1台でも INCOMPLETE(replay_skip > 0、記録の数とノードの計数が合わない、
   imu_fed の i0 の欠け)なら、隣の食い違いはその欠けから来うるので全体を INCOMPLETE(終了コード 2)とする。

注意: 実機のアクターは実機用の縮小版(--features small)の .wasm を使う。シミュレータでも同じ .wasm を渡す。

## 7. 確認の結果(2026-11-15、Windows)

- 既存の出力の無変化: origin/main の dyne-sim2d と、変更後の dyne-sim2d で、熱拡散・形のアクター・波動方程式・モデルの
  アクターの27条件(損失・遅延・一時停止・分断、--field-csv、--track-csv、--dump-node を含む)の標準出力・標準エラー・
  書き出したファイルを比べ、26条件はバイト一致。残る1条件(安定条件を満たさない引数でわざと止める)は、
  止まった場所の行番号とスレッドの番号の表示だけが違う(文面と終了コードは同じ)。
- 既存の回帰: scripts/check-sim2d.ps1(9 + 10 条件 PASS、決定論の fc 相違なし、2次精度の誤差 6.975e-4 / 1.741e-4 /
  4.350e-5、対照実験は FAIL)、1次元の12条件(check-baseline12.ps1 と同じ比較。全て MATCH。ただし公開リポジトリには
  a435bf6 が無いので、手元に既にあった dyne-base-a435bf6 のビルドを使った)、scripts/ci-check.sh(ALL CHECKS PASSED)。
- 合成の記録の再生(scripts/ci-check.sh の [7] と手元の追加の確認):
  - 形のアクター(首振りの場面 room6_move_pan4h、2×2、200 ステップ、損失 0.1 で記録): 再生 ALL PASS、
    シードと損失を変えても ALL PASS(--seed 99 --loss 0.2 --lat-ms 5)、--single でも PASS、
    入力の1ビット(仮数のビット 40)の反転で FAIL(反転したノードだけ、統合の遅れの後のステップから)、
    range_fed を1件消すと INCOMPLETE(終了コード 2)、--outer-bc を変えると設定の食い違いで FAIL。
  - IMU の融合(合成の記録 synth-imu、2×2、200 ステップ): 再生 ALL PASS、シードと損失を変えても ALL PASS、
    1ビットの反転で FAIL(合意の平均を通して全ノードに広がる)。
  - 熱拡散(入力なし、3×2): ALL PASS、--steps を1つ違えると FAIL、--dt を変えると設定の食い違いで FAIL。
- ファーム: `node-esp32\build.ps1 -Board devkitc-ve` でビルドが通る(警告なし。dyne_node.bin 1,352,880 バイト、空き 57%)。

  dyne_cfg の値を正確に運ぶ唯一の記録なので、再生の記録として残し QoS 1 にした(実行の始めに1回だけ)。要確認。
