# 2026-08-05-M1手順書(docs\2026-08-05-m1-guide.md)

## M1の目的と成果物

ESPr Developer 32 Type-C(ESP32-WROOM-32)の実機1台で、M0のWASMアクター
`heat1d_actor.wasm`を**一切変更せず**WAMR上で動かす。成果物は次の2つ。

1. 動くもの: 実機で2000ステップを完走し、PCと同じ誤差値を出すファームウェア
2. 限界レポート第2号: RAM使用量・フラッシュ使用量・1ステップ実行時間の実測値

M1は通信なし・1ノードのみ。Wi-Fi・境界同期はM2で行う。

作業は2部構成。**M1a(通訳方式)は必修**で、これが通ればM1合格。
**M1b(AOT=事前コンパイル方式)は挑戦パート**で、ESP32では実行可能メモリの
制約により失敗報告もある。成功でも失敗でも結果を限界レポートに記録する
(失敗の記録も目標1の立派な成果)。

前提: Windows 10/11ネイティブ(WSL2不要)。M0がWindows上で検証合格済みであること。

---

## 1. ESP-IDFのインストール(初回のみ、30〜60分)

ESP-IDFはEspressif公式の開発フレームワークです。Windows用の
オールインワンインストーラを使います。

1. https://dl.espressif.com/dl/esp-idf/ を開き、**ESP-IDF v5.5系(またはv5.1以降の
   最新安定版)のOffline Installer**をダウンロードして実行します。
2. 途中の選択はすべて既定のままで進めて構いません。インストール先は既定の
   `C:\Espressif`を推奨します(パスに空白・日本語が入らないこと)。
3. 完了するとスタートメニューに**「ESP-IDF 5.x PowerShell」**というショートカットが
   できます。以後のコマンドはすべてこのPowerShellで実行します
   (普通のPowerShellではidf.pyが見つかりません)。

確認:

```powershell
idf.py --version
```

バージョンが表示されればOKです。

## 2. ボードの接続確認

1. ESPr Developer 32 Type-CをUSBケーブルでPCに接続します
   (**データ通信対応のUSB-Cケーブル**を使うこと。充電専用ケーブルは不可)。
2. デバイスマネージャー(Win+X → デバイスマネージャー)を開き、
   「ポート(COMとLPT)」に**「USB Serial Port (COMx)」**が現れることを確認します。
   このボードのUSBシリアル変換ICはFTDI製FT231XSで、Windows 10/11なら
   ドライバは通常自動でインストールされます(初回は1〜2分待つ)。
3. COM番号(例: COM5)を控えます。以後 `COMx` と書いた箇所を読み替えてください。

現れない場合: ケーブルを別のものに変える → 別のUSBポートに挿す →
それでも駄目ならFTDIの公式VCPドライバ(https://ftdichip.com/drivers/vcp-drivers/)を
手動インストール。

## 3. M1プロジェクトのビルド

`dyne`リポジトリの`m1-esp32`ディレクトリがM1のESP-IDFプロジェクトです。
M0で使ったwasm(スタック32KB調整版)が`main/heat1d_actor.wasm`として同梱済みです。

ESP-IDF PowerShellで:

```powershell
cd C:\Users\koyab\Documents\dyne\m1-esp32
idf.py set-target esp32
idf.py build
```

初回ビルドの注意:

- `set-target`実行時にWAMRコンポーネント(espressif/wasm-micro-runtime)が
  ESP Component Registryから自動ダウンロードされ、`managed_components\`に
  展開されます(ネットワーク必須)。
- 初回は10分前後かかります。2回目以降は数十秒です。
- ビルド末尾に表示される**バイナリサイズ**を控えてください(限界レポート用)。
  例: `dyne_m1.bin binary size 0x12345 bytes` のような行、または
  `idf.py size` の `Total image size` の値。

## 4. 書き込みと実行

```powershell
idf.py -p COMx flash monitor
```

書き込み(flash)→シリアルモニタ(monitor)が連続実行されます。
モニタの終了は `Ctrl+]` です。

このボードは自動書き込み回路を積んでいますが、もし
`Connecting........_____....._____` のまま進まない場合は手動で書き込みモードに
入れます: **FLASHボタンを押しながらRESETボタンを押して離し、その後FLASHを離す**。
その状態で再度flashコマンドを実行してください。

## 5. 期待される出力と限界レポートの記入

モニタに以下のような出力が出れば成功です:

```
==== Dyne M1: WAMR on ESP32 ====
[m1] free heap at boot: ...... bytes
[m1] wasm module size: 2181 bytes
[m1] RAM used by runtime+instance: ...... bytes
[m1] init done. running 2000 steps...
[m1]   step 500/2000
...
==== M1 REPORT (ESP32 / WAMR) ====
wasm size        : 2181 bytes
RAM used (rt+inst): ...... bytes
min free heap    : ...... bytes
steps            : 2000
total time       : ...... ms
per-step time    : ...... us
L2  vs analytic  : 5.632e-5  (expect 5.632e-5)
Linf vs analytic : 8.027e-5  (expect 8.027e-5)
u[16]            : 9.816824440839e-2 (expect 9.816824440839e-2)
u[32]            : 1.388308626367e-1 (expect 1.388308626367e-1)
==== END ====
```

**合格判定**: L2/Linfとu[16]/u[32]が表示どおりexpect値と一致すること。
ESP32のf64演算はソフトウェア実装ですがIEEE 754準拠なので、PCと同じ値に
なるはずです。もし末尾桁がずれた場合、それ自体が重要な発見なので記録してください。

限界レポート第2号として以下を控えます(M1 REPORTからの転記):

| 項目 | 値 |
|---|---|
| wasmサイズ | 2,181 バイト |
| ファームウェア全体サイズ (build出力から) | |
| WAMRランタイム+インスタンスのRAM使用量 | |
| 最小空きヒープ | |
| 1ステップ実行時間 (通訳方式) | |
| 誤差一致 (L2/Linf/u値) | 合/否 |

参考: PC(wasmi通訳方式)では2000ステップ約260msでした。ESP32(240MHz)の
通訳方式はこれより1〜2桁遅い見込みです。この差を実測することがM1の主目的の
一つで、遅ければAOT(M1b)の価値が定量化されます。

## 6. M1b: AOT(事前コンパイル方式)への挑戦

AOTはwasmを事前にXtensaネイティブコードへ変換してから実機に載せる方式で、
通訳方式の10〜50倍の速度が期待できます。ただしESP32では変換済みコードを
実行可能メモリ(IRAM)に配置する必要があり、ここで失敗する事例が
報告されています。**うまくいかなくても、その事実と理由の記録がM1bの成果です。**

手順の概要(詳細は結果を見ながら次セッションで詰めます):

1. WAMRのAOTコンパイラ`wamrc`を入手します。
   https://github.com/bytecodealliance/wasm-micro-runtime/releases から
   Windows用バイナリ(`wamrc-x.x.x-windows`系)をダウンロード。
2. 変換:
   ```powershell
   wamrc --target=xtensa -o heat1d_actor.aot heat1d_actor.wasm
   ```
3. `main/CMakeLists.txt`のEMBED_FILESを`heat1d_actor.aot`に変え、
   main.cの埋め込みシンボル名も`_binary_heat1d_actor_aot_start/end`に変更。
   WAMR側はロード時にwasm/aotを自動判別するのでロードコードの変更は不要です。
4. ビルド・書き込みし、結果を記録:
   - ロード/インスタンス化が成功するか(失敗ならエラーメッセージを記録)
   - 成功したら per-step time を通訳方式と比較

## 7. トラブルシューティング

**`idf.py`が見つからない** → 普通のPowerShellで実行している。
スタートメニューの「ESP-IDF 5.x PowerShell」を使う。

**set-target/buildでコンポーネント取得に失敗する** → ネットワーク。プロキシ環境なら
`HTTP_PROXY`/`HTTPS_PROXY`環境変数を設定。

**`wasm_runtime_lookup_function`のコンパイルエラー(引数の数)** → WAMRの版差。
`lookup`関数内の呼び出しを`wasm_runtime_lookup_function(inst, name, NULL)`と
3引数に変えてビルドし直す。

**instantiate failedで止まる** → 線形メモリ128KB(+ランタイム分)を確保できていない。
`[m1] free heap at boot`の値と合わせて限界レポートに記録。その上で
`crates/heat1d-actor/src/lib.rs`の`N_MAX`を4096→1024に減らして再ビルドした
wasmで再試行(線形メモリが1ページ=64KBに減る)。

**書き込みは成功するが出力が文字化けする** → モニタのボーレート不一致。
`idf.py -p COMx monitor` は既定115200で、通常は問題ない。化ける場合は
ケーブル・ハブを疑う(ハブ経由をやめて直挿し)。

**Guru Meditation Error / パニックで再起動を繰り返す** → パニックメッセージの
先頭行(例: LoadProhibited, StackOverflow)を控えて報告。スタック不足の場合は
`sdkconfig.defaults`の`CONFIG_ESP_MAIN_TASK_STACK_SIZE`を32768に増やして
`idf.py fullclean build`。

## 8. M1完了後

M1 REPORTの全文(モニタ出力のコピー)を持ち帰ってください。それをもとに
限界レポート第2号を清書し、仕様書C章のM1を完了にし、M2(実機2台の
Wi-Fi境界同期)の設計に進みます。M2ではM0で確定した仕様変更
(クラスタ全体で一意な界面ID、再送バックオフ)をプロトコルに反映します。
