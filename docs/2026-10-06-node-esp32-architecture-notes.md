## 1. コードの地図(読む順)

全体は4ファイル+ヘッダ、計1,549行。読み順の推奨:

| 順 | ファイル | 責務 | 入口になる行 |
|---|---|---|---|
| 1 | main/dyne_node.h (114行) | 全体の宣言。dyne_cfg_t(設定の全フィールド)、状態遷移の列挙、BC定数 | cfg構造体=29行〜 |
| 2 | main/main.c (895行) | 本体。起動列・cfg解析・BSPループ・WASM呼び出し | 下の節で分解 |
| 3 | main/dyne_mqtt.c (151行) | MQTTクライアント層(第2段=zenoh移行時はここだけ差し替え) | 受信組み立て=99行 |
| 4 | main/sensors.c (263行) | DHT20/BME280のI2Cドライバ+周期発行+最新値の保持 | sensors_task=192行 |
| 5 | main/rssi.c (126行) | AP RSSI+プロミスキャス受信の近傍MAC別RSSI | 起動=125行 |

### main.c の分解(行アンカーは2026-10-06時点)

- **起動列**(node_task、846行〜): `log_heap("boot")` → `wasm_up()`(**Wi-Fiより先**。
  理由コメントが850行前後にある=断片化前の連続128→64KB確保)→ `wifi_up()`
  (173行で **WIFI_PS_NONE**=省電力オフ。M2の遅延ジッタ対策の継承)→
  MQTT → センサ → RSSI → 設定待ちループ。
- **node_task は pthread 上**(889行、スタック32KB): WAMRがpthread_self()を
  要求するため(M1知見3)。FreeRTOSタスク直はassertで死ぬ。
- **cfg解析**(parse_cfg、223行〜): cluster/node/bc必須、n≥3、bcキー検証、
  transparent係数の寸法検証(≤64項)、ifaces↔bc=interfaceの整合、
  mode/assim/発注11フィールドの順。**r=αΔt/h²の検証はない**(→リスク台帳R5)。
- **cfg受理**(dyne_on_cfg、355行〜): 検証→ack(ペイロードCRC32つき)→configured。
- **号令**(dyne_on_ctl、382行〜): start/stop/report/reboot。startは古いstopラッチを
  打ち消す(2026-09-18の事故対策)。retainedなctlは無視(規約§3.6)。
- **BSPループ**(run_bsp): 1周= ペーシング(下記)→ 境界送信 → 隣の値の受信待ち
  (タイムアウト100ms・再送バックオフ・応答再送=M0知見)→ dyne_step() →
  観測周期なら dyne_observe(737〜752行: γはholdoutなら0)→ 観測系の発行。
- **ステップのペーシング**(step_period_ms>0時): `target = pace0 + step×周期` の
  **絶対目標時刻**に vTaskDelay で追従。遅れたら眠らず追いつく=誤差は蓄積しない。
  tickは10ms(CONFIG_FREERTOS_HZ=100)なので1歩あたり最大±10〜20msのジッタ。
- **データ面とMQTTの分離**: 境界交換は自前UDP直送(40バイト、ワイヤ形式)。
  MQTTは観測・制御のみで、観測系の発行は enqueue=true(BSPループを止めない)。

## 2. メモリアーキテクチャ(ESPr Developer 32 Type-C = ESP32-WROOM-32)

### 2.1 ハードの素性

- CPU: **Xtensa LX6 ×2コア 240MHz**(sdkconfigで240MHz固定)。f64はソフト演算。
- SRAM 520KBだが**DRAMとして連続では使えない**: ヒープ初期化の実測で
  区画が 6 / **129** / 14 / 111 KB に割れている(発注7レポート§6.6)。
  **最大の連続ブロックは起動直後でも約108KB**(129KB区画−静的消費)。
  PSRAMなし。フラッシュ4MB(アプリ使用は約1.13MB、空き26%)。

### 2.2 静的RAM(リンカマップ実測、2026-09-21ビルド)

| セクション | 大きさ | 中身 |
|---|---|---|
| .dram0.data | 22.2 KB | 初期値つき静的変数 |
| .dram0.bss | 39.9 KB | ゼロ初期化静的変数 |
| 合計(静的DRAM) | **62.1 KB** | |
| .iram0.text | 92.9 KB | RAM常駐コード(Wi-Fi/WAMR通訳の高速経路) |
| .flash.text / .rodata | 832 / 155 KB | フラッシュ実行コード・定数 |

bssの大口: MQTT受信組み立てバッファ **s_rxbuf 8KB**(dyne_mqtt.c:31)、
main.cの静的JSON作業域 **3KB**(main.c:494)、Wi-Fiスタック約4KBなど。

### 2.3 動的RAM(ヒープ)の予算 — 実測4定点(2026-09-18、2台構成)

| 定点 | 空き合計 | 最大連続 | 読み方 |
|---|---|---|---|
| boot | 201,780 | **110,592** | 起動直後。128KBの連続は構造的に取れない→小型wasm(64KB)の根拠 |
| after-wasm | 112,060 | 53,248 | wasm一式≈90KB消費(線形64KB+WAMRヒープ4KB+実行スタック8KB+管理) |
| after-wifi | 62,280 | 43,008 | Wi-Fi≈50KB |
| after-services | **36,304** | 34,816 | MQTT(受信4KB+送信2KB+管理)+センサ/RSSIタスク後の定常 |

**定常の空き約36KBが実験1の運転余裕**。消費する側の最大物は
cfg受信(transparent 25項込みで**約2.3KB**、組み立て8KB静的バッファ内で処理)と
cJSONの一時パース(数KB)。36KBに対して十分収まる。

### 2.4 WASMまわりの配置

- 小型wasm(heat1d_actor_small.wasm、3,616B)は**線形メモリ1ページ=64KB・
  最大指定なし**(バイナリ解析で確認)。64KBの内訳: wasmスタック8KB+
  u/u_next(16B/点×N_MAX2048=32KB)+透過境界係数・補助変数2.5KB+リンカ予約。
- エクスポート12本を確認済み: dyne_init/step/get/**set**/set_neighbor/
  boundary_value/boundary_grad/len/x/**observe**/**set_bc_value**/**transparent_coef**
  — ファームが必須とする全部(発注8・11の追加分含む)が入っている。
- WAMRはClassic通訳固定(sdkconfig、fast-interpは本環境でロード不能=M1知見)。
  インスタンスヒープ4KB・実行スタック8KB(発注7(c)の縮小)。

## 3. 命令セットと実行方式(AOT問題の現在地)

- Xtensa向けAOT(事前コンパイル)は**不成立で確定**(M1b、2026-08-07):
  LLVM18/19の両方で生成した.aotが、初回のWASM関数呼び出しで**ビット単位で同一の
  クラッシュ**(PC・化け値まで一致)→ 生成側でなくランタイムのXtensa再配置処理を
  疑う切り分け。上流報告ドラフトあり(docs/2026-08-07-wamr-issue-draft.md)。
- よって実機は**Classic通訳**。速度はPC比約600倍遅いが、実験1は1ステップ=1秒の
  実時間運転なので問題にならない(§4)。
- AOTの回避路はRISC-V(XIAO ESP32C6)で、実験1の後の通信検証と併せて判定予定。

## 4. 時間予算(リアルタイム性)

| 量 | 値 | 根拠 |
|---|---|---|
| 計算時間(65点1台) | 79.5 ms/步 | M1実測(240MHz・Classic) |
| 計算時間(33点/台) | ≈41 ms/步 | 発注7実機確認①の実測(compute_ms) |
| **実験1(16〜17点/台)の見込み** | **≈20〜25 ms/步** | 点数比例(通訳実行は点数に線形) |
| ステップ周期 | 1000 ms | step_period_ms=1000 |
| **利用率** | **2〜3%**(余裕40倍) | 観測・発行・I2Cは別タスク/キュー経由 |

付随コスト: dyne_observe(1点)はµs級、透過境界の積和は4×25≈100回/面(µs級、
実機実測でもcompute_ms不変=発注7§6.8(D))。センサ読取(I2C)は別タスクで5秒周期。
ペーシングは絶対時刻追従なので、2000歩×1秒=33分で累積ずれなし
(esp_timerは64bitµs、オーバーフローは事実上なし)。

## 5. リスク台帳(予測と潰し込みの状態)

**凡例**: [済]=コード・設定・実測で潰し込み済み / [機]=実機で確認する定点 /
[監]=運転中の監視項目。

| # | リスク | 状態 | 根拠と手当て |
|---|---|---|---|
| R1 | 線形メモリの連続確保に失敗(instantiate失敗) | [済] | 小型wasm64KB+**WASM→Wi-Fiの起動順**(main.c:846〜)+heap4定点ログ。[機] boot時 largest<70KBなら異常(他の常駐が増えた兆候) |
| R2 | AOT不可で速度不足 | [済] | Classic通訳固定。実験1は利用率2〜3%(§4)。[機] rtトピックで compute_ms≈20〜25・rt_rate≈40〜50 を初回確認 |
| R3 | RAM不足(定常) | [済] | 定常空き36KB vs 最大消費cfg≈2.3KB。[監] 長時間運転での空き減少(次回ファーム改修でstatusにheap定期掲載を検討) |
| R4 | cfgが受信バッファに収まらない | [済] | transparent25項=1,511B、cfg全体≈2.3KB < 組み立て8KB(dyne_mqtt.c:31)。MQTT受信4KBはチャンク結合で吸収(:99) |

| R6 | Wi-Fi省電力による遅延ジッタ | [済] | WIFI_PS_NONE(main.c:173) |
| R7 | 乾電池のブラウンアウト(電圧低下リセット) | [機] | 検出器有効(lvl0)。新品4.5V→LDO3.3Vは余裕。消耗末期+送信バーストで再起動→LWT(offline)で検知できる。実験前に新品、30分放置テストで確認 |
| R8 | ルーターのDHCPで実行中にIPが変わり結線切れ | [監] | peersはcfg注入時に解決(--peers auto)。**対策: ルーター側で4台+PCのDHCP予約(推奨)**。切れたらstop→再注入→start(規約§3.5の手順) |
| R9 | 古いretained cfgで走る | [済] | 世代番号genのエコー照合+start前のack確認(規約§3.6)。実験開始前に `mosquitto_pub -r -n -t dyne/cfg/<id>` で不要IDを掃除 |

| R11 | タスクスタック不足 | [済] | node_task=pthread 32KB(main.c:889)、センサ/RSSI各4KB(葉処理のみ)。メインタスク16KB |
| R12 | 開始ずれ・パケット消失 | [済] | M0以来の再送・応答再送・取り置き・ドレイン(2台実機で再送0〜2の実績) |

| R14 | watchdogによる停止 | [済] | BSPループはvTaskDelay/受信待ちで必ずブロックし、アイドルタスクが走る。2台×2000步完走の実績 |

## 6. 実機での「見る定点」(初回電源投入〜本計測前)

1. モニタの heap 4定点(§2.3の表と比較。boot largest≈110KB / after-services≈36KB)
2. status online の mac/ip → ルーターのDHCP予約に登録
3. rt トピック: step_ms≈1000(ペーシング確認)、compute_ms≈20〜25、wait_ms
4. sensor: temp_c が室温レンジ・5秒周期で安定
5. cfg注入時: 全台の ack(ok) と gen の一致
