# 2026-07-08-Dyne開発課題整理(docs\2026-07-08-plan.md)

## 目的
物理モデルを分割し、軽量化し、分散するエッジデバイスに配置する。
エッジでのデータ収集から物理モデルの分割・デプロイ・分散学習・協調推論、デジタルツインの構成・監視までを、エッジに配置されたマイコン群だけで実行できるプラットフォームを目指す。マイコン群の各マイコンは軽量APIサーバーとPub/Subクライアントを持ち、マイコン群から選出されるブローカー兼任ノードはwebサーバーとMQTTブローカーを持つ。開発者PCは、最初にマイコン群に物理モデル等を流し込む時と監視時および設定変更時、障害時の再分割時(後述のPhysical Cluster Orchestrator機能)のみ接続する。将来的にクラウドとの接続を視野に入れる。
クラウドネイティブアーキテクチャが抱える課題を解決するため、クラウドネイティブアーキテクチャを取り入れつつも依存しないEdge Nativeアーキテクチャを目指す。

上記を目標にツールチェーンの開発を進めている。便宜上このツールチェーンをDyneと呼ぶ。
ただし、ここでのモデル分割とはレイヤー方向の分割ではなく空間方向の分割を指すので注意する。物理空間を分割し、分割されたモデルに書く物理空間を担当させて協調推論を行う。

## 前提
Dyneは3つのレイヤーを持つ。
- 1つ目のレイヤー：コンパイラレイヤーはモデルの分割・配置を担う。具体的には「重いランタイムを除去して計算グラフと重みデータを切り出す」「計算グラフと重みデータを分割」「軽量化」「エッジ最適化」「通信ロジックの注入」「WASMアクター化」を担い、物理モデルが動くコンテナを生成する。
- 2つ目のレイヤー：ランタイムレイヤーは、物理モデルが動くコンテナを、マイコン上で実行・協調させるための超軽量ミドルウェアであり、従来の重いランタイムにとって代わる。
- 3つ目のレイヤー：可視化レイヤーは、開発者PCが接続されている時のみ使われる。docs\2026-07-09-plan-viz.mdを参照。


Dyneの使い方について、大まかに4パターンのワークフローを想定している。
- 1つめのワークフロー：モデル分割・配置。物理モデル（Rust製の数値ソルバ・PINNs・FNO・その他将来的には現代的なPhysicalAIモデル）について、同じパイプラインで、「重いランタイムを除去して計算グラフと重みデータを切り出す」「計算グラフと重みデータを分割」「軽量化」「エッジ最適化」「通信ロジックの注入」「WASMアクター化」「マイコンへのデプロイ」までを行いたい。

- 2つめのワークフロー：データ収集。分割された各領域を担当するマイコンが、1台につき複数のセンサーからのデータを吸い上げる。マイコン群からブローカー兼任ノードとなるマイコンを選出し、ブローカー兼任ノードがMQTTブローカーを持つ。マイコンは通信スタック(Pub/SubとAPIサーバー)を持つ。ユーザーは収集されたデータを入手するとき、PCのCLIツール(またはwebレイヤー)からマイコンへHTTPリクエストで直接アクセスすることも、MQTTブローカーへのPub/Subでマイコン群全体の統合されたデータを収集することもできる。さらに、ユーザーPCのCLIツールから、複数のマイコン群から収集されたデータを統合できるようにしたい。

- 3つめのワークフロー：協調推論。モデル分割ワークフローでマイコンにデプロイされた物理モデルでの推論。隣の領域を担当するマイコンと、担当領域間の境界部分の物理量とその勾配を通信しながら協調推論する。データ収集ワークフローと連携して、定期的に現実のデータとシミュレーションを同期することもできる。また、データ収集ワークフローと同じように、ユーザーはCLIツール(またはwebレイヤー)からマイコンのAPIもしくはマイコン群のMQTTにアクセスして推論結果をリアルタイムに取得できる。

- 4つ目のワークフロー：分散学習。モデル分割ワークフローで分割されたモデルを、各マイコンで分散してファインチューニングし、そのまま協調推論ワークフローに移ったり、ファインチューニングされたモデルを再度統合したりする。



## 決定事項
- Edge Nativeアーキテクチャに従う。クラウドネイティブでは「中央がエッジを管理する」プル型である。Dyneは「エッジが自律し、中央はオプションで接続できる」プッシュ/サブスクリプション型にします。中央サーバーは「なくても動く補助」として設計し、存在する場合はエッジのデータを購読する一ノードとして扱う。
- マイコンを配置し、最初に開発者PCで設定するだけでデータ収集や推論、学習処理が開始して、必要なときだけ開発者が任意のPCでマイコン群に接続して操作する、といった使い方を実現する。
- 通信：ブローカー兼任ノードを役割として動的に選出する設計にする。
```
起動時：
  1. マイコン群がmDNSでお互いを発見
  2. 簡単なリーダー選出（最初に起動したもの、または固定指定）
  3. 選出されたノードがブローカーを起動
  4. 他のノードがそのブローカーに接続

ブローカーノードが落ちた場合：
  5. 残りのノードが再選出してブローカーを再起動
```
```
各マイコン：
  軽量APIサーバーあり（設定変更・ヘルスチェック・コマンド受信）
  Pub/Subクライアントあり（データ発行・コマンド購読）

マイコン群のうち1台（ブローカー兼任ノード）：
  上記に加えてMQTTブローカー + Webサーバー（ダッシュボード配信）
```
```
各マイコンのAPI（最小構成）：
  GET  /health          ← 死活確認
  GET  /status          ← 現在の状態・担当モデル
  POST /config          ← 設定変更
  POST /deploy          ← サブモデルの受け取り・適用
```
- 各マイコンのデータ発行以外の処理はブローカーの存在に依存してはいけない
```
ブローカーへの接続が切れた場合：
  - データ収集・推論・学習は継続（Pub/Subと独立して動く）
  - 発行できなかったデータはローカルにキューイング
  - 新しいブローカーノードを発見したら接続し直してキューを流す
```

- 通信；APIサーバーもマイコンに立てる
```
Pub/Sub が得意なこと：
  - データの継続的な流し出し（センサー値、ログ）
  - 非同期の状態通知
  - 1対多の配信

REST APIが必要になるとき：
  - マイコンへの同期的な命令（モデルの入れ替え、設定変更）
  - 単発の状態取得（「今のファームウェアバージョンは？」）
  - デプロイのトリガー（OTAアップデートの開始）
  - エラー時の診断クエリ
```
- 開発者PCの接続フロー
```
初回セットアップ（PCあり）：
  PC → マイコン群に設定を流し込む → PC切断

通常運転（PCなし）：
  マイコン群が自律的にデータ収集・推論・学習を継続

必要なとき（PCあり）：
  PC → mDNSでブローカーノードを発見
     → Subscriberとして参加するだけ
     → PCが切断してもマイコン群は継続動作
```
- 応用研究として後から開発する：Physical Cluster Orchestrator
```
① 障害検知
  開発者PCがブローカー経由でハートビートの欠落を検知
  または生きているマイコンからの障害通知を受信

② 影響範囲の特定
  落ちたマイコンが担当していた：
    - 物理領域（センサーの担当範囲）
    - サブモデル（モデルの分担）
    - データフロー上の依存関係（他のノードがそのノードの出力に依存していないか）

③ 再分割計画の生成
  残存マイコンのリソース（CPU、メモリ、センサー到達範囲）を収集
  物理領域の再分割案を生成
  サブモデルの再分割案を生成
  ※この2つは独立ではなく連動して計算する必要がある
  ※分割アルゴリズムは、計算グラフ構造と空間的な位置関係をコンパイラが解析して最適な分割線を決定するアルゴリズムが必要。(これをPDE-aware Partitioningとよぶ)


④ 再デプロイ
  新しいサブモデルを対象マイコンにOTA転送
  物理領域の担当マップを更新・配布
  マイコン群に新しい設定を適用

⑤ 動作確認
  再デプロイ後のデータフローを検証
  精度劣化の推定値を開発者に提示
```
- 応用研究：Physical Cluster Orchestratorの責務分担
```
開発者PC（接続時）の責務：
  - 障害検知エージェント
  - 再分割計画エンジン（物理トポロジー × モデル依存グラフ）
  - 再デプロイオーケストレータ
  - 精度劣化の推定・提示

マイコン群（常時）の責務：
  - データ収集・推論・学習の継続
  - ハートビートの発信
  - 再デプロイ指示の受信と適用
```

- 3つ目の協調推論ワークフローについて、マイコンは隣の領域を担当するマイコンとしか通信しない。隣の領域における物理量とその勾配のみ通信するプロトコルを規定する。（このプロトコルをBoundary Sync Protocolと呼ぶ。）不安定なエッジネットワーク環境下での課題への対策を検討する。


- 4つ目の分散学習ワークフローについて、最初のユースケースとしてはデジタルツインを構成する物理モデルの分散学習をサポートする。将来的には校正したデジタルツインの中で自律制御機械(ロボット)を動かすモデルの強化学習タスクにおける分散学習もサポートしたいが、それは可能か。デジタルツイン構成用とロボット関節強化学習用で、分散学習ワークフローが2本走ることになる。



## タスク
- Edge Nativeの標準をリサーチしそれに従う
- モデル分割については、先行研究を模倣した実装をまず行う。（先行研究に従うとモデルアーキテクチャによってそもそもそも分割できないモデルがあったり、分割のアルゴリズムが違ったりするはずなので、そこもいろいろ実装試しながらリサーチし、記録する。）また、近年のPhysical AIのモデルアーキテクチャを分類・整理し、モデル分割が可能なものを検討する。分割できないモデルについても、モデルをそのまま各ノードにデプロイすれば協調推論・分散学習ワークフローがそのまま応用できないか検討する。
- 4つのワークフローの動作に必要なパイプラインを計画する。パイプラインの本数はできるだけ少ないほうが良い。
- パイプラインを計画できたら、パイプライン別にプロトタイプをつくる。






## 課題
- 上記4パターンのワークフローが、同じパイプラインを共有するアーキテクチャにするか、それぞれに異なるパイプラインを実装する必要があるか。

- セキュリティ機能をまだ検討していないが、ここは当面放置でよい。
