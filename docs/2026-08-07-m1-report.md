# 2026-08-07-M1完了レポート(docs\2026-08-07-m1-report.md)— 限界レポート第2号

## 目的と結果

M1の目的: M0のWASMアクター`heat1d_actor.wasm`を**一切変更せず**、実機
ESPr Developer 32 Type-C(ESP32-WROOM-32)のWAMR上で動かし、RAM・フラッシュ・
実行速度を実測する。

**結果: 合格(2026-08-07)。** 実機で2000ステップを完走し、誤差(L2/L∞)と
代表点の値がPC実行と**表示全桁で一致**した。ESP32のf64はソフトウェア演算だが
IEEE 754準拠であることが数値で確認できた。M0のwasmはバイト単位で無改変。

### 速度の位置づけ(目標1の核心データ)

- PC(wasmi・通訳方式): 約0.13 ms/ステップ → **ESP32(Classic通訳)は約600倍遅い**。
- 本問題のdt=1e-4秒に対し1ステップ79.5msなので、実時間の約800倍遅い。
  通訳方式のままでは「実時間追従するデジタルツイン」は米粒サイズの問題でも不成立。
- 高速通訳(fast-interp)は本環境でロード不能(下記知見2)、事前コンパイル(AOT)は
  未検証(M1b)。**AOTが目標1の速度面の生命線**であることが定量化された。

## 知見(すべて再現手順つきで確定)

1. **Rustのwasm既定スタック1MB問題(M1準備段階で検出・対処済み)**。
   wasm32-unknown-unknownの既定ではスタック1MBが線形メモリに含まれ、
   モジュールが最小18ページ=1,152KBを要求してESP32では確実に
   インスタンス化不能。`-C link-arg=-zstack-size=32768`で2ページ=128KBに削減した。
   マイコン向けwasmはスタックサイズの明示指定が必須。

2. **fast-interp(高速通訳)のロード失敗**。ESP-IDFコンポーネント
   (espressif/wasm-micro-runtime)のFastモードでは、`wasm_runtime_load`が
   「WASM module load failed: allocate memory failed」で失敗する。
   ヒープは247KB空いており真のメモリ不足ではない(同メッセージは
   サイズ計算異常でも出る)。同一wasmはLinux x86-64/x86-32のWAMR 2.4.0
   (fast/classic両方)で正常ロードでき、実機でもClassicなら正常。
   → 切り分け: Fast=失敗/Classic=成功を同一環境・同一wasmで確認済み。
   → 当面の方針: Classicを正とし、速度はAOT(M1b)で追う。
   → WAMR本体/コンポーネントへの報告候補(対象版は dependencies.lock の値で特定)。

3. **ESP-IDFのpthread_self()アサート**。WAMRはWASM関数呼び出し時に内部で
   pthread_self()を使うが、ESP-IDFのpthread_self()はpthreadとして作られた
   タスク以外から呼ぶとassertで停止する(実機で実際に停止、バックトレース取得済み)。
   app_mainの素のmain_taskから直接呼んではならず、**WAMRの処理は必ずpthread上で
   実行する**。dyneランタイム(M2以降)の実装規約とする。

4. **自動書き込みリセットの不安定性**。FT231XSのDTR/RTS自動リセットが
   「Wrong boot mode detected (0x13)」で失敗することがある(2/4回)。
   FLASH押下+RESETの手動操作で確実に回復。恒常対策はハブ非経由の直挿し・
   短いケーブル・ボーレート115200への低下。

5. **CPUクロックの既定値**。ESP-IDF既定は160MHzで、ESP32の定格240MHzを
   使っていない。menuconfig(ESP System Settings → CPU frequency)で240MHzに
   変更すると計算がちょうど1.5倍速になった。M2以降のプロジェクトでは
   sdkconfig.defaultsに`CONFIG_ESP32_DEFAULT_CPU_FREQ_240=y`を含める。

## 成立判定

- **正しさ: 成立**(PC完全一致)。WASMのポータビリティの主張が実証された。
- **メモリ: 成立**(使用129KB/残119KB)。M2のWi-Fi(実測目安70KB前後)を
  足しても収まる見込みだが、余裕は薄くなる。線形メモリの削減余地
  (N_MAXの縮小で64KBまで下げられる)を予備カードとして保持。
- **速度: 通訳方式では不成立**(実時間の約800倍遅い)。AOT検証(M1b)が必須。

## M1b: AOT(事前コンパイル)の検証 — 不成立で完了(2026-08-07)

**結論: 現行ツールチェーン組合せ(WAMRコンポーネント2.4.0~1 × Espressif LLVM
18.1.2/19.1.2)では、ESP32上のXtensa AOTは最初のWASM関数呼び出しで
クラッシュし不成立。** 目標1の速度は当面Classic通訳の79.5ms/ステップが確定値。
AOTは上流の修正後に再訪する(下記「残された一手」)。

### 前提として判明した配布状況

- 公式配布のwamrc(全OS)にXtensaバックエンドは入っておらず、Espressif版LLVM
  (実験的Xtensaターゲット)を自前ビルドしてwamrcを作る必要がある。
  → **Dyneが将来AOT配布するには自前ツールチェーンの構築・配布が必須**(A-3への示唆)。
- 本検証ではWSL2上にLLVM+wamrc(2.4.0、ランタイムと同版)を構築した。
  途中、Ubuntu 26.04の既定GCC 15ではLLVM 18系がビルド不能(SmallVectorエラー)
  → GCC 13指定で解決、という環境知見も得た。

### 試行と結果(すべて実機・再現ログ取得済み)

| 試行 | 変換条件 | .aotサイズ | 結果 |
|---|---|---|---|
| 初回 | LLVM18, O3 | 7,776B | ロード成功→初回呼出しでLoadProhibited (PC=0x4008ce1a, 化け値0x81008136+0x10参照) |
| A | +--cpu=esp32 --bounds-checks=1 | 7,776B(同一) | 既定値と同一コードのため実質未変更 |
| B | +--enable-indirect-mode | 6,184B | ローダが拒否:「間接モードのファイルにコード再配置が残存」→ **Xtensaでは間接モード構造的に不可** |
| C | --opt-level=0 | 11,124B | 同型クラッシュ(化け値0xbf14e528+0x10)→ 最適化非依存 |
| D | LLVM 19.1.2で再構築, O3 | 7,692B | **初回と完全同一のクラッシュ状態**(PC・レジスタ・化け値まで一致) |

### 対照実験(PC)

同一wasmを同版WAMR(2.4.0)でx86_32向けにAOT変換すると、2000ステップ完走・
誤差/代表値がすべて実機Classicと全桁一致。**モジュールのAOT適性とAOT機構
一般には問題なし。異常はXtensa経路のみ。**

### 分析(上流報告の核)

生成コードが異なる2つの.aot(LLVM 18版と19版)が、PC・レジスタ・不正アドレス
まで**ビット単位で同一のクラッシュ状態**を示した。生成側を変えても不変である
以上、系統誤りは実機側ローダのXtensa AOT再配置処理(aot_reloc_xtensa /
リテラル配置)にある可能性が高い。症状も「再配置されていないリテラルを読んで
その値+0x10を参照」という形と整合する。4試行はすべてコンパイラ側の変更であり、
ランタイム側(2.4.0~1)は不変だった——これが唯一動かしていないレバーである。

### 残された一手(将来のM1c)

WAMRランタイム側を新しくする: managed_componentsのWAMRをcomponents/へ移して
固定を外し、WAMR本体mainのaot_reloc_xtensa系修正を適用(または本体ごとmainに
更新、その場合wamrcもmainで作り直してAOT形式版を揃える)。上流issue報告と
セットで、M2以降の適当な待ち時間に実施する。

および19.1.2)/ランタイム: espressif/wasm-micro-runtime 2.4.0~1 / ESP-IDF 5.5.5。
