Interface、バイナリ同士が関数名・引数・メモリ配置をどう取り決めるかの規約)。

## 1. 「重いAIランタイム」が本来行っていること

PyTorchやONNX Runtime(いずれも数百MB規模で、PC/サーバーのOS・仮想メモリ・動的リンクを
前提とする)が1回の推論・学習の裏で担っている仕事は、分解するとおおよそ次の8つになる。

| # | 機能 | 中身 |
|---|---|---|
| R1 | モデル形式の読み込みと解釈 | ファイル(ONNX等)を読み、計算グラフ(演算の依存関係の有向グラフ)を組み立てる |
| R2 | 演算カーネルの提供 | 行列積・畳み込み・活性化関数など、あらゆる演算の実装ライブラリを「全部入り」で持つ |
| R3 | メモリ管理 | テンソル(多次元配列)を実行中に動的に確保・解放し、再利用を最適化する |
| R4 | 自動微分 | 計算グラフを逆向きにたどって勾配を作る(学習に必須) |
| R5 | 最適化器 | SGDやAdamなど、勾配から重みを更新する手続き |
| R6 | ハードウェア抽象 | 同じグラフをCPU/GPU/アクセラレータへ振り分け、BLAS(基本線形代数ライブラリ)等を呼び分ける |
| R7 | スケジューリング | 演算の実行順・並列実行・バッチ処理の管理 |
| R8 | 配備と差し替え | モデルの入れ替え、バージョン管理、リモートからの更新 |

ESP32(RAM約520KB、OSなし・リアルタイムOSのみ)にはこの「全部入り+実行時に何でも
決められる柔軟性」が載らない。これが当初計画(2026-07-08-plan.md)の「重いランタイムを
除去して計算グラフと重みデータを切り出す」の出発点である。

## 2. 当初計画での振り分け(2026-07-08)

当初計画は上の8機能を2つのレイヤーに割った。

- **コンパイラレイヤー(PC、実行前)**: 「重いランタイムの除去=計算グラフと重みの
  切り出し」「分割」「軽量化」「エッジ最適化」「通信ロジックの注入」「WASMアクター化」。
  → R1・R2・R6の大半を**実行前に済ませて、結果だけをWASMに焼き込む**という方針。
- **ランタイムレイヤー(マイコン、実行時)**: 「物理モデルが動くコンテナを、マイコン上で
  実行・協調させるための**超軽量ミドルウェア**であり、従来の重いランタイムにとって代わる」。
  → 残りの、どうしても実行時にしかできない仕事(実行そのもの・協調・差し替え)だけを持つ。

用語の規約(2026-09-01確定、spec-review A-5改訂): 本プロジェクトで「ミドルウェア」と
言えばこのランタイムレイヤーの軽量ミドルウェアだけを指し、通信の文脈では使わない。

## 3. 現在の実装での振り分け(実測に基づく現状)

8機能が現在どこに行ったかの対応表。「焼き込み」=コンパイル時にアクター(.wasm)の中に
固定されたもの。「ミドルウェア」=ホスト側が実行時に担うもの。

| # | 機能 | 現在の居場所 | 具体物 |
|---|---|---|---|
| R1 | グラフの解釈 | **消滅(焼き込みで不要化)** | グラフを実行時に解釈する代わりに、計算手順をRustで直接書いて`wasm32-unknown-unknown`へコンパイル。差分法アクター(heat1d-actor)はステンシル計算、学習型アクター(heat1d-pinn-actor)はtanh基底のネットワークそのものがコード |
| R2 | 演算カーネル | **焼き込み** | 必要な演算だけが入る。全部入りライブラリは存在しない(no_std、外部依存ほぼゼロ) |
| R3 | メモリ管理 | **焼き込み(静的化)+ミドルウェア(器の確保)** | アクター内は固定長配列のみで動的確保なし(線形メモリ1ページ=64KB固定)。その64KBの器を実行時に確保するのはホスト(WAMR/wasmiのインスタンス化) |
| R4 | 自動微分 | **焼き込み(手動実装化)** | 学習型アクターはu, u', u''のジェット(関数値と導関数の組)を厳密に順伝播する式を直接実装。実行時のグラフ逆走は存在しない |
| R5 | 最適化器 | **焼き込み** | レーベンバーグ・マーカート法(LM法)がアクター内に実装済み(固定5反復、幅上限32) |
| R6 | ハードウェア抽象 | **WASM自体+ミドルウェア** | CPU差(Xtensa/RISC-V/x86)はWASMが吸収。実行はESP32=WAMR通訳方式、PC=wasmi。AOTはXtensa不成立(M1b)、RISC-Vで再検証予定 |
| R7 | スケジューリング | **ミドルウェア** | 1アクター=1ノードなので演算間の並列化は不要になり、「ステップをいつ刻むか」(step_period_msの絶対時刻ペーシング)と周辺タスク(センサ・通信)との共存管理に置き換わった |
| R8 | 配備と差し替え | **ミドルウェア+制御面** | .wasmの積み込み(現状はファームウェア同梱、無線差し替えは将来)、MQTT経由の設定注入(係数・役割・校正値)が実行時の自由度 |

さらに、重いランタイムには存在しない仕事が1つ追加されている:

| # | 機能 | 居場所 | 具体物 |
|---|---|---|---|
| +1 | **境界協調(通信ロジック)** | ミドルウェア | 40バイト境界交換メッセージ(dyne-wire)の送受・再送・取り置き。アクターはABI関数で値を出し入れするだけで、通信を知らない |

### 契約面(ABI)が振り分けの境界線そのもの

焼き込み側とミドルウェア側の境界は、アクターがエクスポートする12関数で固定されている
(crates\heat1d-actor\src\lib.rs。学習型も同じ面を実装):

```
初期化・設定   dyne_init / dyne_set_bc_value / dyne_transparent_coef
境界協調       dyne_set_neighbor / dyne_boundary_value / dyne_boundary_grad
時間発展       dyne_step
観測・同化     dyne_observe / dyne_set
状態の読み出し dyne_len / dyne_get / dyne_x
```

この面より内側(数値解法・NN・最適化器)はコンパイル時に決まり、外側(いつ呼ぶか・
何をつなぐか・どの観測値を渡すか)は実行時にミドルウェアが決める。M0レポートの
「C ABIはランタイム非依存」という確認が、この面の両側を独立に差し替え可能にしている
(同じ.wasmがPCのwasmiでもESP32のWAMRでも動く根拠)。

## 4. 「軽量ミドルウェア」と今のファームウェアの関係

**別物ではなく、ファームウェアがミドルウェアを内蔵している**。node-esp32の中身を
役割で塗り分けると:

| node-esp32の部品 | 役割 |
|---|---|
| WAMR組み込み・wasm積み込み・ABI呼び出し・ペーシング(main.cの中核) | **ミドルウェア本体**(当初計画のランタイムレイヤーのESP32実装) |
| 40バイト境界交換の送受(dyne-wire準拠) | **ミドルウェア本体**(通信ロジックの注入) |
| MQTT制御面クライアント(設定受信・テレメトリ・生存通知) | コントロールプレーンの端点(ミドルウェアではなく制御面。用語規約どおり区別する) |
| センサ読取タスク(DHT20等)・電波強度タスク | 実験1用の付加物(デジタルツインの観測入力) |
| Wi-Fi/FreeRTOSの初期化・ブート列 | ESP32という土台の都合(どの実装でも要る下回り) |

同じミドルウェア役は3実装ある: **node-esp32**(実機)、**dyne-sim + dyne-core**(PC上の
Nノードシミュレータ。仮想時刻・仮想ネットで決定論)、**dyne-host**(歴史的な2プロセス版。
保存のみ)。3つが同じ.wasmと同じワイヤ形式を使うことが、ビット一致検証と「シミュレータで
規模検証・実機で成立判定」という開発方針(spec-review冒頭)の土台になっている。

## 5. 当初計画からの差分(何が未実装で、何が置き換わったか)

- **コンパイラレイヤーのパイプラインは未実装**。当初の「ONNXを受け取りランタイムを
  除去する」自動変換はまだなく、現状はアクターを**最初からRustで手書き**している。
  ただし効果は同じ(むしろ徹底している): 実行時に解釈するものが何も残っていない。
  ONNX経路(tract/burn)はspec-review A-3の設計のまま将来課題。
- **エッジ最適化(AOT)は半分だけ成立**。WASM→機械語の事前コンパイルはXtensa
  (ESP32-WROOM-32)でローダの再配置処理が原因と疑われるクラッシュにより不成立(M1b)。
  現行実機は通訳方式で運転し、実験1の規模では時間予算に収まることを実測で確認済み
  (約20〜25ms/ステップ、周期1秒の2〜3%。architecture-notes §4)。AOTはRISC-V
  (XIAO ESP32-C6)で再挑戦する計画(M1c)。
- **動的構成(参加・離脱・幅の変更)のミドルウェア側対応は部分実装**。シミュレータでは
  不在ノード・観測専用役・保留検証まで動くが、実機での動的差し替え(R8の無線更新)は
  未着手。
- **学習ジョブの多重実行(実行スロット)**はspec-review A-6の設計のみで未実装。

## 6. まとめ(一文ずつ)

- 重いランタイムの仕事は「実行時に何でも決められる柔軟性」の塊であり、その大半
  (グラフ解釈・カーネル選択・自動微分・最適化器)は**コンパイル時に決めてしまえば消える**。
- 消えない残り(実行の器・時刻の管理・差し替え・協調通信)だけを集めたものが
  **軽量ミドルウェア**で、当初計画のランタイムレイヤーはこの読みが正しかったことが
  実装で確認された。
- 今のファームウェアは「ミドルウェア+制御面の端点+実験用センサ」の同居体であり、
  ミドルウェア部分はPC版(dyne-sim)と実機版(node-esp32)の2実装が同じ契約面
  (12関数のABIと40バイトワイヤ)を共有している。
