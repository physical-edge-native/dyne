# 2026-08-16-M2手順書(docs\2026-08-16-m2-guide.md)

## 概要

ESP32を2台使い、Wi-Fi直結(接続形態=案b)で境界同期・協調推論を実行する。
プロジェクトは`m2-esp32`。同一のファームウェアから、menuconfigの役割設定だけを
変えて2つのバイナリを作り、それぞれのボードに書き込む。

所要時間の目安: 初回ビルド10分+役割切替の再ビルド数分+書き込み2回+実行約3分。

役割:
- **ノードA** = アクセスポイント役。Wi-Fiネットワーク「dyne-m2」を自分で立てる。
  担当は左半分 [0, 0.5] の33点。
- **ノードB** = 子機役。「dyne-m2」に接続する。担当は右半分の32点。

ルーターも設定入力も不要(SSIDとパスワードはファームに焼き込み済み)。

## 1. 準備(USBデータケーブル1本での運用)

必要なもの: データ通信対応USBケーブル×1、**2台目の電源**(スマホ用USB充電器や
モバイルバッテリー+充電専用ケーブルで可。実行中のボードはデータ通信不要)。

**モニタ接続はノードA側の1本だけでよい。** ノードBは実行終了後、自分の
レポートをWi-Fi経由でAに送り、Aのモニタが両ノードぶんを表示する
(ファームに転送機能を実装済み)。

書き込みはデータケーブルを差し替えて1台ずつ行う。COM番号はボードごとに
変わりうるので、差し替えのたびにデバイスマネージャーで確認する。

## 2. ノードAの書き込み

ESP-IDF PowerShellで:

```powershell
cd C:\Users\koyab\Documents\dyne\m2-esp32
idf.py set-target esp32
idf.py menuconfig
```

menuconfigで **Dyne M2 → Node role → Node A (access point, left half)** を
確認(既定でAになっている)。`S`保存→`Q`終了。

```powershell
idf.py -p COMa build flash
```

(初回はWAMRコンポーネント取得+フルビルドで10分前後。monitorはまだ開かない。)

## 3. ノードBの書き込み

同じプロジェクトで役割だけ切り替える:

```powershell
idf.py menuconfig
```

**Dyne M2 → Node role → Node B (station, right half)** に変更、保存して終了。

```powershell
idf.py -p COMb build flash
```

(役割切替はWi-Fi部分の再コンパイルのみ、数分。)

## 4. 実行(ケーブル1本版)

1. Bのボード(手順3で書き込んだ方)を充電器等の電源に繋ぐ。まだRESETは押さない
   (電源投入で勝手に走り出すが、Aを探してリトライし続けるだけなので実害なし)。
2. データケーブルをAのボードに繋ぎ、ESP-IDF PowerShellでモニタを開く:
   ```powershell
   cd C:\Users\koyab\Documents\dyne\m2-esp32
   idf.py -p COMa monitor
   ```
3. **AのボードのRESETを押し、`access point 'dyne-m2' up`の表示を確認してから、
   BのボードのRESETを押す。**

進行の目安: Aのモニタに`starting 2000 steps...`→500ステップごとの進捗→
約3分で完了。Aは自分のレポートを表示した後、
`waiting for node B report over Wi-Fi (up to 15s)...`と出て、数秒以内に
`---- report relayed from node B ----`としてBのレポートが続けて表示される。
**Aのモニタ1画面に両ノードのM2 REPORTが揃えば持ち帰り完了。**

## 5. 期待される出力と合否

各ノードが最後に出すM2 REPORTの例(数値は実測で埋まる):

```
==== M2 REPORT (role A) ====
steps              : 2000 (warmup 100 excluded from wait stats)
free heap wifi/inst: ...... / ...... bytes
min free heap      : ...... bytes
total wall         : ...... ms
compute            : ...... ms total, ...... ms/step
sync wait us       : min=... med=... p95=... max=...
sync overhead      : ...... %
msgs               : sent=.... resend=.... replay=.... crc_err=....
L2 / Linf (own dom): ....e-5 / ....e-5
CRC32(u bytes)     : 0x........ (expect 0x3CC6AD26) -> MATCH
==== END ====
```

**合否は最後のCRC行で自己判定される。** AがMATCH(期待値0x3CC6AD26)、
BがMATCH(期待値0x8AC47DE7)なら、2台の分割解が単一ノード解と
ビット完全一致したことを意味し、M2合格。期待値はPC上で単一ノード解から
事前計算した値がファームに内蔵されている。

持ち帰ってほしいもの: **両ノードのM2 REPORT全文**(限界レポート第4号の
材料。特にsync waitの分布とresend数がシミュレータ校正値になる)。

## 6. トラブルシューティング

**Bが`connecting to 'dyne-m2'...`のまま進まない** → Aが起動していない/
AP起動前にBが探し終えた。Aの起動を確認してからBをRESET。Bは自動リトライ
するので放置でも通常は繋がる。数分待っても駄目ならAをRESETしてやり直し。

**A側で`instantiate failed`(メモリ不足)** → Wi-Fiのアクセスポイント役と
線形メモリ128KBの併存に失敗した場合。軽量版wasm(線形メモリ64KB、同梱済み)に
切り替える: `main\CMakeLists.txt`のEMBED_FILESを`"heat1d_actor_small.wasm"`に、
`main.c`のシンボル2行を`_binary_heat1d_actor_small_wasm_start/end`に変更して
両ロール再ビルド。**この切替が起きたこと自体が限界レポートの重要データ**なので
必ず記録すること(役割Aのみで起きたか、両方かも)。

**片方だけ先に完了して相手が止まる** → 終了時ドレイン(3秒)内に回復するのが
正常。3秒を超えて止まる場合は両ノードのその時点の表示を持ち帰る。

**`WARN: node B report not received`が出た** → 転送パケットが全滅した稀な
ケース。予備手順: データケーブルをBに差し替えて`idf.py -p COMx monitor`を開き、
**AのRESET→BのRESETの順で再実行**すると、今度はBのレポートがBのモニタに
直接表示される(AのレポートはCRC期待値0x3CC6AD26のMATCH/MISMATCHだけ
前回の画面から控えておけば十分)。2回の実行はそれぞれ独立に有効。

**書き込み時のConnecting...停滞** → いつもどおりFLASH押しながらRESET。

**crc_errが多発する** → 電波環境の問題(他のWi-Fiとの干渉)。ボード間の距離を
1〜2mにし、電子レンジ等から離す。crc_err数も計測データとして記録価値あり。

## 7. 完了後

両レポートを受領後、こちらで限界レポート第4号の清書、仕様書C章のM2完了化、
実測値(遅延分布・喪失率)のM-S0シミュレータへの注入検証を行う。
