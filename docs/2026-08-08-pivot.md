# 2026-08-08-方針転換(docs\2026-08-08-pivot.md)

## 思想
「群としてのAI」：独立した多数のAIモデルが何等かの通信をしながら協調して推論・学習し、互いに影響しながら動作する。
「空間をAI化する」：既存のワールドモデル学習は視覚への依存度が高い。人間の感覚に基づいたセンシングを離れて、多様な物理量のセンシングによってワールドモデルを作れると面白い。
「NNを動的に構成する」：現存するマルチエージェントは、深さや幅が固定されたNNをエージェントとして、エージェントを複数並べて協調させるものである。協調推論中・分散学習中にエージェントのNNを動的に構成できるマルチエージェントシステムは新規性が高い。

## 開発方針
シミュレータ開発：ハードウェアの購入や組み込みLinux機器の購入に使える予算が少ないため、ソフトウェア開発やシミュレータの開発、シミュレータ上での検証に時間を割く方針。

## マイコンについて
現状はXtensaのESPrDeveloper32typeCを4台持っていて、M1ではインタプリタ実行では動いた。ただし速度に課題があり、AOT実行を試して失敗した。(インタプリタ実行では動いていたWASMモジュールについて、高速化を図ってAOT実行で動くか試したところ、AOTファイルの読み込み・インスタンス化までは成功するのに、最初の関数呼び出しで必ず不正メモリアクセスが起きる問題。)
- M2（マイコン2機での境界同期）はESPrDeveloper32typeCをこのまま使う。
- 問題はIssueとしてWAMRのリポジトリに投げておく。
- ニューラルネットの実機推論に進む際はESP32-C6など他のボードを調べて入手する

## 通信について
もともとのアイデアとしては、データ収集やコマンド送信用にMQTTブローカーを持つノードを用意し、Pub/Subでの通信を行うことを考えていた。
- 「群としてのAI」という見方で考えると、P2Pで通信できれば十分。
- ただし、ユーザが群全体を観測するには、ブローカーノードを持たせてデータの吸い上げを行うか、あるいはユーザがAPIを叩いて各マイコンが持っているデータを取得できる必要がある。

MQTTブローカーの要否について、ROS2を参考に考えた結果、当面は不要という判断になった。この形なら、mDNS+リーダー選出+MQTTブローカー+スプリットブレイン対策という一連の機構がまるごと削れる可能性がある。
- ROS2との比較：ROS2のDDSは中央ブローカーを持たないP2Pのpub/sub
- マイコンの制約：DDSはRAMの問題で難しい
- 今後の方針：
    1. マイコン群の自律動作 → P2P pub/subで完結
    2. 群全体の観測 → 開発者PCがpeerとして参加し、ワイルドカード購読で全ノードのデータを受ける
    3. 同期的なコマンド → 各マイコンの軽量APIサーバー(既存設計のまま)
- ROS2を参考に、zenohの導入を検討。その場合は以下のようになる。
    1. シミュレーションプレーン(境界同期) → 現行のまま。自前のUDP・固定長バイナリ・論理ステップ同期。Zenohは使わない。
    2. コントロールプレーン(テレメトリ・コマンド・ハートビート・観測) → ここをMQTT+mDNS+選出ロジックの代わりにZenohで置き換える候補とする。また、zenohを採用する場合でも軽量APIサーバーはユーザPCからの同期的な通信のために必要。
- zenohにも課題はある。
    1. 観測者不在時のデータ保持（MQTTのretainやローカルキューイング相当）
