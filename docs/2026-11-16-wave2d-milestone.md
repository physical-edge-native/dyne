# 2次元の波動方程式を多数の区画に分けて CPU で解く — ビット一致と並列化の効率(2026-11-16)

> barye リポジトリ(physical-edge-native/barye@760cd20)から移した(2026-11-16、Issue #38)。コマンド名・パスは Dyne での名前に置き換え、Issue 番号は barye のもの(physical-edge-native/barye#N)と明記した。本文の「Barye」は移す前のプロジェクト名。
> 用語: この文書の「区画」は各ノードの担当区間(合意済みの用語の「区画」と同じ)、「境目」は界面(ノードとノードの区画の境目)を指す。

作成: Claude Code(下書き。メンテナーの編集前)。関連: Issue physical-edge-native/barye#2(First development milestone, 2D)。
内部向けの作業記録。第三者向けの説明は README.md(英語)にある。

## 0. 要約

- 2次元の波動方程式を、格子を px×py の区画(パッチ)に分け、**1区画を1スレッド**で解く仕組みを作った。
  区画どうしは毎ステップ、**境目の値1列だけ**を、Dyne のメッセージ形式(ワイヤ形式 v2 の IFACE_BAND)で
  隣の区画とだけ交換する(全体の同期はステップのループの中にない)。
- 区画の計算部品は、Dyne の WebAssembly(ブラウザ外でも動く移植性の高い命令形式。以下 wasm)の
  波動方程式の計算部品 `wave2d-actor` と**同じ浮動小数点の演算を同じ順に行う Rust のネイティブ実装**を主にした
  (後述の (b))。wasm の計算部品を `wasmi`(wasm の解釈実行系)で動かす経路 (a) も用意し、両者の一致を確かめた。
- **ビット一致**: 単一区画の解と、1×1・2×2・4×4・8×8・3×5・7×2・1×6・6×1 の分割解が、値固定・ゼロ勾配・
  吸収境界・混在、および安定条件を超えて発散する場合(クーラン数 0.72)のすべてでビット一致した。
  さらに、Dyne が自分の回帰シナリオで記録した**全体の場の CRC32(誤り検出用のハッシュ値)10件を、
  Barye のネイティブ実装が単一区画でそのまま再現**した(Dyne の分割の形でもビット一致)。
- **ネイティブ = wasm**: 4種の境界で、単一区画・3×2 分割(wasm をスレッドごとに1個)の場がビット一致し、
  境目のメッセージは毎ステップ**バイト単位で同一**だった。速さはネイティブが約 80〜120 倍。
- **並列化の効率は低い**(この PC では)。理由は主に2つ: (1) 1点あたりの計算が軽く、**メモリの帯域で頭打ち**に
  なる(大きな格子)、(2) この PC の CPU は**速さの違うコアの混在**で、6スレッドを超えると1区画あたりの計算時間が
  伸びる。小さな区画では、待ち合わせ(スレッドの起床)の時間も効く。測定は電池駆動の状態で行った(§4.1)。

## 1. 選んだ方式と理由

### 1.1 (a) wasm の計算部品をそのまま動かす / (b) 同じ演算順のネイティブ実装

| | (a) Dyne の wasm を `wasmi` で動かす | (b) ネイティブ実装(採用、主経路) |
|---|---|---|
| Dyne の機器との共有 | 同じバイナリそのもの | 同じ式・同じ演算順(ビット一致を CI で確認) |
| 速さ(192×192、1区画) | 3.32 ms/ステップ | 0.027〜0.040 ms/ステップ(**約 80〜120 倍速い**) |
| 区画の大きさ | 1辺 196 点・枠つき 40,000 点まで(wasm 側の静的確保) | 制限なし |
| 依存 | wasm のビルド(wasm32 のターゲット)が必要 | なし |

(b) を主経路にした理由: 並列化の効率を測る目的では、(a) は解釈実行の遅さが支配して計算と通信の比が
実際と違ってしまう。区画の大きさの上限もある。一方、(b) が (a) と同じであることは、(1) Dyne の記録した
CRC32 の再現(全 OS の CI で、wasm 無しで確認できる)、(2) 同じ問題での場と境目のメッセージのバイト一致
(wasm を CI でビルドして確認)の2段で保証した。(a) の経路も残し、`dyne-native-wave2d --wasm` で使える。

演算順を揃えるために守ったこと: ラプラシアンは `(u_W − 2u + u_E) + (u_S − 2u + u_N)` の順、
更新は `2u − u^{n−1} + ν²·lap`(最初のステップは `u + (ν²/2)·lap`)、ν² と ν²/2 と吸収境界の係数
(ν−1)/(ν+1) は初期化で1回だけ計算、初期条件は純 Rust の数学ライブラリ libm(Dyne と同じ 0.2.16)。
Rust は乗算と加算を勝手に融合(FMA)しないので、自動ベクトル化されても各点の演算は同じ。
外周の境界の適用順(吸収境界を西・東・南・北、その後に値固定。角は後の面が勝つ)も同じにした。

小さな実装判断: ネイティブ実装では、受け取った隣の値を別の配列に置かず、枠(ゴースト点)へ直接書く。
値は同じで、写しが1回減る。

### 1.2 スレッドの形

- 1区画 = 1スレッド(`std::thread::scope`)。区画の計算部品はそのスレッドの中で作る(メモリを最初に触るのが
  使うスレッドになるように)。
- 交換は区画ごとの受信用チャネル(`std::sync::mpsc`)。各区画は「自分の境目の値を送る → 同じステップの隣の値が
  揃うまで受ける → 1ステップ進む」を繰り返す。隣より最大1ステップ先に進めるので、先のステップの
  メッセージは取っておく。**全体のバリア(全スレッドの待ち合わせ)はループの外(開始と終了)だけ**。
  結果はスレッドの実行の順序によらない(メッセージのステップ番号と送信元で照合するため)。
- 1つの区画が失敗したら全体を止めて最初の誤りを返す(待っている区画は 50 ms ごとに中止の印を見る)。
  テストあり(わざと失敗させても固まらない)。
- 待ち方の選択肢として、受信を一定時間ぐるぐる確かめてから眠る「スピン」(`--spin-us`)を付けた。既定は 0
  (すぐ眠る)。§4 のとおり効くかどうかは条件次第なので、既定は変えていない。

### 1.3 Dyne の形式をどこで使ったか

- 境目のメッセージ: ワイヤ形式 v2 の IFACE_BAND(ヘッダに界面の番号とステップ、本体に f64 の列)、
  量は変位(QTY_DISPLACEMENT)、枠は Dyne のメールボックスと同じ `[u32 長さ][メッセージ]`。
  wasm の計算部品の送信箱の中身をそのまま隣へ渡せるので、(a) と (b) を同じ実行器で動かせる。
- 界面の番号付けと区画の分け方(先頭の区画から1点ずつ余りを配る)は Dyne の dyne-sim2d と同じ(テストあり)。
- 使わなかったもの: dyne-core の仮想時刻・仮想ネットワーク(損失・遅延)。Barye は実時間で本物のスレッドを
  動かすので不要。dyne-core の wasm 読み込み(`actor.rs`)は1次元の差込口専用なので、2次元の差込口
  (`dyne_init2d` など)の読み込みは Barye 側に書いた(`wasm2d.rs`、`wasmi` 0.47 は Dyne と同じ版)。

### 1.4 3次元への伸ばし方

- 分割(`decomp.rs`)は次元 D を型の引数にした: 区画の原点・大きさ・面(番号 = 2·軸 + 側。2次元で Dyne の
  西0・東1・南2・北3 と一致し、3次元で z の下側4・上側5)・界面の番号付け・全体の場の組み立て。
  3次元のテスト(界面がちょうど2区画で共有される、組み立てで全点が戻る)を付けた。
- 計算部品の差込口(`PatchSolver`: 送信箱・受信箱・1ステップ・場の読み出し)と実行器は次元によらない。
  3次元の面は2次元の値の集まりを1列の f64 として送る(IFACE_BAND の数の欄は u32 で足りる)。
- 3次元の波動方程式は、新しい計算部品(7点のラプラシアン、安定条件 ν ≤ 1/√3)を足すだけでよい。
  ただし、Dyne と共有する wasm の 3次元の差込口(`dyne_init3d` 相当)は Dyne 側に無い(未解決 §6)。

## 4. 並列化の効率

### 4.1 測定の条件

- CPU: Intel Core Ultra 7 155H(16コア 22スレッド。内訳は、2スレッドずつ動く高性能コア6、高効率コア8、
  低消費電力の高効率コア2)。Windows 11、電源プラン「バランス」、**電池駆動**(測定中に気づいた。電源につないだ
  状態での再測定が望ましい)。スレッドをコアに固定する指定はしていない(OS に任せた)。
- 問題: 定在波 sin(πx)·sin(πy)、値固定0、クーラン数 0.5。正規化数でない極小の値(非正規化数。多くの CPU で
  非常に遅い)が出て時間を乱さないように、ガウス型の山ではなく定在波を選んだ。
- 時間: スレッドが準備を終えてから全区画が最後のステップを終えるまでの実時間 ÷ ステップ数。各条件5回の中央値。
  「計算」は各区画が1ステップの計算そのものに使った時間(平均 / 最も遅い区画)。実時間との差が、
  メッセージと待ち合わせの時間。
- 効率: 強スケーリング(格子を固定) = T(1) / (p·T(p))、弱スケーリング(1区画の大きさを固定) = T(1) / T(p)。
  T(1) は同じ実行器で1区画1スレッドの値。
- 再現: `cargo run --release --bin dyne-native-wave2d -- scaling --mode strong --grid 2048x2048 --cores 1,2,4,6,8,12,16,20,22 --steps 100 --repeat 5`
  など(下の各表の見出しの条件)。

### 4.7 読み取り

1. この方式(1点の計算が軽い陽解法、1ステップごとに境目を交換)は、この PC では**メモリの帯域**と
   **スレッドの起床の遅れ**で効率が決まり、22コアでの速度向上は大きな格子で約 3.5 倍、キャッシュに入る区画の
   弱スケーリングで約 5 倍(処理量。1コアの外れ値 0.123 ms を基準にすると 11 倍)にとどまった。
2. 境目の交換そのもの(メッセージの組み立てと写し)は、計算の時間の列と実時間の差から見て、大きな区画では
   小さい。差が大きいのは小さな区画で、主因は待ち合わせ。
3. 測定のばらつきが大きい(同じ条件の1コアで 1.5〜2 倍)。電池駆動・速さの違うコアの混在・スレッドの
   コアへの割り当てを OS に任せたことが疑われる。

## 5. 失敗・限界として残すこと

- 「コアを増やせば速くなる」は、この問題の大きさとこの PC では成り立たない範囲が広い。限界は計算の方式
  (メモリの帯域)と機械(コアの混在)の両方から来ている。
- 測定は電池駆動で行った。電源につないだ状態・電源プラン「高パフォーマンス」での再測定、デスクトップや
  Linux の機械での測定が必要。
