# 低レイヤ学習計画(2026-10-12〜11-08)(reference\2026-10-09-lowlayer-study-plan.md)

作成: 2026-10-09(Claude Code)。進捗に応じて本書を直接編集する。
前提: 実験1の実機実測と並行で週4〜6時間。数値計算(2026-09-27-num-study-plan-month1.md)・
PhysicalAI(2026-09-27-phys-study-plan.md)の2計画と同じ運用。対象は
コンピュータアーキテクチャ・低レイヤ(メモリ・リンカ・リアルタイムOS)・WASM
(WebAssembly、CPUに依存しない仮想的な命令形式)の3本で、ファームウェア読解
(docs\2026-10-06-node-esp32-architecture-notes.md)で残った理解負債の返済と、
AOT(事前コンパイル)再挑戦・複数アクター化など今後の判断の材料にする。

## 運用ルール

- 到達判定は「読んで分かった」ではなく、**自分のリポジトリの現物(リンカマップ・
  .wasm・main.c・実測ログ)で手を動かして確かめる**ことで満たす。
- 到達判定を全部満たしたら次の週へ進む(カレンダーより判定を優先。実験1が忙しい週は
  週をずらす)。
- 課題の結果は、該当するdocsの文書(architecture-notes、runtime-middleware-mapping)への
  追記案として溜め、更新は作業セッションで行う。
- 本計画はPC側の知識装備であり、実験1の手順(runbook)には影響しない。

## 第1週(10/12〜10/18): マイコンのメモリ — 「どこに何が置かれるか」

実験1で監視するヒープ4定点(読解ノート§2.3)を、他人の説明でなく自分の理解で
言えるようにする週。

### 読む順番

- [ ] 読解ノート §2(メモリアーキテクチャ)を再読し、分からなかった語を書き出す
- [ ] パタヘネ 第2章のうちメモリオペランド・スタックの節(2.3、2.8あたり): レジスタ/スタック/ヒープの区別
- [ ] IDFガイド Memory Types: DRAM/IRAM/フラッシュキャッシュの区別、なぜ命令用と
      データ用でRAMが分かれているか
- [ ] IDFガイド Heap Memory Allocation: heap_caps、最大連続ブロックの意味
- [ ] TRM メモリマップの章(流し読み。アドレス空間のどこがRAMかを見るだけ)
- [ ] 坂井 第1〜2章(オブジェクトファイルとリンク、セクションの概念): .text/.data/.bssが
      リンカマップの語彙そのもの

### 到達判定(3つとも満たしたら第2週へ)

- [ ] build\dyne_node.map を自分で開き、.bss の大口3つ(受信組み立てバッファ8KB等)を
      **自力で探し出して**読解ノート§2.2の表と一致させる
- [ ] 「静的62KB+ヒープ、ブート直後201KB・サービス起動後36KB」の数字の間の関係
      (どこで何に食われたか)を図1枚に手書きできる
- [ ] 実験1の初回電源投入で記録するヒープ4定点のログを見て、異常値だったら
      どの部品を疑うかを言える(R1の監視を理解で裏づける)

### 課題1: 学習型アクターは実機に載るかの見積り

- [ ] 学習型アクター(heat1d-pinn-actor)の.wasmの線形メモリ宣言ページ数を確認し、
      差分法アクター(1ページ=64KB)との差を出す
- [ ] サービス起動後の最大連続ブロック(実測)と比べ、「載る/載らない/条件つき」を
      見積もる。結果を読解ノート§2.4への追記案にする(学習型の実機適合は
      roadmap 2.5.2で「実測待ち」とされている項目)

## 第2週(10/19〜10/25): WASMという機械 — 契約面(ABI)の下にあるもの

「同じ.wasmがPCのwasmiでもESP32のWAMRでも動く」を支える仕組みを現物で見る週。
ABI(Application Binary Interface、バイナリ同士の関数名・引数・メモリ配置の取り決め)の
語を自分のものにする。

### 読む順番

- [ ] 分担文書(2026-10-09)を再読: 焼き込み/ミドルウェアの境界が12関数の面であること
- [ ] WASM論文 §1〜3(設計目標、モジュール、線形メモリ、スタックマシン)。形式的意味論の
      節は飛ばしてよい
- [ ] 入門WASM 第1〜3章(WAT=WASMのテキスト表記、関数、メモリ)
- [ ] 入門WASM のメモリ章(線形メモリへの読み書き、ページ=64KBの意味)
- [ ] WAMR文書 memory_usage(ランタイム側が何にRAMを使うか)
- [ ] WASM仕様は読み通さない。wasm-objdumpの出力で分からないセクションが出たときの辞書

### 到達判定(3つとも満たしたら第3週へ)

- [ ] `wasm-objdump -x heat1d_actor.wasm` を実行し、Export/Memory/Codeの各セクションを
      読んで、エクスポート12関数と線形メモリ1ページを**現物で**確認する
- [ ] `wasm2wat` で小さい関数(dyne_lenなど)を逆アセンブルし、スタックマシンの
      命令列として読める(push/pop の流れを口で追える)
- [ ] 「アクターは通信を知らない」(境界値はホストがdyne_set_neighborで注入する)を、
      .wasmにインポートがほぼ無いことと結びつけて説明できる

### 課題2: 1ステップの呼び出し列の書き出し

- [ ] node-esp32\main\main.c から、1ステップの間にホストがABI 12関数をどの順で呼ぶかを
      書き出す(受信→dyne_set_neighbor→dyne_step→dyne_boundary_*→送信→観測、の実順)
- [ ] 同じ列をdyne-sim側でも確認し、2実装が同じ契約面を同じ順で使っていることを照合。
      差があれば分担文書への追記案にする(ビット一致の前提条件の明文化)

## 第3週(10/26〜11/1): 実行方式と命令セット — AOT不成立の正体に近づく

通訳方式とAOTの違い、再配置(ロード時にアドレスを埋め直す処理)を学び、
M1bの「Xtensa AOTはローダの再配置処理を疑う」という切り分け(読解ノート§3)を
自分の仮説として言い直せるようにする週。M1c(RISC-VでのAOT再挑戦)の判断材料づくり。

### 読む順番

- [ ] パタヘネ 第2章の残り(命令セットとは何か。MIPSの詳細は深追いしない)と
      第4章冒頭(命令実行の流れ)
- [ ] RISC-V原典 第1〜2章(RISC-Vの設計思想、RV32I)。XIAO ESP32-C6のCPUはこれ
- [ ] 坂井 第3〜5章(リンカの仕事、再配置、動的ロード): AOTファイルをロードする
      WAMRのローダが行うのはここで学ぶ再配置と同種の処理
- [ ] 速度論文(Jangda): WASMとネイティブの速度差の要因分解。「AOTは通訳の10〜50倍」
      (spec-review A-1)の経験則の中身
- [ ] WAMR文書 wamr_running_mode(通訳/高速通訳/AOT/JITの選択肢)と
      M1系文書の再読(クラッシュの再現条件・切り分けの記録)

### 到達判定(3つとも満たしたら第4週へ)

- [ ] 「通訳方式が遅い理由」を命令ディスパッチ(1命令ごとの分岐)のコストとして説明でき、
      実機実測(1ステップ約20〜25ms、読解ノート§4)がなぜ実験1では問題にならないかを
      時間予算で言える
- [ ] 再配置とは何かを、具体例(絶対アドレス参照を持つコードを別番地に置く)で説明できる
- [ ] M1bの切り分け(PC対照で生成側は無罪→ランタイムのXtensa再配置処理を疑う)を、
      坂井の語彙で言い直した1段落を書ける

### 課題3: M1c(RISC-V AOT)の判定実験計画の下書き

- [ ] 「何を測れば成立判定になるか」を列挙する(クラッシュ再現の有無、AOT/通訳の
      速度比、AOTファイルのサイズとRAM占有、再配置種別の差)
- [ ] XIAO ESP32-C6到着後に1日でできる手順の形にして、docsの実験計画の下書きとして
      提案する(実施判断はユーザー)

## 第4週(11/2〜11/8): リアルタイムOSと時間 — 「1秒に1歩」を保証する仕組み

step_period_msのペーシング(絶対時刻目標方式、読解ノート§1)とWi-Fi・センサタスクの
共存を、FreeRTOSの語彙(タスク・優先度・tick)で説明できるようにする週。
実験1の実測データがそのまま教材になる。

### 読む順番

- [ ] FreeRTOS本 第3〜4章(タスクの状態遷移、優先度、スケジューリング)
- [ ] FreeRTOS本 のキュー・セマフォの章(流し読み。タスク間でデータを渡す定石)
- [ ] IDFガイド FreeRTOS (IDF): tick=10ms、デュアルコアでのタスク配置
- [ ] main.c のペーシング部・センサタスク・電波強度タスクを、タスク図(優先度と周期)に
      自分で描き直す
- [ ] WARDuino(マイコン上のWASM仮想機械の先行例): 自分たちの構成(WAMR+自前ホスト)
      との共通点・相違点を1段落でまとめる

### 到達判定

- [ ] 「vTaskDelayで寝る=他のタスクに譲る」を説明でき、tick 10msの粒度がペーシングの
      誤差に与える影響(±1 tick)を言える
- [ ] ペーシングが「絶対時刻目標で、遅れが累積しない」実装であることをコードで指差せる
- [ ] 実験1の実測rt(step_ms・計算時間)の分布を取り、ジッタ(ばらつき)の源を
      タスクの言葉で推定できる(R2の監視を理解で裏づける)

### 課題4: 時間予算表の実測更新

- [ ] 実験1の本計測ログから1ステップの実測時間の統計(中央値・最大)を出し、
      読解ノート§4の時間予算表を実測で更新する追記案を作る
- [ ] 「今の構成で1ステップ周期をどこまで縮められるか」(周期100ms運転の成否見積り)を
      計算時間+通信+センサの内訳で見積もる(非同期化・多物理化の前提データになる)
